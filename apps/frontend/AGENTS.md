### Permanent appearance evolution (ADR-115)

Owner clarification (2026-09-06): `cinema / premiere / montage` are permanent user-selected experience tracks, not temporary test arms and not candidates for elimination or eventual merger. The saved value follows the track as it evolves; it does not freeze one visual release. Each track advances from a versioned baseline through one scoped candidate at a time: an adopted candidate becomes the next baseline, a rejected candidate alone is removed, and the next idea starts from the latest adopted baseline. `system / light / dark` remains an independent colour preference, and no experiment or default change may overwrite an explicit saved appearance.

Terminology lock (owner correction, 2026-09-06): **theme** means only the `system / light / dark` axis. A theme changes visual atmosphere while page composition, hierarchy, density, disclosure, action placement and user experience stay identical. `system` remains the third preference and dynamically resolves to light or dark; it is not a third static palette in the current implementation. **Appearance** means only the `cinema / premiere / montage` axis. An appearance must change page distribution, composition and visual identity materially and recognisably; sharing tasks, truth, state and business logic does not permit one layout recoloured three times. Do not describe the theme goal as an appearance goal or the appearance goal as a theme goal.

The protected directions are: `cinema` = immersive, image-led, atmospheric and low-density; `premiere` = curated, editorial, ceremonial and balanced; `montage` = fast, modular, constructive, information-dense and direct-action oriented. A mature version of every track must differ materially—not as one skin recoloured—across composition, hierarchy, density, action placement, disclosure, palette, shape, depth, typography, in-product Kolme logo/lockup, icon family, numeric presentation, visual effects, motion grammar and where those devices are used.

This owner clarification supersedes any reading of IDENTITY Q9/Q24 that forces one in-product font, Kolme mark or icon artwork across all appearances. Exact assets are not frozen by ADR-115, but every track needs a distinct approved bilingual type family/pairing and a distinct in-product Kolme mark/lockup and icon family. ADR-94 self-hosting/licensing, the readable tabular-digit contract, RTL icon direction, the recognisable `Kolme` name/triad promise and official third-party marks remain protected. Every action keeps its localised accessible name on the control; decorative/redundant icons and graphic-only logo marks stay hidden from assistive technology. Numbers must differ by visual hierarchy, face, prominence, placement, enclosure, visualisation and disclosure, never by changing their value, locale, unit, precision, source or rounding.

Motion also differs by use, not only duration: cinema uses measured fades/focus/continuity for scene entry and reveal; premiere uses restrained fades/lifts/wipes for sequence and confirmation; montage uses snaps/short slides/cuts for reorder, filtering, paging and immediate feedback. All retain an equivalent static Reduced Motion path, immediate input response and the same accessible state. Track-specific composition, tokens and assets remain variants over one route/component/state/data tree; do not fork business logic or create three products.

Treat the current implementation as `Baseline v1 — owner-approved visual baseline; pre-measurement; complete per-track structural and identity differentiation not yet established`: fonts, Kolme mark, icon artwork, numeric grammar, motion and composition are still shared. Before opening a candidate intended to evolve a baseline, record in its existing task or PR: track, surface and current baseline; protected identity; one hypothesis, exact delta and what stays fixed; formative success signal plus accessibility/performance guardrails; decision owner and point; rollback. This does not apply to regression, conformance or accessibility fixes that restore the accepted baseline. Keep only one active candidate per track. Use `PROPOSED → BUILT → VISUALLY_ACCEPTED → FORMATIVE_REVIEWED → ADOPTED / REJECTED`; a revision returns the same candidate to `PROPOSED`, only `ADOPTED` advances the baseline, and every closed candidate records its evidence and decision before the slot receives a new idea. The first required distinction is structural on a shared core journey; subsequent bounded candidates cumulatively complete every required identity dimension. Palette-only work counts only for an explicit colour/contrast/accessibility hypothesis.

Before public launch or while eligible human traffic is insufficient, use owner acceptance, task usability, accessibility and formative research without claims of a causal winner. Track-selection share is self-selected preference, not proof of superiority; default bias and different populations must be stated. A multi-dimension bundle supports only a bundle-level conclusion. An adopted learning may remain track-specific, be adapted to another personality, become shared when identity-neutral, or inform default policy; never copy it literally across all tracks merely because one is used more.

The future event contract is definition-only: `appearance_exposed` means that the resolved track and baseline/candidate were actually rendered; `appearance_selected` means the first successful persistence of an explicit track; `appearance_changed` means successful persistence from one explicit track to a different one. A saved preference alone does not prove exposure, and a failed or same-value write is not a change. Before activation, the closed event properties must include `selectionOrigin: default | explicit | restored`, locale, `colorPreference` and `resolvedColorMode`; reports cover consenting users only, never upload pre-consent history and never record accessibility or assistive-technology settings. A motion candidate either evaluates the static Reduced Motion fallback as part of its bundle or withholds motion-specific attribution when motion did not render. Do not add production collection or widen the analytics allowlist until matching versioned disclosure, consent and version-aware enforcement are implemented. Do not build allocation, power/sample, survey or dashboard machinery merely for the current baseline.
