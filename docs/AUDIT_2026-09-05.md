# Deep audit — backend, ML pipeline, frontend, database, infra, docs

Pinned to commit `3393eb1` on `main`. Method: six parallel read-only agents, one per layer, each instructed to verify claims against current code rather than trust prior "closed" markers. The system is already **live in production** (`kolme.app` / `api.kolme.app` on Railway) as of 2026-09-04, which raises the stakes of several findings below relative to a pre-launch audit.

## 1. Critical

### C1. Admin panel (`/admin`) has no real client-side access control — live in production
`apps/frontend/app/admin/page.tsx` renders `<AdminScreen/>` unconditionally; there is no `middleware.ts` anywhere in the app. `AdminScreen.tsx:433-450` defaults `forbidden=false`, so the full tab UI (catalog, features, models, privacy tables, filters) mounts immediately and only flips to a 403 banner if `api.adminGetTitles({limit:1})` returns **exactly** `err.status === 403`. An unauthenticated visitor has no token, so the backend call returns 401, not 403 — `forbidden` never becomes true and the admin shell stays visible/interactive. **Anyone who navigates to `kolme.app/admin` today sees the admin dashboard UI.** Underlying data calls likely still 401/403 server-side (not independently confirmed by this audit — verify), but the surface itself (tab structure, filters, which controls exist) is exposed to the public, and any admin endpoint the frontend forgets to reject would be silently walked into. Fix: gate the route on a real role check before mount, treat any non-2xx (not just 403) as forbidden, and add a server-enforced redirect.

### C2. Unclosed Postgres connections in the long-running model service — live in production
`services/workers/src/training.py:299` (and the same pattern in `evaluation.py`, `fingerprint_v2_eval.py`, `train_demo.py`): `with psycopg2.connect(database_url) as connection, connection.cursor() as cursor:` — psycopg2's connection context manager commits/rolls back on exit but **never closes the connection**. In the one-shot CLI scripts this is harmless (process exits). In `model_service.py`'s long-running worker (`run_worker` → `train_profile()` on every job — per RANKING_ALGORITHM.md §6, triggered every 3 completed triads, on demand, or nightly) this leaks one physical connection per training job for the life of the process. Against Postgres's default `max_connections` (~100), the model service will exhaust the pool after roughly that many completed training jobs — at which point every subsequent training request fails, and it can starve the Node backend sharing the same database. No test exercises `train_profile()`'s real DB path, so this is invisible to CI. **Fix**: explicit `connection.close()` in a `finally`, or restructure as `with psycopg2.connect(...) as connection:` immediately wrapped in `try/finally: connection.close()`.

### C3. Test-schema-reset guard checks the wrong variable — can `DROP SCHEMA CASCADE` the shared dev database
`apps/backend/scripts/reset-test-schema.js:11-17` checks `process.env.POSTGRES_DB` ends in `_test` before running `DROP SCHEMA public CASCADE`, but the actual connection is opened with `process.env.DATABASE_URL` — a different variable. `test/test-db-env.js` always forces `POSTGRES_DB='moviedb_test'` regardless of what `DATABASE_URL` resolves to, and lets a shell-exported `DATABASE_URL` override the composed test URL. If any session's shell has `DATABASE_URL` exported pointing at the shared dev database (plausible — load scripts like `load-imdb-ratings.ts` want exactly that) and then runs `npm run test:e2e`, the guard passes (`POSTGRES_DB` says `moviedb_test`) but the `DROP SCHEMA CASCADE` executes against the **real shared dev database** (`movie-postgres:5433/moviedb`). This is the same class of accident as A-14 (160 test accounts written to the shared dev DB in September) except destructive rather than additive. **Fix**: parse the database name out of the actual `DATABASE_URL` being used, not a sibling env var.

### C4. Railway migration service cannot run in the production image (already tracked — elevate to urgent)
This is the existing open request **A4** in `.claude/SESSIONS.md` §6 (A → C), confirmed independently by this audit: `apps/backend/railway.migrate.json:9` still has `"startCommand": "npm run migrate"`, which needs `src/` and `ts-node` that don't exist in the built `runtime` image (only `dist/` is copied; `prod-deps` omits dev deps). The compiled entry point `migrate:prod` (`node dist/migrate.js`) exists and works but `railway.migrate.json` was never switched to it. **Any future deploy that includes a new migration will fail this step.** Not new, but given the app is now live, this should be the next thing C picks up — it is a one-line fix.

## 2. High

### H1. Password-reset enumeration oracle reopens on mail-provider failure
`apps/backend/src/modules/auth/password-reset.service.ts:76-91` — `request()` calls `await this.mailer.send(...)` uncaught. The route is designed to resolve identically for real vs. non-existent emails, but `ResendMailer.send()` throws on a Resend-side error (bounce, invalid address, outage). A non-existent email returns 202 immediately (no send attempted); a real email whose send fails propagates to a 500. This both reopens the enumeration the design intends to close, and silently orphans the reset token (row saved, no email, no retry, no visible failure record). Fix: wrap the mailer call, log/audit failure, return the same response either way.

### H2. `UserTitleState.upsert()` has no handling for its own unique constraint
`apps/backend/src/modules/user-title-state/user-title-state.service.ts:22-61` does find-then-create-then-save with no transaction and no catch for Postgres `23505`, despite `@Unique(['profileId','titleId'])` on the entity. Two concurrent writers for the same (profile, title) — e.g. a double-fired `PATCH .../titles/:id/state` racing `WatchEventsService.create()`'s own call into the same upsert — both pass the initial `findOne` check and one gets a raw unhandled `QueryFailedError` (500). Every sibling service with a unique constraint (`AuthService.register`, `ProfilesService`, `TriadsService`) already has this catch-and-retry pattern; this one doesn't.

### H3. Race in `TriadsService.replace()` can silently drop an accepted replacement
`triads.service.ts:332-389` reads the triad and `priorReplacements` count, and picks a replacement title, all outside any lock; only the writes are transactional. Two concurrent `POST /triads/:id/replace` calls for the same triad (double-click, or a client retry before the first response returns) can both pass the `priorReplacements < MAX` check and both pick a title before either commits; the second `save()` overwrites the first's `titleIds`, so an accepted replacement vanishes from the triad while its `TriadReplacement` log row still claims it happened — the append-only log disagrees with the triad's actual state, with no unique-index safety net.

### H4. `holdout` column not honored by the trainer, contradicting the documented protocol
`training.py:300-308` and `evaluation.py:402-424` select every completed/ranked triad without excluding `holdout = true` rows, though RANKING_ALGORITHM.md §6 explicitly requires excluding them. Currently a no-op (`holdout` is "always false today" per `triad.entity.ts`), but it is a live landmine with zero test coverage: the day anything sets `holdout = true` for a reserved validation triad, the trainer will silently train on it, defeating the purpose, with nothing to catch the regression.

### H5. Weakest L2 regularization is applied exactly when data is scarcest
`training.py:228-233,263` — below the 5-triad floor, `chosen_regularization` defaults to the *smallest* (least restrictive) grid value, because there's no held-out slice to select from. A profile with 1-4 triads fitting a 40-dimensional weight vector is the single most underdetermined case in the pipeline, yet it gets the loosest shrinkage of any regime — and that model is served unconditionally (`serving_ranker.fit(...)` runs regardless). Worth a product/algorithm decision: should new-user models default to the *strongest* grid value instead, on the reasoning that "no information to select regularization" argues for more caution, not less?

### H6. Privacy-request/consent migration rollbacks permanently destroy tombstones
`1788454000000-PrivacyRequestsTombstone.ts:37` and `1788460000000-ConsentsTombstone.ts:28` both `DELETE FROM ... WHERE "userId" IS NULL` inside `down()` before restoring `NOT NULL`. Any rollback of these migrations after a real privacy deletion has occurred permanently erases the tombstone rows PRIVACY.md requires to survive — an irreversible data-loss path inside a nominally-reversible migration.

### H7. Missing indexes on high-traffic foreign-key columns
`embeddings.titleId`, `recommendations.titleId`, and `watch_events.titleId` all have a `CASCADE` foreign key but no index. Every title-scoped lookup and every cascading title delete on these (expected to be the largest tables) does a full scan.

### H8. `backup-postgres.sh` can silently produce an empty/corrupt backup on failure
`docker/backup-postgres.sh:21-25` pipes `pg_dump | gzip > "$OUT"` under `set -e` in POSIX `sh`, which has no `pipefail` — the pipeline's exit status is `gzip`'s, not `pg_dump`'s. If `pg_dump` fails, `gzip` still succeeds on empty stdin, producing a small-but-valid `.gz` file, and the script reports success. A restore drill run infrequently would not catch this for a long time.

### H9. `restore-postgres.sh` has no confirmation guard and defaults to the **production** compose file
`docker/restore-postgres.sh:11,20-22` — `COMPOSE_FILE` defaults to `docker-compose.prod.yml`, and `DROP DATABASE IF EXISTS` runs with no interactive confirmation (unlike the Makefile's `db-reset`, which prompts). An operator testing a restore locally, in a shell whose Docker context happens to be prod, drops the live production database with zero confirmation.

## 3. Medium

- **M1.** `outcomes.triadId` is `ON DELETE NO ACTION` while both paths that reach it from a profile (`profiles→triads` and `profiles→recommendations→outcomes`) cascade — a `ranked_later` outcome could hit an FK violation during a privacy erasure depending on trigger order. Needs a concrete test (create a `ranked_later` outcome, delete the owning profile, on `postgres-test`).
- **M2.** Tie-handling differs between the persisted training metric (`ranker.compute_pairwise_accuracy`: ties = 0 credit) and the offline acceptance gate (`evaluation.py::pairwise_hits`: ties = 0.5 credit). A near-zero-weight model (exactly the state produced under H5) makes many near-ties, so the two "pairwise accuracy" numbers for the same kind of model aren't comparable, and this isn't documented as intentional.
- **M3.** `assertNotLoopbackInProduction` only fires when `NODE_ENV==='production'` — a misconfigured staging/preview with `NODE_ENV` unset gets no protection against pointing at a loopback database.
- **M4.** `shared_latent_space_versions.createdAt` is a bare nullable `TIMESTAMP` with no DB default, while every sibling table's equivalent column is `NOT NULL DEFAULT now()` — entity/migration drift a raw insert could exploit.
- **M5.** AdminScreen's sub-tabs (catalog search, filters) mount and fire calls in parallel with the top-level forbidden check, so a logged-in non-admin briefly sees a working admin UI before any 403 response replaces it (same root cause as C1, cheaper to fix alongside it).
- **M6.** `RankScreen.submitRanking`/`confirmReplacement` rely solely on a `disabled={busy}` button attribute, not an entry guard in the handler; `api.rankTriad`'s idempotency key is generated fresh per call, so two rapid clicks before React commits `disabled` produce two distinct idempotent-looking POSTs.
- **M7.** `manifest.ts` hardcodes `lang: 'ar', dir: 'rtl'` even though the app fully supports English at runtime — an English-preference user's installed PWA still advertises Arabic/RTL to the OS.
- **M8.** `RankScreen.loadTriad` has no cancellation guard against out-of-order responses (unlike `DiscoverScreen`/`WorkScreen`, which both use one) — a stale response can clobber newer state if `profileId` changes mid-flight.
- **M9.** No URL-based routing between app sections (`view` lives only in `useState` in `page.tsx`) — reload always drops to home, browser back/forward do nothing between sections.
- **M10.** `docs/IMPLEMENTATION_STATUS.md` is ~193 commits stale relative to HEAD and contains both wrong "closed" statuses in the wrong direction (marks the admin API, frontend tests, refresh-token flow, and the backup/restore drill as ❌ when all four are done) and internal self-contradictions (says CI is ❌ in one table, "runs on every push" a section later). See §5 below for the full list — this is the single highest-leverage doc fix available, since the team visibly relies on this file for status.

## 4. Low

- Access + refresh tokens live in `localStorage`, not an httpOnly cookie (`session.tsx`). No XSS vector exists in the codebase today (no `dangerouslySetInnerHTML` anywhere), so this is latent, but it's the single biggest blast-radius amplifier if one is ever introduced — worth a deliberate "we accept this" note in an ADR rather than leaving it implicit.
- No focus management on section change in `AppShell`/`page.tsx` — skip-link and landmark exist, but switching sections doesn't move focus to the new content.
- `RankTriadDto.ranking` has no `@ArrayMaxSize(3)` before the shape check rejects it — cheap hardening, consistent with bounds used elsewhere.
- CORS origin silently falls back to `localhost:3000` in production if `FRONTEND_URL` is unset, with no boot-time check (unlike `JWT_SECRET`'s explicit guard). Fails closed, so availability-only risk.
- `ConsentsPanel.tsx` defines a `load()` callback that's never called on mount; a separate near-identical inline effect does the real fetch. Two copies of the same logic will drift.
- Stray empty directory `init-test-db.sql/` at the repo root (distinct from the real `docker/init-test-db.sql`) — Docker-created debris from a past wrong-working-directory compose run. Safe to delete.
- No `.dockerignore` — no leak (all `COPY`s are explicit/narrow), just slower builds and unnecessary build-context transfer.
- `docs/SCHEMA.md`'s changelog entry numbering drifts by one starting at 2.26 — cosmetic; the authoritative migration list in §1 is accurate.
- `docs/QUICKSTART.md` §8.1/§8.2 cites "ADR-87" as the hosting-decision ADR twice; the real one is **ADR-88** (ADR-87 is the training-trigger-timing fix).
- `docs/ARCHITECTURE_DECISIONS.md`'s ADR-26 "Update" note ("no admin route exists yet") is stale — the admin route has existed since B-4. The ADR summary table also silently skips ADR-52 through ADR-62 (eleven real ADRs missing from the index, though their full entries exist in the body).
- No ADR documents the per-user rate-limit tracker (`IdentityThrottlerGuard`, commit `42830a3`/A-10) — a real architectural change with no corresponding decision record.
- `.github/workflows/ci.yml`'s comment still describes the retired `postgres-test` compose topology (merged into shared Postgres per C-17); CI itself is unaffected (uses its own ephemeral container) — comment-only drift.

## 6. What's confirmed clean (no action needed)

- No committed secrets anywhere (`docker/secrets/*.example` are placeholders, `.gitignore` correctly excludes real secret files, `.env.example` has only dev-default/placeholder values).
- All three Docker images run as non-root, use `dumb-init`, correctly separate build tooling from the runtime stage, and have matching `HEALTHCHECK`/Railway `healthcheckPath` pairs.
- CI runs type-check → lint → unit → e2e against a real, fully disposable Postgres for every push, no ignored exit codes, no `continue-on-error`.
- No XSS surface in the frontend (`dangerouslySetInnerHTML` absent repo-wide), no open redirects, no CSRF exposure (Bearer-token auth, not ambient cookies), no secrets in the client bundle beyond a plain API base URL.
- RTL handled correctly throughout (logical CSS properties only, zero physical `left`/`right` found repo-wide).
- Service worker (`public/sw.js`) is well-scoped — caches only static assets and the last navigation shell, explicitly bypasses `/api/*` and non-GET requests.
- Entity/migration drift check across all 29 entities and 25 migrations came back clean — every column traces both ways, cascade behavior and rename/type-conversion migrations (ADR-15, ADR-16) are handled correctly including symmetric `down()` reconstruction.
- Python ML pipeline: no SQL injection (fully parameterized), no API keys logged, no SSRF surface (no external HTTP fetches in this pipeline — Wikidata/TMDB ingestion lives in TypeScript). Unit coverage of pure math (ranker scoring, small-sample edges, determinism) is unusually thorough.
- `docs/ARCHITECTURE_DECISIONS.md`, `docs/API.md`, `docs/SCHEMA.md`, `docs/FINGERPRINT_SCHEMA.md`, and `docs/QUICKSTART.md`'s actual command sequences are all current and accurate (aside from the single ADR-87/88 mislabel above) — these are the well-maintained docs in this repo.
