هذه الوثيقة تفصل مسؤولية الثيم عن مسؤولية الشاشة، حتى لا يعيد فريقان بناء المنطق نفسه أو يغيّر مطور الثيم الداكن أثناء تنفيذ الفاتح. عند التعارض، يحكم ADR-112؛ أما تدقيقات وملفات canvas الأقدم فهي سجل تاريخي لما كان معتمداً وقت إنشائها.

## 1. القرار وحالة خط الأساس التاريخية

عند خط الأساس المذكور أعلاه كان Kolme منتجًا واحدًا بواجهته ومنطقه ومكوّناته، وله وضعان بصريان شقيقان وليسا اتجاهين متنافسين:

| الوضع | الهوية المعتمدة | الحالة في الكود عند خط الأساس | حدود المهمة التالية |
|---|---|---|---|
| الداكن | الأسود المائل للنيلي/النيلي العميق الموجود: أرضية شبه سوداء، سطوح نيلية، وفعل نيلي | منفّذ ومحفوظ بقرار المالك؛ قيمه الحالية في `apps/frontend/app/styles/tokens.css` | **محفوظ وخارج نطاق تنفيذ الفاتح**؛ لا إعادة تصميم ولا إعادة ضبط لقيمه إلا بقرار مالك جديد |
| الفاتح | «طاولة المونتاج»: أرضية بيضاء، أزرق للفعل والبنية، ولمسات ليمونية محدودة، مع شخصية شريط الفيلم | **غير منفّذ وغير مقبول بعد**؛ القيم الفاتحة النيلية الحالية حالة انتقالية قديمة وليست الهدف | تُجمّد الصورة المختارة محلياً أولاً، ثم تُستخرج منها رموز دلالية وتُراجع بصرياً قبل أي تعميم على الشاشات |

كانت حالات الاختيار عند ذلك الخط `system / light / dark`، وتبقى دلالتها كما هي: `system` يحلّ إلى أحد الوضعين ولا يمثل تصميمًا ثالثًا. لم يكن وجود كتلة CSS للفاتح عندئذ يعني أن هوية «طاولة المونتاج» مكتملة.

### تصحيح المصطلحات الحاكم — قرار المالك 2026-09-06

هذه الوثيقة وADR-112 يحكمان **الثيم** فقط: `system / light / dark`. هدف هذا المحور هو تغيير الجو البصري مع ثبات تجربة الاستخدام وتوزيع الصفحة وتكوينها وتسلسلها الهرمي وكثافتها ومواضع أفعالها ومقدار الإفصاح فيها. `system` هو خيار التفضيل الثالث ويتبع وضع الجهاز ديناميكياً؛ لا يضيف لوحة ثابتة ثالثة في التنفيذ الحالي.

أما **المظهر** فهو محور مستقل: `cinema / premiere / montage`. اختلاف توزيع الصفحات وشكلها وهويتها يقع تحت ADR-115، ولا يجوز نسبته إلى الثيم. وبالعكس، لا يجوز وصف المظاهر بأنها الجو نفسه أو التخطيط نفسه مع ثلاثة ألوان؛ مشاركة الوظائف والحقائق والحالة لا تلغي وجوب اختلاف تكوينها.

لم تكن عند ذلك الخط قيم Hex معتمدة للأبيض/الأزرق/الليموني. كان الوصف اللوني يثبت الاتجاه ولا يجيز تخمين لوحة نهائية؛ لذلك اشترط العقد حفظ الأصل الذي اختاره المالك داخل المستودع وفحص التباين قبل لمس رموز الإنتاج.

## 2. ما يبقى مشتركاً وما يجوز أن يختلف

| طبقة مشتركة واحدة — لا تُنسخ | جلد بصري خاص بكل وضع |
|---|---|
| مسارات Next ومكوّنات React وبنية المعلومات وحالة الشاشة | قيم الرموز الدلالية للأرضية والسطح والخط والنص والفعل والأدوار |
| النص العربي/الإنجليزي، RTL/LTR، عقود API، التخزين والتحليلات | معاملة الحدود والظلال والغسلات بما يناسب الأرضية |
| ترتيب الثلاثية رأسياً، الأسهم كبديل ظاهر، Undo حيث يوجد فعل قابل للتراجع، وحالات الحفظ والخطأ | أصول زخرفية شرطية خفيفة، مثل معالجة شريط الفيلم في الفاتح، من خلال variant داخل المكوّن المشترك |
| Reduced Motion، أهداف لمس لا تقل عن 44px، الرجوع، مناطق الأمان ومنع التمرير الأفقي العرضي | درجات اللون الدقيقة بعد تثبيتها وفحصها؛ لا سلوك أو معنى مختلف بسبب اللون |
| الفصل الصادق بين الملاءمة الشخصية والجودة العامة والتوفر والثقة | طريقة إبراز هذه القيم بصرياً مع بقاء أسمائها ومعانيها وترتيبها ثابتة |

الممنوع صراحةً:

- إنشاء `LightScreen` و`DarkScreen` أو نسخ route/component/CSS كامل لكل وضع.
- إعادة تنفيذ السحب أو الحركة أو منطق التوصية داخل مهمة الثيم الفاتح.
- تغيير كتلة الداكن أو أصوله أو لقطاته أثناء حزمة الفاتح، إلا لإصلاح انحدار سببه التغيير نفسه وبملكية معلنة.
- وضع Hex خاص باللوحة داخل مكوّن شاشة؛ المكوّن يستهلك رمزاً دلالياً من المصدر المركزي.
- تحويل الليموني إلى لون لكل إجراء أو لكل حالة؛ هو إبراز محدود، وتُثبت دلالته مع لوحة الفاتح قبل التنفيذ.
- اعتبار صورة GPT مواصفة بكسل أو ادعاء اكتمال الفاتح من دون أصل محلي، رموز معتمدة ولقطات قبول.

## 3. تقسيم العمل ومنع التداخل

أساس التبديل موجود ولا يُعاد بناؤه: `public/theme-boot.js` يمنع وميض الثيم قبل hydration، و`app/lib/theme.tsx` يدير `system / light / dark`. الفاتح هو كتلة `:root` الأساسية لأن `system` على جهاز فاتح لا يضع `data-theme="light"`؛ لذلك لا تُنفذ اللوحة الجديدة تحت selector الصريح وحده. يُحفظ مفتاح التخزين الحالي `reel.theme` كيلا تضيع تفضيلات المستخدمين، وتبقى كتلتا system-dark وexplicit-dark متطابقتين بلا تغيير.

يُنفّذ العمل بهذا الترتيب، وكل مرحلة لها مالك واحد مسجّل في `.claude/SESSIONS.md`:

| الحزمة | المالك الحصري والملفات | بوابة البدء/الانتهاء |
|---|---|---|
| L0 — تثبيت المرجع | مالك تصميم واحد؛ يحفظ **الصورة المختارة نفسها** تحت `docs/design/light-theme-gpt-2026-09-05/` ويكتب خريطة الرموز المقترحة | لا يبدأ كود الفاتح قبل اعتماد الأصل وخريطة الدلالات؛ لا يعيد توليد الصورة ولا يستبدلها بتفسير جديد |
| L1 — أساس الثيم | مالك واجهة واحد لـ`apps/frontend/app/styles/tokens.css` · `apps/frontend/app/lib/theme.tsx` (`LIGHT_GROUND` فقط) · `apps/frontend/public/theme-boot.js` (لون الفاتح فقط) · `apps/frontend/app/manifest.ts` · `apps/frontend/app/lib/brand-icon.tsx` · `apps/frontend/app/__tests__/manifest.test.ts` واختبارات boot/provider/toggle الجديدة | يغيّر الفاتح فقط، ويثبت باختبار/لقطات أن الداكن لم يتغير؛ لا يملك الشاشات في هذه الحزمة |
| L2 — استهلاك الشاشات | يمكن تقسيم الشاشات بعد دمج L1 فقط، بملكية ملفات صريحة لا تتقاطع | لا يلمس أي مالك شاشة `tokens.css` أو plumbing الثيم؛ يستخدم الرموز/variants المشتركة ولا ينسخ المكوّن |
| L3 — قبول مستقل | مراجع لا يشارك في كتابة الحزمة التي يراجعها | يراجع مصفوفة القبول أدناه ويحدّث الحالة؛ نجاح البناء أو الاختبارات وحده ليس قبولاً بصرياً |

إذا احتاجت شاشة رمزاً ناقصاً، يرسل مالكها طلباً إلى مالك L1 بدلاً من إضافته بالتوازي. وإذا انتهت L1، يحرر المالك ملفاتها في اللوحة قبل بدء L2. كل commit يخص حزمة واحدة ويُدرج بالمسارات الصريحة فقط.

قالب بريد استعادة كلمة المرور في `apps/backend/src/modules/auth/password-reset-email.ts` يستخدم ألواناً فاتحة صريحة، لكنه خارج ثيم واجهة التطبيق وخارج L1. إذا قرر المالك توحيد البريد مع «طاولة المونتاج»، يُفتح له نطاق لاحق مستقل يملك القالب واختباره؛ لا يضمه مالك L1 خفيةً ولا تبدأ عليه جلسة موازية.

## 4. مصفوفة القبول

لا يُكتب «الثيمان مكتملان» حتى تُراجع الشاشات المتأثرة في المصفوفة كلها:

| محور | المطلوب |
|---|---|
| الوضع | اختيار `light` و`dark` صراحةً، ثم `system` مع تفضيل نظام فاتح وداكن |
| الاتجاه | العربية RTL والإنجليزية LTR، بلا اختلاف وظيفي أو نص مفقود |
| الجوال | عروض 360 و390 و430px، بلا تمرير أفقي عرضي، ومع safe areas وأهداف لمس 44px |
| سطح المكتب | عرض واحد على الأقل عند 900px أو أكثر؛ مبدّل الثيم ينتقل هنا من درج الهاتف إلى الهيدر، فيُراجع الفرعان |
| حالات البيانات | loading وempty وerror، إضافة إلى الحالة الممتلئة، على كل سطح يتغير لونه أو تباينه |
| الوصول | تباين النصوص/الأفعال وفق WCAG AA، تركيز ظاهر، أسماء وصول، وReduced Motion |
| عدم الانحدار | لقطات مقارنة للداكن قبل/بعد، والمسارات والحالة وطلبات API نفسها في الوضعين |
| القبول البصري | الفاتح يطابق شخصية «طاولة المونتاج» والأبيض/الأزرق/الليموني؛ الداكن يحتفظ بشخصيته السوداء/النيلية الحالية |

قبول الفاتح وقبول الداكن نتيجتان منفصلتان. قد يكون الداكن مكتملًا والفاتح غير مكتمل، كما هي الحال عند خط الأساس.

## 5. قائمة المطور قبل لمس الواجهة

- اقرأ ADR-112 وهذه الوثيقة، ثم افحص `.claude/SESSIONS.md` وسجّل الملفات التي ستملكها.
- حدّد هل عملك مشترك، أم L0، أم L1، أم شاشة من L2؛ لا تجمع طبقتين في جلسة واحدة بلا تنسيق.
- إن كانت L1 مفتوحة، لا تبدأ معالجة لونية داخل شاشة. وإن لم تكتمل L0، لا تخمّن الألوان.
- استخدم الشجرة والمكوّنات والمنطق الحالي؛ أي fork للفاتح يحتاج قراراً جديداً، لا اجتهاداً محلياً.
- سلّم لقطات ونتيجة كل خانة من مصفوفة القبول، ثم حدّث صف الحالة مرة واحدة.
