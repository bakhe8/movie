## 1. Source coverage and test ownership

The complete [AdminScreen](../apps/frontend/app/components/AdminScreen.tsx), [admin entry](../apps/frontend/app/admin/page.tsx), [admin client methods](../apps/frontend/app/lib/api.ts), [session readiness](../apps/frontend/app/lib/session.tsx), [AdminController](../apps/backend/src/modules/admin/admin.controller.ts), [AdminGuard](../apps/backend/src/modules/auth/admin.guard.ts) and relevant [catalog](../apps/backend/src/modules/admin/admin-catalog.service.ts), [models](../apps/backend/src/modules/admin/admin-models.service.ts), [operations](../apps/backend/src/modules/admin/admin-ops.service.ts) and [DTO](../apps/backend/src/modules/admin/dto/admin.dto.ts) implementations were reviewed at the baseline. The controller has 23 operations: 16 reads and 7 writes; the screen uses six read methods and one write method. No dedicated AdminScreen frontend test exists at this baseline.

In the matrices, **F1** owns W1 contracts/access/request correctness, **F2** owns W2 shell/migration and frontend preservation tests, **M3** owns later monitoring reads, and **S4** owns later write safety and administration. These are sequential ownership slots, not active sessions or permission to start. The coordinator assigns one named session to each slot before editing; the implementer owns its tests. W0 defines the cases; passing source review does not pass those future tests.

Existing partial evidence to extend: [admin API e2e](../apps/backend/test/admin.e2e-spec.ts) covers role denial, catalog summaries, review supersession, model registration/activation and account protections; [AdminGuard tests](../apps/backend/src/modules/auth/admin.guard.spec.ts) cover the current role gate; [model service tests](../apps/backend/src/modules/admin/admin-models.service.spec.ts) cover readiness and training-summary delegation. These do not prove frontend parity, all filters, capability enforcement, concurrent activation or visual acceptance, and were not rerun in W0.

## 5. Merge order, compatibility and stop gates

The governing order is **CAT-1 accepted/merged → W0 accepted → W1 PASS → remaining first package/W2 PASS → W3 → W4 → W5 → W6 → W7 → W8**. W3 and W4 are serialized conservatively here; the coordinator may later split disjoint files after contract freeze. **W5 precedes W6**, tightening the sibling branches in plan §19. No later slot opens merely because its document exists.

| Gate | Concrete evidence required before proceeding | Stop / next decision |
|---|---|---|
| W0 close → consider opening W1 | Unique ADR headings and complete summary through 117; unchanged ADR-116; every §2/§3 function has destination, test and owner; internal links resolve; `git diff --check`; exactly three owned files in one local commit and clean Git | Coordinator reads the delivery, reconciles the live ledger and accepts W0 before assigning W1; no code/tests claimed delivered by W0 |
