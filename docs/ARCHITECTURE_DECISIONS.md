## ADR-1 — Monorepo with npm workspaces

**Context.** Next.js frontend, NestJS backend, Python model service and shared types.
**Decision.** One repository: `apps/frontend`, `apps/backend`, `services/workers`, `packages/shared`; npm workspaces; Poetry for Python.
**Rationale.** One place for contracts and docs; refactors land everywhere; matches `BP §12` "start simple".
**Consequences.** Frontend and backend release together; the backend keeps a hand-synced copy of the fingerprint type because there is no project-reference build yet (see [FINGERPRINT_SCHEMA.md](FINGERPRINT_SCHEMA.md) §2).
**Revisit when.** `BP §12.3` team/deploy-boundary signals appear.

## ADR-2 — PostgreSQL as the single store: relational + FTS + pgvector

**Context.** Need transactional event storage, alternate-title search and vector candidate retrieval (`BP §12.1`).
**Decision.** One PostgreSQL; full-text search over `localized_titles`; `pgvector` columns for embeddings; no separate search or vector service.
**Rationale.** One backup/compliance surface; joins between events, titles and models; adequate for the MVP catalog size.
**Consequences.** The `ankane/pgvector` image is already used, but embeddings are stored as `real[]` and no FTS index exists — migration M3/M7 in [SCHEMA.md](SCHEMA.md).
**Revisit when.** Search or similarity exceeds measured Postgres capacity (`BP §12.3`).

## ADR-3 — Plackett–Luce linear utility as the core ranker

**Context.** Learn interpretable taste from few listwise rankings (`BP §7.1`–`§7.2`).
**Decision.** Utility $s(u,m)=b(m)+\theta_u^\top\phi_m+p_u^\top q_m+\delta_{u,m}$; listwise PL likelihood; MLE/MAP with regularization; $b(m)$ in the code path from day one; $p^\top q$ from internal data only when enough exists; $\delta$ strongly shrunk.
**Rationale.** Interpretable weights → honest explanations; sample-efficient; fast; a well-studied model with fair baselines (`BP §16.3`).
**Consequences.** Non-linear interactions are not captured in MVP; person and cultural effects are separate shrunk blocks, not dense features.
**Revisit when.** A candidate model beats it on the `BP §16.5` gate.

## ADR-4 — The triad ranking is the only explicit preference question

**Context.** `BP §2.4 #2`, `§4.3`.
**Decision.** No star, 1–10, thumbs or like/dislike input anywhere, permanently. "Haven't watched" and "don't remember" are neutral replacement controls. Imported ratings are auxiliary, low-confidence, never solicited.
**Rationale.** Rankings avoid scale ambiguity; a single fixed question keeps the meaning of the answer stable; the blueprint makes this non-negotiable.
**Consequences.** The claim "a triad teaches more per minute than a pair or a single rating" is `BP` Gate 1 — an **experiment**, not an assumption; a triad is never treated as three independent pairwise observations (`BP §7.2`). Post-watch (2026-09-03, [UI_MOCKUP_REVIEW_2026-09-03.md](UI_MOCKUP_REVIEW_2026-09-03.md) §5.2): the surface after a watch takes only watch facts (`watch-events`) and outcomes (`outcomes`) as typed in [API.md](API.md); it never asks how the film compared with expectation, better or worse than expected, or any two-point liking question — those are ratings without stars. The loop closes as `BP §4.5` says: the watched title re-enters a later triad.
**Revisit when.** Never for the question itself; only UX mechanics (ties, partial order) via `BP App. C`.

## ADR-5 — PWA first; native apps only on evidence

**Context.** `BP §5.1`–`§5.2`.
**Decision.** Next.js PWA (installable, offline shell) for web and mobile. Native iOS/Android are built only if the PWA measurably fails a performance or push-notification need.
**Consequences.** The current frontend is a plain Next.js app without manifest or service worker — PWA work is a listed gap.
**Revisit when.** PWA telemetry proves the need.

## ADR-6 — LLM enrichment through OpenAI Responses API with Structured Outputs

**Context.** `BP §15`.
**Decision.** Background-only use: fingerprint extraction and post-hoc explanation rephrasing via the Responses API with JSON-Schema structured outputs; `store=false`; model id from configuration (`OPENAI_FINGERPRINT_MODEL`, `OPENAI_EXPLANATION_MODEL`); batch endpoints where available for bulk seeding; versioned re-extraction only on schema/model change.
**Rationale.** Structured output prevents invented dimensions; multilingual; one-time cost per title-version.
**Consequences.** No model name or price appears in docs (they change); the worker's Chat Completions call and its hard-coded default model are gaps. Costs are tracked per film and per 1,000 explanations against a phase budget (`BP §15.4`), not estimated here.
**Revisit when.** Cost or vendor risk justifies a distilled local extractor.
**Superseded in part by ADR-63** (2026-09-03): provider is Anthropic, not OpenAI; `store=false` no longer applies (no such flag exists on this provider); batching is application-level, not a provider batch endpoint. The background-only, structured-output, versioned-model design is unchanged.

## ADR-7 — Individual profiles with a pseudonymous taste id

**Context.** `BP §2.4 #10`, `§13.1`, `§21.1`.
**Decision.** One person = one profile; `profiles.id` is the pseudonymous taste id; every event/model table references `profileId`, never `userId`. Group matching later merges rankings, never profiles.
**Consequences.** Exports and model jobs never touch account identity.

## ADR-8 — Three deterministic tracks with a declared exploration share

**Context.** `BP §4.4`, `§8.3`, `§14.1`.
**Decision.** Recommendations are split into `safe` / `discovery` / `outside_usual`; each track is deterministically ordered; exploration is a small, declared, logged share; every shown item logs `selectionPropensity`.
**Rationale.** Measurable, explainable, prevents the filter bubble without a full bandit.
**Revisit when.** Off-policy evaluation shows a bandit policy beats it on the `BP §16.5` gate.

## ADR-9 — Centralized training with explicit purpose consents

**Context.** `BP §21.1`, `§7.5`.
**Decision.** Models are trained server-side on pseudonymous events under purpose-specific consents. Pooled cross-profile training for the shared latent space is a **separate consent purpose** with an opt-out that does not remove individual personalization ([PRIVACY.md](PRIVACY.md)).
**Consequences.** Export, delete, reset and audit are product features, not afterthoughts.
**Revisit when.** Privacy requirements justify differential privacy or federated approaches.

## ADR-10 — Recommendations computed per request from precomputed model state, then persisted

**Context.** `BP §12.2`, `§13.1`, `§14.1`.
**Decision.** No LLM or training on the request path. Scores come from the latest snapshot via the model service; every served list is persisted (`recommendations` rows) so outcomes can close the loop. A Redis cache is added only if latency measurements require it.
**Consequences.** Redis is currently idle by design. Today's on-the-fly, unpersisted list is a gap.

## ADR-13 — Shared latent space with per-profile calibration

**Context.** Estimating tens of correlated weights per profile from a handful of triads is an identifiability problem (`BP §7.5`).
**Decision.** Build one population factor space (~15–30 factors) from all profiles' triads and fingerprints, retrained on a schedule inside the model service; calibrate each profile onto it (MIRT/CAT-style); seed it before launch **only** from data licensed for commercial use — otherwise from Alpha-cohort data; gate any disclosed cross-user claim behind `BP §7.6` and the cohort gate in `BP §17.3`.
**Consequences.** MovieLens/Tag Genome are blocked without written GroupLens permission ([DATA_LICENSING.md](DATA_LICENSING.md)); pooled training needs its own consent purpose; feedback-loop controls apply to the retraining data (`BP §21.2`).
**Partially superseded by ADR-72** (2026-09-04): "seed only from commercially-licensed data before launch" becomes "an external seed is optional during the free period; the permission question is an input to the post-launch revenue-model study" — no external seed is blocked, none is currently planned either.

## ADR-17 — Replacement semantics ("haven't watched" / "don't remember")

**Context.** `BP §4.3`, `§13.1`, `§14`; the two controls must be neutral and distinct.
**Decision.**
- `POST /triads/:id/replace { titleId, reason }` writes a `triad_replacements` row and swaps only that item; the triad gets a fresh `displayOrder`.
- `reason = not_watched` → `user_title_states.state` becomes `not_watched` (exposure unknown): the title stays a recommendation candidate and leaves the triad pool.
- `reason = not_remembered` → the title stays `watched` (it is not recommendable) and `triadEligible` becomes `false`.
- Neither reason enters any loss, prior or score. A triad exceeding `maxReplacementsPerTriad` (a policy parameter set before the Phase 0 test) is marked `skipped`. Replacement rate is a Phase 0/Alpha metric (`BP §17.1`, `§21.2`).
**Consequences.** Implemented 2026-09-03 (migration `AddTriadReplacements`, `TriadsService.replace()`, the two buttons on the triad screen). Observed on the first browser pass: because `displayOrder` is redrawn, a replacement reshuffles all three cards under a user who had already started ranking — correct for the position-bias log, costly for the user. Recorded as a `BP App. C` question ("display order after a replacement", blueprint v1.2) rather than changed here.
**Revisit when.** The `BP App. C` tie/weak-memory experiment reports, or its "display order after a replacement" question decides for keeping the in-progress order.

## ADR-20 — Internal blend vs displayed separation

**Context.** `BP §10.3` allows an internal rerank blend of Public Quality and Personal Fit; `BP §4.4` forbids showing a merged number.
**Decision.** The rerank score $\lambda_u\cdot PQ+(1-\lambda_u)\cdot PF+\text{ContextFit}+\text{Exploration}$ decides what is shown; the API and UI expose only the four separate values plus a reason that names the dominant component ("widely praised; we don't know your taste yet" vs "fits your taste specifically"). $\lambda_u$ decays with reliable evidence.

## ADR-27 — Password hashing library: `bcryptjs`, not `bcrypt`

**Context.** `bcrypt` compiles a native module via `node-pre-gyp`, which pulls in `tar`; a 2026-09-03 dependency audit found this chain carried a critical path-traversal advisory (`tar <=7.5.20`, e.g. GHSA-34x7-hfp2-rc4v) with no fix available inside `bcrypt`'s current major version.
**Decision.** Use `bcryptjs` — a pure-JavaScript implementation of the same bcrypt algorithm, with the same `hash`/`compare` API — instead of `bcrypt`. No native compile step, so no `node-pre-gyp`/`tar` dependency chain at all.
**Rationale.** Removes a critical, unpatchable-without-a-major-bump vulnerability from the production dependency tree at zero API cost; this app's request volume does not need native `bcrypt`'s raw hashing throughput.
**Consequences.** Hashing/comparison is measurably slower per call than the native binding (acceptable at this scale, verified by the e2e auth suite over real HTTP); ADR-26's "bcrypt passwords" still holds exactly — same algorithm, same cost factor, different implementation.
**Revisit when.** Login-endpoint throughput becomes measurably bottlenecked by hash cost.

## ADR-28 — At most one active triad per profile, enforced by a DB constraint

**Context.** `TriadsService.getCurrent()` checks for an existing active triad and creates one when there is none; without a database-level constraint, two concurrent requests for the same profile can both pass that check and both insert an active row. Found by a 2026-09-03 code audit — the blueprint assumes one open ranking round per profile (`BP §4.3`) without specifying how to enforce it under concurrency.
**Decision.** A Postgres partial unique index, `IDX_triads_one_active_per_profile` on `triads(profileId) WHERE status = 'active'`, makes the invariant a database guarantee instead of an application-level assumption. `TriadsService.getCurrent()` catches the resulting unique-violation on the losing request and returns the winning row instead of erroring or silently creating a duplicate.
**Rationale.** A check-then-insert pattern in application code cannot be made race-free without either a DB constraint or an explicit lock; a partial unique index is the standard Postgres tool for "at most one row matching a condition" and costs nothing on the read path.
**Consequences.** Any future change to the triad lifecycle must keep `'active'` meaning "the one open round for this profile" — a second concurrently-valid "in progress" status would need its own partial index or a rethink of this constraint.
**Revisit when.** The triad lifecycle grows a second concurrently-valid in-progress status (e.g. simultaneous ranking modes).

## ADR-29 — NestJS 10 → 11, not 12

**Context.** `@nestjs/core <=11.1.17` carries CVE-2026-35515 (GHSA-36xv-jgw5-4q75, moderate: unsanitized newlines in Server-Sent Events `type`/`id` fields inside `SseStream._transform()` — this app has no SSE routes at all, so it was never actually reachable, but `npm audit` offered no non-major fix). `npm audit`'s suggested fix target was `@nestjs/core@12.0.1`, but the advisory's real patched version is `11.1.18`. Checking peer dependencies directly on npm: `@nestjs/throttler` (guards `/auth/login` and `/auth/register` against brute-force, `ARCHITECTURE_DECISIONS.md` ADR-26) has no published version whose `peerDependencies` include `@nestjs/common@^12.0.0` — its latest, `6.5.0`, only declares support up to `^11.0.0`.
**Decision.** Upgrade the `@nestjs/*` family to the 11.2.x line — `@nestjs/common`/`core`/`platform-express`/`testing` at `^11.2.3`; `@nestjs/config` `^12.0.0`, `@nestjs/passport` `^12.0.0`, `@nestjs/typeorm` `^12.0.1` (all three declare peer support for `@nestjs/common@^11.0.0`, so using their latest majors alongside Nest 11 is still inside their supported range); `@nestjs/throttler` unchanged at `^6.5.0` — instead of jumping to the 12.x line. `@nestjs/platform-express@11.x` already pulls Express 5 (the breaking change happens at 11, not 12), so targeting v11 costs the same migration effort as v12 while staying inside every dependency's officially-declared peer range.
**Rationale.** Same CVE fix, same Express-5 migration cost, zero unverified peer-dependency combinations — particularly for the rate limiter, which is a security control guarding the login endpoint, not a cosmetic dependency.
**Consequences.** `apps/backend/package.json` now declares `engines.node >= 20.19.0` (the strictest floor in the tree, from `@nestjs/typeorm@12.0.1`). A dedicated e2e test, `test/throttling.e2e-spec.ts`, proves the 6th `/auth/login` attempt within a minute still returns `429` under the new `@nestjs/throttler`/Nest-11 combination — verifying the exact compatibility question this decision turned on, not just that the app boots. `npm audit --omit=dev`: 3 moderate → 0.
**Revisit when.** `@nestjs/throttler` publishes a release whose `peerDependencies` include `@nestjs/common@^12.0.0`, or another dependency forces a 12.x requirement anyway.

## ADR-30 — Dev-tooling security bump: `@typescript-eslint` and `vitest`, minimal patched line

**Context.** Two backend devDependency chains carried `npm audit` findings unrelated to NestJS: `@typescript-eslint/eslint-plugin`/`parser@^6.19.0` pulled a `minimatch` ReDoS chain (high, reachable only by a developer linting their own machine — no attacker-controlled input); `vitest@^1.1.0` (resolved `1.6.1`) was vulnerable to CVE-2026-47429 (critical, GHSA-5xrq-8626-4rwp: arbitrary file read/RCE via the Vitest UI server, but only when `vitest --ui`/browser mode is run or `api.host` is exposed to the network — this repo's `test`/`test:cov`/`test:e2e` scripts only ever call plain `vitest run`, which starts no server, so it was never reachable as configured, though a developer running `--ui` manually to debug on Windows — this project's own dev platform — would trip it).
**Decision.** `@typescript-eslint/eslint-plugin`/`parser` bumped to `^8.69.0` (peer-compatible with the existing `eslint@8.57.1` and `typescript@5.9.3` — confirmed no ESLint flat-config migration is required). `vitest` bumped to `^3.2.7`, not `npm audit`'s suggested `4.1.11`: the advisory's earliest patched line is `3.2.6`, and jumping only to 3.x avoids an unforced second major bump (Vite 6→7/8, `@types/node` floor, Node engine floor) for no additional security benefit.
**Rationale.** Same reasoning as ADR-29 (bcryptjs, ADR-27) — take the smallest version step that actually closes the advisory, verified against this repository's specific dependency/config surface rather than assumed from the tool's own suggested "safe" target.
**Consequences.** `vitest.config.ts`/`vitest.e2e.config.ts` needed no changes (both only use the small, version-stable `defineConfig`/`plugins`/`test.include` surface). Full backend suite (unit + e2e) and lint re-verified green under the new versions. `npm audit`, full (including dev): 10 → 0.
**Revisit when.** A future `test:cov`/`--ui` workflow is actually adopted — worth re-confirming the vitest version in use still isn't in CVE-2026-47429's affected range before turning on any network-exposed vitest server.

## ADR-31 — Temporal hold-out in training (gap 2); `createdAt` stands in for `answeredAt`

**Context.** `training.py` fit on every completed triad and reported `pairwiseAccuracy` on that same set — an in-sample number, not a validation metric (`BP §8.3`, `§16.1`, `§17.2`; RANKING_ALGORITHM.md §6). Implementing §6's real protocol exactly needs `triads.answeredAt` for temporal ordering and `triads.holdout` for policy-reserved rows — neither column exists yet (gap 3, `IMPLEMENTATION_STATUS.md`).
**Decision.** Order completed triads by `createdAt` instead: with the one-active-triad-per-profile constraint (ADR-28), a profile's triads are created and completed in strict sequence, so creation order already equals answer order today — an accurate stand-in until gap 3 adds the real column, not an approximation of something else. `train_and_evaluate()` (services/workers/src/training.py) holds out the most recent `max(1, n // 5)` triads when `n ≥ 5` (§6 step 2, `floor(0.2n)` computed exactly via integer division since 0.2 = 1/5); below that, no held-out metrics are computed or persisted (`NULL`, not a metric over 0–1 triads). Two separate `PlackettLuceRanker` instances are used — one fit on the training slice only (for the held-out metrics), a fresh second one fit on all `complete_triads` for the actually-served weights (§6 step 6) — because `fit()` only zero-initializes when `self.weights is None`, so reusing one instance across two fits would silently break ADR-22's determinism guarantee for the second fit. `compute_nll()` (new, `ranker.py`) reports mean NLL per held-out triad, without the L2 term (that shapes the optimization objective, not the predictive fit being reported).
**Consequences.** Migration `AddHeldOutTrainingMetrics` adds `heldOutTriadCount`/`heldOutNll`/`heldOutPairwiseAccuracy` to `user_model_snapshots` (nullable; `pairwiseAccuracy` is kept, unchanged, as the in-sample number). Running this end-to-end against a real database — for the first time in this codebase's history, since no test exercises `train_profile()` itself, only the pure `fingerprint_vector()` — surfaced two independent, previously-undiscovered bugs that made `train-profile` fail on every real invocation: (1) psycopg2 has no default typecaster for a `uuid[]` column and returned it as raw Postgres text, silently iterated character-by-character wherever the code expected a list (fixed with `psycopg2.extras.register_uuid()`, with every id re-cast to `str` immediately after fetching so the rest of the module's `str`-keyed logic is unaffected); (2) `compute_nll()`'s return value stayed a numpy `float64`, which psycopg2 cannot adapt as a query parameter (fixed by casting to a native Python `float`). Both would have blocked *any* use of `train-profile` against a real database, hold-out or not.
**Revisit when.** ~~Gap 3 adds `triads.answeredAt`/`holdout`~~ — done same day (ADR-32): `train_profile()`'s query now orders by `COALESCE("answeredAt", "createdAt")`, real `answeredAt` for triads completed after that migration, the `createdAt` stand-in only for legacy rows with none recorded. Still open: exclude `holdout = true` rows once gap 3's `holdout` column and a policy that sets it exist (neither does yet).

## ADR-32 — Triad event completeness: `shownAt`/`answeredAt`/`modelVersion`, `Idempotency-Key`, ranking by title id (gap 3)

**Context.** `triads` had no `shownAt`/`answeredAt`/`modelVersion` columns (`BP §13.2`), `POST …/rank` had no idempotency key (`BP §14`, only a status guard), and `ranking` stored positions into `titleIds` rather than the title ids themselves, contrary to ADR-15's already-decided target.
**Decision.** Migration `AddTriadEventCompleteness` adds `shownAt`/`answeredAt`/`modelVersion`/`idempotencyKey` and converts `ranking` from `integer[]` to `uuid[]` with a data backfill (`titleIds[ranking[i]+1]` per row, Postgres arrays being 1-indexed). `shownAt` is set once, at triad creation; `answeredAt` once, at `rank()`; `modelVersion` stays `NULL` under `random-v1`, which selects no model — not a fabricated version string. `Idempotency-Key` is an optional request header (not a body field, matching the header-based convention `BP §14` implies): omitted, behavior is unchanged from before; if sent and a row with that key already exists for the *same* triad, that row's result is returned instead of erroring on "already submitted"; for a *different* triad, `409` (a real conflict — the client reused a key it must not have). `TriadsService.rank()` validates the submitted ranking is exactly the fetched triad's own three title ids (a check that needs the triad row, so it runs after the shape-only checks that don't).
**Rationale.** Header-based idempotency avoids polluting the ranking payload's schema and matches how most HTTP idempotency-key conventions work (e.g. Stripe); scoping the uniqueness/replay check to `(idempotencyKey)` globally rather than per-triad is what lets a concurrent duplicate retry be caught by the DB's own unique constraint (`23505`) and resolved the same way ADR-28 already resolved the analogous triad-creation race — return the winner's row, not an error.
**Consequences.** `packages/shared/src/types.ts`, `apps/frontend/app/lib/api.ts` and `docs/API.md`/`docs/SCHEMA.md` updated to match (`ranking: string[]`, not `number[]`). `RankScreen.tsx` mints a fresh `crypto.randomUUID()` per submit attempt and sends it as `Idempotency-Key`, so a network retry or double-click is safe. Verified over real HTTP against a real Postgres (new `test/triad-rank.e2e-spec.ts`: title-id ranking accepted, a foreign title id rejected, a retried request with the same key returns the same result) and manually in a browser (network tab showed the exact persisted row: real title UUIDs in `ranking`, `shownAt` < `answeredAt`, `modelVersion: null`, the generated `idempotencyKey`).
**Revisit when.** `holdout`/`correctsTriadId` (still-missing `triads` columns, same M1 plan step) are added — nothing here needs to change for that.

## ADR-33 — Prediction display: verbal confidence on every prediction surface; Personal Fit never a percentage

**Context.** `BP §7.2` states that a relative ranking gives no absolute "liked" anchor and that the product does not show «سيعجبك بنسبة 91%» until the number is calibrated on later watch outcomes; `BP §4.4` fixes what a recommendation shows ("سبب قوي، ثقة لفظية، وتوفر") and forbids merging the values into one percentage; `BP §9.3` defines the four visible confidence bands with their copy; `BP §2.4 #6`–`#7`. The 2026-09-03 mockup review ([UI_MOCKUP_REVIEW_2026-09-03.md](UI_MOCKUP_REVIEW_2026-09-03.md), §5.1) raised the question whether the `§7.2` sentence applies only to the triad screen. It does not: `§7.2` sits in the model chapter and constrains what the ranking's *output* may claim; the triad screen shows no prediction at all (SPECIFICATION §5.2: poster, title, year); and `§4.4` repeats the rule for the recommendation surface itself. What the blueprint leaves open is the display *format* of Personal Fit — the engineering choice recorded here.
**Decision.**
1. *Scope*: every surface that displays a prediction or an inference — recommendation cards, taste profile, work page, library ranking, post-watch and library banners, share cards. Not the triad screen, which displays none.
2. *Confidence* is always one of the four `BP §9.3` bands (`initial` / `likely` / `strong` / `inconclusive`, API `confidenceBand`), rendered as its copy in the UI language; never a number, a percentage, or a bar labelled with a number.
3. *Personal Fit* is displayed in a relative form only: a verbal level (high / medium / low), an ordinal position inside its track, or an unlabelled bar; never `NN%` and never a decimal that reads as a probability. [API.md](API.md) already types it `personalFit: number // ordinal score; never shown as a %`.
4. *Public Quality* and *Watchability* keep their native forms (a source-attributed score with its vote count; provider and market) in their own cells; no cell repeats a value shown elsewhere on the card, and nothing is merged (ADR-20).
5. Formatting goes through one shared helper per value (`formatConfidence`, `formatPersonalFit`) in the frontend so that a `%` cannot reach the screen by accident; the `§9.3` copy lives in the i18n dictionaries in both languages.
**Rationale.** The Plackett–Luce model learns "A above B above C"; its output is a relative utility, not a probability of liking. A percentage promises a calibration that does not exist before post-watch outcomes are collected ([RANKING_ALGORITHM.md](RANKING_ALGORITHM.md) §7: Brier, ECE), and after 3–5 seed triads the posterior is wide — "initial" is honest, "88%" is false precision. A broken numeric promise costs trust in the product, not only in the item.
**Consequences.** Recommendation, taste-profile and work-page components accept `confidenceBand` and a Personal Fit level, never raw scores. The mockup cells «ملاءمة 94%» and «ثقة التوقع 88%» are replaced by a level and a band. SPECIFICATION §5.2–§5.4 carry the UX contract. Implemented 2026-09-03 for the recommendations screen: `apps/frontend/app/lib/format.ts` (`formatConfidence`, `formatPersonalFit`, `formatNumber`) is the only path from a model value to the screen; `CONFIDENCE_BAND_COPY` and `TRACK_COPY` in `lib/copy.ts` carry the `§9.3`/`§4.4` copy in both languages; `RecommendationsScreen` (the home view) renders the four labelled cells and shows unknown as unknown.
**Revisit when.** The `BP App. C` "confidence display" experiment (SPECIFICATION §11 open-experiments table: verbal only vs calibrated % later) runs, after calibration against post-watch outcomes passes the `BP §16.5` gate with Brier/ECE reported per cohort. Until then the display is verbal.

## ADR-34 — Random policy excludes only the previous triad's titles, not every title ever ranked (H1)

**Context.** `TriadsService.getCurrent()` excluded every title that had ever appeared in *any* completed triad for the profile, so a title could enter at most one triad, ever: with W watched titles a profile got `floor(W/3)` triads for its entire lifetime (5 max on the 15-title seed catalog), the `likely`/`strong` confidence bands and the ≥5-triad hold-out (ADR-31) became unreachable in dev, and a user with exactly 3 watched titles who had just ranked them got "mark at least three films" back — a false message; they already had. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §2 H1), reproduced and confirmed independently before fixing.
**Decision.** `getCurrent()` now excludes only the immediately previous completed triad's three titles, not the full history. `BP §8.2`'s selection score treats repetition as a penalty term ("`-λr·Repeat`"), not a hard filter, and `BP §8.1` names "verification/refutation in an independent context" — a deliberate *re-test* of a past comparison — as one of six intended triad functions; a permanent ban contradicts both. `random-v1` has no scoring function to apply a soft, graduated penalty through, so "not the triad that was just completed" is its policy-appropriate stand-in until the adaptive policy (`BP §8.1`–`§8.2`, still gap territory) exists to compute a real `Repeat` term. The "fewer than 3 watched" and "3+ watched but the pool is temporarily empty because they were all just used" cases now get distinct messages instead of one misleading one.
**Consequences.** A title can be reused after just one intervening triad. `random-v1`'s other `BP §8.3` gaps (session limit/fatigue, reserved hold-out, director/language guard) are unchanged and still open.
**Revisit when.** The adaptive policy lands and can express repetition as a real scored penalty instead of a fixed one-triad lookback.

## ADR-35 — `AuthService.validateUser()` checks `active` (H2)

**Context.** `login()` already rejected a deactivated account (`§21.3` account takeover controls), but `validateUser()` — what `JwtStrategy` actually runs on *every other* guarded request — did not check `active` at all. A deactivated account's still-unexpired JWT kept full API access for the rest of its 7-day lifetime; only re-authenticating was blocked. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §2 H2), reproduced and confirmed independently before fixing.
**Decision.** `validateUser()` now returns `null` when `!user.active`, exactly as it already does for "no such user" — Passport treats a `null` return from a JWT strategy's `validate()` as authentication failure (`401`), so this reuses a mechanism that already existed rather than adding a new one.
**Consequences.** No behavior change for active accounts. A newly deactivated account is locked out of every guarded route on its very next request, not just at its next login.
**Revisit when.** ADR-26's refresh-token work lands — re-verify the refresh path also re-checks `active` and doesn't reintroduce this gap through a second code path.

## ADR-36 — `services/workers`: the OpenAI client is built lazily, not at import time (H3)

**Context.** `src/enrichment.py` built `openai.OpenAI(...)` at module import time, and `src/__init__.py` imported `enrichment` unconditionally — so importing the `src` package at all (including `python -m src.training`, which has no dependency on OpenAI) raised `openai.OpenAIError` on any machine without `OPENAI_API_KEY` set. [QUICKSTART.md](QUICKSTART.md) §Prerequisites already (correctly) documents that the core loop needs no OpenAI key; this bug just made that untrue in practice. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §2 H3), reproduced independently before fixing (`env -u OPENAI_API_KEY python -m src.training --help` raised before the fix, exits 0 after).
**Decision.** Two changes, both from the audit's suggested fix: (1) `src/__init__.py` no longer imports `enrichment` — callers reach it directly via `from src.enrichment import ...`, same as the existing test file already did; (2) `FilmEnrichmentWorker` builds its OpenAI client lazily, cached on first use in a private `_get_client()`, instead of module scope. A key is now only ever required at the point a call to OpenAI is actually about to happen.
**Consequences.** `import src`, `import src.training`, and `import src.enrichment` all succeed with no `OPENAI_API_KEY` set; so does constructing a `FilmEnrichmentWorker()`. The key is still required — unchanged — to actually call `generate_fingerprint()` / `generate_recommendation_explanation()`. No behavior change for the enrichment worker's real callers, which always have the key set before running it.
**Revisit when.** Never, barring a redesign of how workers share OpenAI clients across multiple worker instances (not needed today — one process runs one worker at a time).
**Superseded in part by ADR-63** (2026-09-03): the client is Anthropic's, resolving `ANTHROPIC_API_KEY` instead — but the lazy-construction fix itself is preserved exactly as designed here, unchanged by the provider switch.

## ADR-37 — `ParseUUIDPipe` on every UUID path param (H4)

**Context.** No controller validated that a UUID-shaped path param (`profileId`, `titleId`) was actually a UUID before handing it to TypeORM. Postgres rejected the cast with a raw SQL error, which Nest's default exception filter turned into an unhandled `500 {"statusCode":500,"message":"Internal server error"}` — the wrong contract (should be `400`) and a cheap noise generator for error monitoring. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §2 H4), reproduced independently before fixing (`GET /api/titles/not-a-uuid` and `GET /api/profiles/not-a-uuid` both returned `500`).
**Decision.** `@Param('id', ParseUUIDPipe)` on every UUID path param in `ProfilesController`, `UserTitleStateController`, `TitlesController`, `RecommendationsController` and (closed 2026-09-03, see below) `TriadsController` — a malformed id now fails validation before it ever reaches a service or the database, and Nest's `ParseUUIDPipe` throws `BadRequestException` (`400`) by default. Per-param, not a global pipe: explicit at each call site, and safe against a future route that legitimately takes a non-UUID param.
**Consequences.** `GET /titles/not-a-uuid`, `GET /profiles/not-a-uuid`, `PATCH /profiles/:id/titles/not-a-uuid/state`, `GET /profiles/not-a-uuid/recommendations`, `GET /profiles/not-a-uuid/triads(/current)`, `POST /triads/not-a-uuid/rank` and `POST /triads/not-a-uuid/replace` now all return `400` instead of `500`. No behavior change for well-formed ids (valid-but-nonexistent or valid-but-wrong-owner ids still resolve through the service layer to `404`, unchanged — verified against the existing IDOR e2e suite).
**Closed 2026-09-03.** `TriadsController`'s `:triadId`/`:profileId` params were originally left out — another session was concurrently editing that exact file (the triad-replacement feature) while this fix was first made. Closed once that work landed (`ADR-17`): reproduced live first (all four routes still `500`ing on a malformed id), then the same `ParseUUIDPipe` treatment applied, with 4 new e2e tests (33 e2e total) and a live before/after check against a temporary instance.
**Revisit when.** Never, barring a new route with a non-UUID path param that needs a different pipe.

## ADR-38 — `docker compose` invocations pin `--project-directory .` (H5)

**Context.** Every compose invocation (`npm run docker:up`/`docker:down` at the repo root, `test:e2e:up` in `apps/backend`, `docker-logs` in the `Makefile`) passed only `-f docker/docker-compose.yml`. Compose derives the *project directory* — where it looks for a `.env` to interpolate `${VAR}` references — from the directory of the first `-f` file when `--project-directory` isn't given, i.e. `docker/`, which has no `.env`. Only the repo root does (`POSTGRES_PASSWORD=dev_password_change_in_production`), so `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-postgres}` in `docker-compose.yml` silently fell back to `postgres` on `postgres`'s *first* `initdb` (a fresh clone) — a password the backend's own `.env` never uses, so `npm run docker:up && npm run db:migrate` fails authentication on a clean checkout. The `postgres-test` service is unaffected (its credentials are hard-coded, not interpolated). Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §2 H5), reproduced independently before fixing: `docker compose -f docker/docker-compose.yml config` resolved `POSTGRES_PASSWORD: postgres`; adding `--project-directory .` resolved the correct `dev_password_change_in_production` from the root `.env`.
**Decision.** Add `--project-directory <path-to-repo-root>` to every compose invocation: `.` where the script's cwd is already the repo root (root `package.json`, `Makefile`), `../..` where it's `apps/backend`. Chosen over moving `docker-compose.yml` to the repo root (the audit's alternative) to avoid touching an unrelated, working file layout for what is purely an invocation-flag fix.
**Consequences.** A fresh clone's first `docker:up` now initializes Postgres with the password the rest of the stack (backend, seed, CLI, trainer `.env`) actually expects, closing the authentication-failure trap. No effect on this development machine's already-running `movie-postgres` container — its data volume was already initialized (evidently under different, working conditions; see the audit) and Postgres passwords are fixed at `initdb` time, not re-read from `POSTGRES_PASSWORD` on every restart — so this fix was deliberately *not* forced onto the live container (no `docker compose up` was run for real; verified via `config` only) to avoid disrupting a concurrently-running session's database connections. Documented as a `QUICKSTART.md` §9 troubleshooting row with the manual recovery path (`down -v` + re-run) for anyone who already has a volume initialized under the old, broken behavior.
**Revisit when.** Never, barring a repo-layout change that moves `docker-compose.yml` (at which point re-derive the relative `--project-directory` paths, or drop the flag if the file moves to the root).

## ADR-39 — Catalog reads require auth; fingerprint/externalIds never leave the DB (M2)

**Context.** `TitlesController` (`GET /titles`, `GET /titles/search`, `GET /titles/:id`) had no guard, and `TitlesService` returned the raw `Title` entity — the full 13-dimension fingerprint plus provenance, and third-party `externalIds` (IMDb/TMDb/Wikidata) — to anyone, with only the global 60 req/min throttle in the way. `BP §21.3` lists API scraping with quotas as a threat model; `BP §5.3` says the work page shows only a *reviewed summary* of the fingerprint, never the raw dimensions; [DATA_LICENSING.md](DATA_LICENSING.md) treats the derived fingerprint as a licensed asset, not something to hand out for free. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M2), reproduced independently before fixing: an unauthenticated `curl` against the live dev server's `/api/titles` returned the full fingerprint and `externalIds` for every item.
**Decision.** Two changes. (1) `@UseGuards(AuthGuard('jwt'))` on `TitlesController` — the only client is this app, and every screen that reads titles already holds a token by the time it renders (behind `SessionProvider`), so this has no effect on the frontend. (2) `TitlesService.findAll()`/`findOne()` now `select` only the public columns (`id`, `internalId`, `titleEn`, `titleAr`, `description`, `releaseYear`, `genres`, `createdAt`, `updatedAt`) — `fingerprint` and `externalIds` are never fetched from Postgres at all, not merely stripped from the response afterward. A `PublicTitle = Omit<Title, 'fingerprint' | 'externalIds'>` type makes the guarantee visible at the type level. The frontend's own `Title` type (`api.ts`) already excluded both fields, so it needed no change.
**Consequences.** `GET /titles*` now `401`s without a token. An authenticated response never carries `fingerprint`/`externalIds`, proven by a real end-to-end round trip (e2e), not just a unit-level projection check. A reviewed fingerprint *summary* on the work page (`BP §5.3`) remains a separate, not-yet-built feature — this fix only closes the leak of the raw dimensions, it doesn't add the summary.
**Revisit when.** The work page's reviewed-summary feature is built — it will need its own, deliberately narrower field, not a relaxation of this guard.

## ADR-40 — `AuthService.register()` catches the concurrent-duplicate race (M3)

**Context.** `register()` did `findOne(email)` then `save(user)` with no guard between them — two concurrent registrations for the same email could both pass the `findOne` check before either saved, so the loser hit the raw `users.email` unique-constraint violation (`23505`) as an unhandled `500`, not the `409 Conflict` a duplicate email should produce (which the sequential case already got, via the `findOne` check). `ProfilesService` already catches `23505` the same way for its own unique constraint (`userId, name`) — `AuthService` was simply missing the equivalent. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M3), reproduced independently before fixing: two genuinely concurrent `POST /auth/register` requests for the same email, fired in parallel against the live dev server, came back `201` + a raw `500`.
**Decision.** Wrap `usersRepository.save(user)` in try/catch; on a `23505` unique-constraint error, throw `ConflictException('Email already registered')` — the same message and exception type the sequential `findOne` check already used, so callers see one consistent error regardless of which path caught the duplicate. Mirrors `ProfilesService.isUniqueConstraintError()` exactly (both now have their own private copy; not extracted to a shared helper for two call sites).
**Consequences.** A concurrent duplicate registration now reliably returns `409`, proven with a real two-in-flight-request e2e test (not simulated sequentially, which wouldn't exercise the race at all) plus a unit test that forces the `save()` rejection path directly. No behavior change for the non-concurrent case.
**Revisit when.** A third unique constraint needs the same treatment — worth extracting `isUniqueConstraintError` to a shared utility at that point, not before (rule of three).

## ADR-41 — Dev-stack ports bind to `127.0.0.1`, not all interfaces (M11)

**Context.** `docker-compose.yml` published Postgres (`5433`), Redis (`6379`) and `postgres-test` (`5544`) as `"<host>:<container>"` with no host IP, which Docker binds to `0.0.0.0` by default — reachable from any device on the same network as the developer's machine, not just `localhost`. None of these services have their own auth worth relying on for network-level exposure (Redis has none at all; Postgres's password is a dev-only placeholder). Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M11).
**Decision.** Bind all three port mappings to `127.0.0.1:<host>:<container>` explicitly.
**Consequences.** Verified via `docker compose config` (resolves `host_ip: 127.0.0.1` for all three) and, more directly, on the actual `postgres-test` container recreated during this fix's own e2e run (`docker inspect` shows `HostIp: 127.0.0.1` baked into its real port binding). No effect on this machine's already-running `movie-postgres`/`movie-redis` containers until they are next recreated — deliberately not forced now, to avoid disrupting a concurrently-running session's database connections (same caution as ADR-38/H5).
**Revisit when.** A deployment topology needs these services reachable from another host (should not happen for local dev images with placeholder credentials — reach for a real network/VPN boundary instead of reopening these binds).

## ADR-42 — `UserTitleStateService.upsert()` follows PATCH semantics (M1)

**Context.** `PATCH .../titles/:titleId/state` set `state.notes = dto.notes ?? null` unconditionally — a caller PATCHing only `state` (the common case: `DiscoverScreen`'s "mark watched" button) silently wiped any existing note, because `dto.notes` is `undefined` whenever the field is simply absent from the body, and `?? null` treats "absent" the same as "explicitly cleared". The same shape of bug applied to `watchedAt`: a caller-supplied value was stored even when the target `state` wasn't `'watched'`, so a date could end up attached to a `'watchlist'`/`'not_watched'`/`'interested'` row where it has no meaning. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M1), reproduced independently before fixing by reading the assignment logic directly (`state.notes = updateTitleStateDto.notes ?? null` unconditionally overwrote on every call).
**Decision.** `notes` is only written when `updateTitleStateDto.notes !== undefined` — omitted means "leave alone"; an explicit `notes: null` still clears it (the DTO's type is now `string | null` to say so honestly). `watchedAt` is only ever set when the target `state === 'watched'` (from the DTO if supplied, else kept or stamped `now()`); for any other state it's unconditionally `null` — not merely left alone, since a stale `watchedAt` next to a non-`'watched'` state is itself meaningless. This mirrors `TriadsService.replace()`'s `not_watched` path, which already nulls `watchedAt` the same way for the same reason, so the two write paths now agree.
**Consequences.** A "mark watched" PATCH that omits `notes` (the only call the frontend currently makes) no longer destroys a note written through some other path. A PATCH that supplies `watchedAt` alongside a non-`'watched'` state has that value silently dropped rather than stored nonsensically. Proven with a real HTTP round trip against real Postgres (`test/user-title-state.e2e-spec.ts`), not just a unit-level assertion, since the bug is specifically about what a PATCH does and doesn't touch on the actual persisted row.
**Revisit when.** A future import path needs different clear-vs-leave semantics for `importedRating`/`ratingSource` — those fields are untouched by this endpoint entirely (see the existing comment in `upsert()`), so this ADR doesn't cover them.

## ADR-43 — `SessionProvider` only logs out on a real `401` (M4)

**Context.** `SessionProvider`'s profile-resolution effect ran `ensureProfile().catch(() => { /* wipe the stored session */ })` unconditionally — a network error, a `500`, or a `429` from the throttle was indistinguishable from an actually-invalid token, so any transient failure silently signed the user out and dropped them back to `AuthScreen` with no explanation. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M4), confirmed by reading the `.catch()` block directly: it took no argument and branched on nothing, so every rejection reached the wipe.
**Decision.** The `.catch(err)` now only wipes the session when `err instanceof ApiError && err.status === 401` — the same `ApiError`/`status` pattern this file's own `login()`/`register()` catch blocks already use to distinguish server-reported failures from everything else. Any other rejection (network failure, `5xx`, `429`) leaves `auth`/`profile` untouched; `profile` stays `null`, which `page.tsx` already renders as "setting up your profile" rather than bouncing to the auth screen.
**Consequences.** A transient failure no longer destroys a valid session. It does not yet add a retry affordance beyond a manual reload (re-triggers the hydration effect, which re-triggers profile resolution) — a proper retry/error-banner UI is M5's broader scope, not duplicated here. **Verification note:** this fix could not be exercised live in a browser — Next.js 16 refuses a second `next dev` instance against the same `apps/frontend` directory, and a concurrent session's own dev server was actively running against it at the time; disrupting that session's live browser state (logging its active account out to trigger the effect) was judged worse than skipping the live check for a change this small and deterministic. Verified instead by direct code review (`tsc --noEmit` clean; the added condition mirrors the exact pattern already proven correct two functions above in the same file) — no automated frontend test suite exists in this codebase to substitute either.
**Revisit when.** A frontend test harness (Playwright/Testing Library) is introduced — this is exactly the kind of behavior that harness should cover, and the live-verification gap above should close then.

## ADR-44 — Tailwind removed; `globals.css` expanded to readable source (M6)

**Context.** `tailwindcss`/`@tailwindcss/postcss` were installed and imported (`@import "tailwindcss";` in `globals.css`, after other rules — invalid `@import` placement per the CSS spec, tolerated only because the PostCSS plugin doesn't enforce it), but zero components used a single Tailwind utility class (confirmed by grep across every `.tsx`) — dead weight in the bundle and the dependency tree, plus the built-in preflight reset silently applying under the hand-written CSS. `globals.css` was also minified into a handful of massive single-line rule blocks, with a `.rank-list`/`.rank-card` block — including `.rank-card img` poster-image rules — left over from before `RankScreen`'s ADR-17 rebuild moved to its own CSS module (`RankScreen.module.css`); nothing in the current codebase references `.rank-card`/`.rank-list` any more (confirmed by grep across every `.tsx`/`.module.css`). Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M6).

## ADR-48 — `trust proxy` set to one hop; the throttler tracks the forwarded client IP (M10)

**Context.** No `trust proxy` configuration existed anywhere, and the app-wide `ThrottlerGuard` used `@nestjs/throttler`'s default tracker. Behind any reverse proxy — every staging/prod topology these docs describe, even though the vendor itself is undecided (ADR-24) — Express's `req.ip` resolves to the proxy's own address for every request, not the real client's, so every user shares one 60 req/min bucket, and `AuthController`'s tighter 5/min brute-force limit on `/auth/login`/`/auth/register` becomes 5/min combined for everyone rather than 5/min each. Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M10), reproduced by inspecting `@nestjs/throttler`'s installed source directly: its default `getTracker(req)` is exactly `return req.ip`, which already respects Express's `trust proxy` setting once one exists — so, contrary to the audit's suggested fix, no custom `getTracker` is actually needed, only correct `trust proxy` configuration.
**Decision.** `app.set('trust proxy', Number(process.env.TRUST_PROXY_HOPS ?? 1))` in `main.ts`'s `bootstrap()`, requiring `NestFactory.create<NestExpressApplication>(AppModule)` instead of the untyped `NestExpressApplication`-less default (Express's `.set()` isn't on the platform-agnostic `INestApplication` interface). A hop *count* (`1`), not `true`: `true` trusts an arbitrary-length forwarded chain, which would let any client set its own `X-Forwarded-For` and dodge the limit outright — the opposite of the fix. `1` (a single reverse proxy directly in front of the app) is correct for every topology named in these docs; `TRUST_PROXY_HOPS` lets the real value be set once a hosting topology is actually chosen (ADR-24 still open), without another code change.
**Consequences.** `req.ip` — and therefore the throttler's bucket key — now reflects the outermost trusted hop of `X-Forwarded-For` instead of the proxy's own address. e2e tests build their own Nest app directly and never run `main.ts`'s `bootstrap()`, so `test/throttling.e2e-spec.ts` mirrors the same `app.set('trust proxy', 1)` call in its own setup; without it (verified by temporarily removing it and re-running), the new forwarded-IP test fails exactly as predicted (`[429,429,429,429,429]` instead of `[401,401,401,401,401]` — the second client's requests inherit the first client's already-exhausted bucket). Verified twice: the e2e test, and directly against `main.ts`'s real bootstrap on a temporary instance — two forwarded IPs, one exhausts its 5/min bucket (`429` on the 6th attempt), the other is untouched (`401`, not `429`).
**Revisit when.** ADR-24's hosting decision lands — set `TRUST_PROXY_HOPS` (or a specific trusted-IP list, if the chosen topology needs one) to match the real proxy chain depth instead of the single-hop default.

## ADR-50 — `generate_recommendation_explanation()` never receives user data (M12)

**Context.** The function took `user_preferences: Dict[str, float]` (the profile's learned model weights) and `similar_titles: list[str]` (previously-watched favorites) and put both into the OpenAI prompt — `dim_text` named the dimensions with the highest `user_preferences[dim] * fingerprint[dim]` contribution, and `similar_text` embedded the literal titles verbatim. This is exactly what ADR-23 already forbids ("prompts contain licensed evidence and schema only — never user ids, rankings, preferences or account data") and what `BP §15.2` rules out ("لا يستنتج سمات حساسة عن المستخدم من سجل المشاهدة" — must not infer sensitive user traits from watch history). Found by an independent audit ([AUDIT_2026-09-03.md](AUDIT_2026-09-03.md) §3 M12), confirmed by reading the prompt-building code directly. Not yet a live incident: the function is called only from its own test file (confirmed by grep), so no user data has actually reached OpenAI — but it was a landmine for whenever a recommendations feature wires it in.
**Decision.** `user_preferences` and `similar_titles` removed from the signature entirely, not merely left unused — a future caller cannot pass user data back in by mistake, only get a `TypeError`. The prompt is now built solely from the film's own fingerprint values (the 4 farthest from the neutral 0.5 midpoint — the most informative evidence about the film itself, independent of any viewer) and its themes, with instructions that explicitly tell the model not to mention any viewer, preference, or recommendation framing. What personalizes a recommendation — which dimensions actually drove the score, and in which direction — already exists as `RecommendationsService`'s own `RecommendationReason`, computed and rendered entirely on the backend/client and never sent to OpenAI or any third party; this function's role is narrowed to describing the film itself, for any viewer, exactly as `FINGERPRINT_SCHEMA.md` §7 already specifies ("Template explanations are the default; an LLM may rephrase a template from the evidence payload only, never invent evidence").
**Consequences.** The function can no longer leak user data even if wired into a live path carelessly — the parameters to do so don't exist. Verified with 2 new/rewritten unit tests (41 Python tests total): the old four-argument calling convention now raises `TypeError`; the actual `input` text sent to `responses.create` is asserted to contain only the film's title/evidence/themes and never contain the neutral (least-informative) dimension, with `instructions` asserted to explicitly mention "viewer" and "preference" as things *not* to reference. Not live-verified against the real OpenAI API — no real key is configured on this machine (`.env`'s `OPENAI_API_KEY` is a placeholder), and the function has no live caller to exercise end to end either way.
**Revisit when.** A recommendations feature actually wires this function in — re-verify then that whatever calls it still only ever supplies film evidence, never a `Profile`/`UserModelSnapshot`/watch-history object.

## ADR-59 — Confidence band now factors in held-out prediction success (blueprint gap 5, partial)

**Context.** `BP §9.2` lists five criteria for showing a confidence tendency: stable posterior direction, sufficient effective evidence, director/language/genre diversity, successful prediction of held-out comparisons, and fingerprint quality. `confidenceBand()` implemented only two: evidence quantity (raw `trainingTriadCount`, an explicit interim heuristic per ADR-21) and fingerprint quality (ADR-19's one-band demotion). `heldOutTriadCount`/`heldOutNll`/`heldOutPairwiseAccuracy` have existed on `UserModelSnapshot` since gap 2 (ADR-31, `training.py` computes real held-out metrics every run) but `confidenceBand()` never read them. The other two criteria — posterior stability and diversity — genuinely cannot be closed the same way: `posterior` is never populated (`PlackettLuceRanker.fit()` computes no per-weight uncertainty; that is real Bayesian/MAP estimation work in the Python trainer, not a wiring gap), and "diversity" has no defined metric anywhere in this repository (Shannon entropy over genres? a raw distinct-director count? no document says) — inventing one now would be fabricating a product decision the same way an unspecified embedding dimension would have been (ADR-57).
**Decision.** Close only the criterion that already has real data and a domain-standard threshold: when `heldOutPairwiseAccuracy` is known (non-null; it's null below the 5-triad floor per ADR-31, in which case behavior is unchanged) and at or below `0.5` — chance level for a binary pairwise comparison — the band is `'inconclusive'` outright, overriding the triad-count band rather than a single-step demotion. `0.5` is not an invented number: `BP §9.3` already defines `inconclusive` as "conflicting evidence," and a model that predicts held-out comparisons no better than a coin flip is exactly that. Posterior stability and diversity are left unimplemented and explicitly documented as still-open, not silently skipped.
**Consequences.** A profile whose model demonstrably fails to predict its own held-out comparisons can no longer show `'strong'`/`'likely'` confidence purely from triad count — this was previously possible and is a real correctness improvement, not cosmetic. `confidenceBand()` is still not the full `BP §9.3` system; two of five criteria remain open and each needs real work before Alpha reporting (Bayesian uncertainty estimation for posterior stability; a diversity metric definition — a product decision — for the third). Verified with 4 new unit tests (chance-level demotes regardless of triad count, below-chance demotes, meaningfully-above-chance keeps the triad-count band, unknown/null falls back unchanged) plus the full suites (104 unit, 42 e2e green); `tsc`/`eslint` clean. `rankLibrary()` shares the same `confidenceBand()` method, so this applies to the library ranking too, not just recommendations.
**Revisit when.** Either remaining `§9.2` criterion is tackled: posterior stability needs the Python trainer to compute and store per-weight uncertainty (a real ML task); diversity needs a metric definition decided with the user first, not invented here.

## ADR-62 — Confidence band closes on two more `§9.2` criteria: posterior stability and genre diversity (blueprint gap 5, remainder)

**Context.** ADR-59 wired held-out prediction success into `confidenceBand()`, leaving two of `BP §9.2`'s five criteria open: "stable posterior direction beyond a pre-set threshold" and "diversity of directors/languages/genres" (paired with "sufficient effective evidence (not one series repeated)"). Both had previously been deferred as needing either real ML work or an undecided metric — asked to complete the remainder. Investigation found real, grounded techniques for both rather than needing another invented threshold: `ranker.py`'s `fit()` already calls `scipy.optimize.minimize(..., method='BFGS')`, whose result carries a dense inverse-Hessian approximation as a side effect of the optimization already running; because the objective adds an L2 term, the optimum is a MAP estimate under an implicit Gaussian prior, so that inverse Hessian is the textbook Laplace approximation to the posterior covariance — not the true posterior, but a well-established approximation to it, already sitting unused in a value the code already computes. Separately, `Title.genres` is real, populated data (unlike director/language, which need the still-empty `people`/`credits` tables from gap 6) — genre diversity across a snapshot's training triads is a plain query over data that already exists.
**Decision.** `PlackettLuceRanker` gains `standard_errors()` (`sqrt(diag(hess_inv))`, one per fingerprint dimension). `training.py` gains `compute_genre_diversity()` (distinct-genre count across every title in the triads trained on, titles with no known genre contributing nothing either way) and threads a `genres: Dict[str, List[str]]` mapping (fetched alongside `fingerprint` in the existing titles query, TypeORM's simple-array format split on comma) into `train_and_evaluate`. Both new signals are computed only at/above the same 5-triad floor `heldOutTriadCount` already uses (ADR-31) — too little data for either to mean anything below it — and persisted on the snapshot: standard errors into `posterior` (`{ standardErrors: number[] }`, the shape that column was always documented for since M4, ADR-54, but never populated until now) and genre diversity into a new `trainingGenreDiversity integer` column (migration `AddTrainingGenreDiversity`) rather than folded into `posterior`'s JSON, since it's a well-defined single number matching `heldOutTriadCount`/`heldOutNll`'s own typed-column convention, not `posterior`'s variable-shaped concept. `confidenceBand()` overrides the band to `'inconclusive'` outright (not a one-step demotion, matching ADR-59's precedent) when no dimension's `|weight| / standardError` exceeds `1.0` — the most permissive defensible bar ("at least one standard error from zero," not a strict ~1.96 significance test, consistent with the function's own "deliberately conservative... a soft heuristic" posture) — or when `trainingGenreDiversity < 2`, the literal reading of BP §9.2's own phrase "one series repeated."
**Consequences.** `confidenceBand()` now covers four of `BP §9.2`'s five criteria; only director/language diversity remains open, correctly blocked on gap 6's still-empty catalog-provenance data rather than anything fixable here. Both new columns are `NULL` for every snapshot trained before this migration and for any profile with fewer than 5 training triads — existing behavior is unchanged in both cases (verified: the `it.each` triad-count band test and every pre-existing inline snapshot mock, none of which set the new fields, still pass unmodified). Verified with 6 new Python unit tests (`standard_errors()` raises before fit, returns one positive finite value per dimension, and a clearly-informative dimension shows `z > 1`; `compute_genre_diversity()`'s counting, repetition and missing-data cases) and 7 new TypeScript unit tests (both new checks' override/pass-through/unknown-falls-back-unchanged branches); the full Python suite (85 tests) and backend suites (118 unit, 45 e2e) green, `tsc`/`eslint`/`ruff` clean. Additionally verified against real Postgres beyond the automated suite: a disposable script seeded a real profile with 6 titles (3 "Thriller"/3 "Drama") and 6 completed triads directly into `postgres-test`, called `train_profile()` for real, and confirmed the `posterior`/`trainingGenreDiversity` columns round-tripped correctly (`{"standardErrors": [...13 values]}`, `trainingGenreDiversity: 2`) — not just that pure-Python unit tests with mocked objects pass, that the actual `json.dumps`/`%s::uuid[]` SQL path works end to end (the same category of bug ADR-31's gap-2 work found by insisting on this same kind of real-database check).
**Revisit when.** Director/language diversity data exists (blueprint gap 6's ingestion pass) — extend the same `< 2` pattern to a combined diversity check across all three axes BP §9.2 names, not just genre. **Partially done by ADR-64** (2026-09-03): language diversity closed the same day, the data having turned out to already exist in the demo catalog fixture; director stays blocked on gap 6 as described here.

## ADR-64 — Confidence band closes a third `§9.2` criterion: language diversity (blueprint gap 5/gap 6, partial)

**Context.** ADR-62's own "Revisit when" named the trigger: "director/language diversity data exists (blueprint gap 6's ingestion pass) — extend the same `< 2` pattern to a combined diversity check across all three axes." Both new columns are `NULL` for every snapshot/title that predates this migration; existing behavior is unchanged for them (verified: every pre-existing inline snapshot mock, none of which set `trainingLanguageDiversity`, still passes unmodified). No file owned by session C was touched — `fetch-catalog.ts`, `enrichment.py`/`enrich_catalog.py`, and the fixtures stay hers; this ADR only adds a column and reads it. Verified with 4 new Python unit tests (`compute_language_diversity()`'s counting, repetition, missing-data and zero-known-language cases) mirroring `TestComputeGenreDiversity` exactly, 2 new `train_and_evaluate` cases, and 4 new TypeScript unit tests (override/pass-through/unknown-falls-back-unchanged, mirroring the genre suite); the full Python suite (96 tests, after also fixing a stale local venv missing the `anthropic` package so the whole suite — not just `test_training.py` — could actually run) and backend suite (139 unit tests) green, `tsc`/`eslint`/`ruff` clean. **Revisit when.** Director diversity data exists (blueprint gap 6's people/credits ingestion pass, still blocked on either extending `fetch-catalog.ts` or a separate Wikidata P57 pass against loaded titles) — extend the same `< 2` pattern to the third axis, closing `§9.2`'s diversity criterion in full.

## ADR-66 — Watch events and outcomes close the post-watch loop (blueprint gap 4, remainder)

**Context.** ADR-58 closed gap 4's write side for `recommendations` but left its own "Still open" note: no `outcomes`/`watch_events` recording exists, so `BP §4.5`'s diagram (recommendation shown → actual watch → title returns to triads → compare prediction to real ranking → correct weights) has a log to write into and nothing writing to it. Both tables and entities have existed, empty, since M5. `API.md`'s own not-yet-implemented `§14`/`§2.2` target draft already specifies the shape (`POST /api/v1/watch-events`, body `{ profileId, titleId, watchedAt?, source, audioLanguage?, subtitleLanguage?, provider? }`, "does not imply liking; if the title was recommended, links an outcomes row") — this ADR implements that behavior, not a new design, adapted to this repository's own convention of `profileId` in the URL (every other route) rather than the body, and kept unversioned under `/api` like every other endpoint built this session (ADR-15: the whole API migrates to `/api/v1` in one step, not per-endpoint).
**Decision.** New `WatchEventsModule` (`Controller`/`Service`/`CreateWatchEventDto`, mirroring `ConsentsModule`'s structure) adds `POST /profiles/:profileId/watch-events`. `WatchEventsService.create()`: checks profile ownership and title existence (same pattern as `UserTitleStateService`); finds the most recent `Recommendation` for the same `(profileId, titleId)`, if any; writes a `WatchEvent` row (`source`, optional `audioLanguage`/`subtitleLanguage`/`provider`, `recommendationId` if found); when a recommendation was found, also writes an `Outcome` row (`type: 'watched'`, same `occurredAt`); and — mechanically required for "returns to triads" to mean anything — upserts the title's `UserTitleState` to `state: 'watched'` by calling `UserTitleStateService.upsert()` (exported from `UserTitleStateModule` for this), not by duplicating its PATCH semantics (M1). No rating/liking field exists anywhere on this path, matching `UpdateTitleStateDto`'s own rule and API.md's explicit "does not imply liking."
**Consequences.** The post-watch loop's first two arrows now close for real; the last two ("compare prediction to real ranking", "correct weights/fingerprint/exception") already happen on their own once a watched title re-enters a completed triad — `training.py` reads completed triads directly, not `outcomes`/`watch_events` — so nothing further was needed there. This is additive, not a replacement: `PATCH …/state` keeps working exactly as before for watchlist/interested and for watch history with no in-app recommendation event; the two paths converge only through the shared `UserTitleStateService.upsert()` call, never duplicated logic. Still open: the other four `outcomes` types this endpoint doesn't cover (`saved`/`clicked`/`dismissed_not_relevant`/`opened_provider`, the target's separate `POST …/recommendations/:id/outcome`) and `library_imports`, M5's one still-unwritten table — the CSV import feature itself doesn't exist. Nothing yet reads `outcomes`/`watch_events` back for `§16`'s evaluation. Verified with 8 new unit tests (mocked repositories: ownership, unknown title, with/without a matching recommendation, no rating field on either row written, `watchedAt` default-vs-supplied, the `UserTitleState` upsert call's exact arguments) and 4 new e2e tests over real HTTP against real Postgres (links the right recommendation and writes the outcome; records a bare watch with none and still marks the title watched; IDOR-rejects another user's profile; 400s on an unknown body field under whitelist validation) — full backend suite green (158 unit; e2e green except one pre-existing case unrelated to this change, `recommendations-persistence.e2e-spec.ts`, confirmed to fail even in isolation from `postgres-test` data accumulated across this session's many prior e2e runs, flagged as its own follow-up rather than fixed here); `tsc`/`eslint` clean.
**Revisit when.** The other `outcomes` types get their own endpoint, closing gap 4 in full; or `§16`'s offline evaluation is built and needs to read `outcomes`/`watch_events` back.

## ADR-67 — The remaining `outcomes` types get their own endpoint (blueprint gap 4, in full)

**Context.** ADR-66's own "Still open" named the exact next piece: `saved`/`clicked`/`dismissed_not_relevant`/`opened_provider` still had no writer. `API.md`'s target draft already specifies this too (`POST /api/v1/recommendations/:id/outcome`, body `{ type: 'saved'|'clicked'|'dismissed_not_relevant'|'opened_provider' }`, "no thumbs/stars") — same situation as ADR-66, implementing an already-specified shape rather than designing a new one. `Outcome.type` also carries `'watched'` (ADR-66's own path) and `'ranked_later'` (for when a previously-recommended title re-enters a triad and gets ranked — the literal "compare prediction to real ranking" arrow of `BP §4.5`'s diagram); neither belongs on this endpoint, since both are system-observed facts, not something a caller reports about themselves.
**Decision.** New `OutcomesModule` (`Controller`/`Service`/`CreateOutcomeDto`, the same three-file shape as `ConsentsModule`/`WatchEventsModule`) adds `POST /recommendations/:recommendationId/outcome`. No `profileId` in the path — ownership comes from the recommendation's own `profileId`, the same id-only pattern `POST /triads/:triadId/rank` already uses (load the resource, then `assertProfileOwnership` on the row it points to), not the `/profiles/:profileId/...` shape every other route here uses, because this resource already carries its owner. `CreateOutcomeDto` whitelists exactly the four caller-facing types via `@IsIn` — `'watched'`/`'ranked_later'` are rejected by validation, not merely undocumented, so no caller can spoof a system-observed outcome through this path. `OutcomesService.create()` writes one `Outcome` row per call, `occurredAt: new Date()` — an append-only event log like `triad_replacements`, not a toggle: acting on the same recommendation twice (e.g. "clicked" then "saved") writes two real rows, not an overwrite.
**Consequences.** Closes gap 4's write side in full for the four caller-reportable outcome types; `'ranked_later'` — the one piece of `BP §4.5`'s diagram genuinely not built ("title returns to triads → compare prediction to real ranking") — stays open, since writing it needs `TriadsService.rank()` to notice a just-ranked title was previously recommended and is real, separate scope (a different service, a different trigger point), not a gap in this endpoint. Nothing yet reads any `outcomes` row back for `§16`'s evaluation either. IDOR-safe by construction: an unknown recommendation id and a real recommendation owned by another user return the identical `NotFoundException('Profile not found')`, matching `TriadsService`'s own convention, so a caller can't distinguish "doesn't exist" from "isn't yours." Verified with 8 new unit tests (unknown id, IDOR same-error assertion, all four accepted types via `it.each`, timestamp bounds, two calls append two rows not one) and 5 new e2e tests over real HTTP against real Postgres (records an outcome; two calls append two rows with different types; 404 on an unknown id; 404 on another user's recommendation; 400 on `type: 'watched'` under whitelist validation); `tsc`/`eslint` clean.
**Revisit when.** `TriadsService.rank()` is extended to write `'ranked_later'` outcomes when a ranked title traces back to an earlier recommendation, closing `BP §4.5`'s diagram in full; or `§16`'s offline evaluation is built and needs to read `outcomes` back.

## ADR-68 — `ranked_later` outcomes close `BP §4.5`'s diagram in full (blueprint gap 4, done)

**Context.** ADR-67's own "Revisit when" named the exact last piece: `TriadsService.rank()` needed to notice a just-ranked title was previously recommended and write the `'ranked_later'` outcome — the literal "title returns to triads → **compare prediction to real ranking**" arrow of `BP §4.5`'s diagram, the one step of the whole loop that was still just a diagram. `Outcome.triadId`/`rankPosition` have existed in the schema since M5 for exactly this type, unused until now.
**Decision.** `TriadsService` gains direct `Recommendation`/`Outcome` repositories (the same choice `WatchEventsService` made — a repository-level write, not a cross-module call into `OutcomesService`, since both services need the identical one-row-write and going through another module's service for it would be indirection with no benefit). A new private `recordRankedOutcomes()` runs once, only from `rank()`'s fresh-completion path — never from an idempotent replay or a lost-race retry, both of which return a triad the winning attempt already recorded outcomes for, so running it there too would double-write. For every title in the submitted `ranking` (best first, ADR-15), it looks up the most recent `Recommendation` for `(profileId, titleId)` — the same "most recent, if any" convention `WatchEventsService` already uses — and, when one exists, writes one `Outcome` row (`type: 'ranked_later'`, `triadId`, `rankPosition` = the title's index in `ranking`, so `0` means it was ranked best). A title never recommended writes nothing; today, with no candidate-generation policy beyond `random-v1` reading watched titles directly (blueprint gap: policy), most triads have no recommendation history at all, so an all-empty result is the common case, not a defect.
**Consequences.** Closes blueprint gap 4 in full: every `Outcome` type now has a writer (`'watched'`/`recommendationId`-link via `WatchEventsService`, ADR-66; the four caller-reportable types via `OutcomesService`, ADR-67; `'ranked_later'` here), and `BP §4.5`'s whole diagram — recommendation shown, actual watch, title returns to triads, compare prediction to real ranking, correct weights — is mechanically wired end to end for the first time (the last arrow, "correct weights/fingerprint/exception," already happened on its own once a watched title re-enters a completed triad, since `training.py` reads completed triads directly). Still nothing reads any `outcomes` row back for `§16`'s offline evaluation — that remains a separate, later piece, unaffected by this closing the write side. Verified with 5 new unit tests on `TriadsService` (no outcome for a never-recommended title — the common case; correct recommendation linked with `rankPosition` matching the title's position in the final ranking, not its position in the original unordered `titleIds`; one outcome per recommended title when more than one of the three qualifies; the query is scoped by `profileId` as well as `titleId`; no double-write on an idempotent replay) and 1 new e2e test over real HTTP against real Postgres (marks three titles watched, recommends one of them, ranks the resulting triad, confirms exactly one `outcomes` row exists — linked to the right recommendation, the right triad, and the right `rankPosition` — and that the other two untouched titles wrote nothing). Full backend suite green: 171 unit tests, e2e 11 files/56 tests; `tsc`/`eslint` clean.
**Revisit when.** `§16`'s offline evaluation is built and needs to read `outcomes`/`watch_events` back, or a real candidate-generation policy (beyond `random-v1`) makes `ranked_later` outcomes common enough to analyze.

## ADR-69 — V2 fingerprint families wired into the trainer and scorer (blueprint gap 5/6, model change)

**Context.** Session C's first non-synthetic ranker evaluation (`claude@judge.local`, a real human-derived ranking, not a synthetic persona, `DEMO_DATA_PLAN_2026-09-03.md` §7.1) disagreed with V1 exactly where V1 has no words for the difference — a cynical film scored like a contemplative one, a warm humanist film sank, because V1 knows only `warmth`. `FINGERPRINT_SCHEMA.md` §3.1 specified and `enrichment.py` extracted 15 new namespaced dimensions (narrative, tone, characters, ending — the families a plot synopsis can actually support) into a `fingerprint.v2` block, published for all 300 demo titles, but left the wiring "proposed to its owner" rather than done: growing `FINGERPRINT_DIMENSIONS` from 13 to 28 is a model-identity change (any existing snapshot's weight vector becomes the wrong length), not a routine addition. Owner confirmed directly (asked explicitly, not inferred from a peer's relay) before this was undertaken. A real 50-round evaluation against that same human-derived ranking (`fingerprint_v2_eval.py`, `DEMO_DATA_PLAN_2026-09-03.md` §7.2) already validated the wiring empirically before any of this code existed: held-out NLL 0.82 vs 0.91 for V1 alone, Spearman agreement with the judge's own order 0.83 vs 0.79, all six of V1's mis-rankings moved to the correct half; V2 alone is weak (0.53–0.57) — it complements V1, it does not replace it; at 25 rounds the 28-dimension vector overfits under a single fixed regularization strength.
**Decision.** `training.py`'s `FINGERPRINT_DIMENSIONS` becomes `FINGERPRINT_V1_DIMENSIONS + V2_FEATURES` (28 keys, V1 first) — `V2_FEATURES` imported from `enrichment.py` (read-only; that file is session C's, untouched) rather than duplicated, so the two can never drift apart. `fingerprint_vector()` reads V1 keys at the top level and V2's namespaced `family.feature` keys from the nested `fingerprint.v2.features` block (`FINGERPRINT_SCHEMA.md`'s own storage shape) — both into one flat 28-value vector, so nothing downstream needs to know a fingerprint has two internal shapes; a title enriched with V1 only (no `v2` block — true of the original 15 seed titles, which the enrichment-v2 pass never touched) is therefore incomplete under the 28-dimension vector and its triads are excluded from training, the same "unknown, not zero" rule (`BP §6`, `§11.3`; ADR-19) a missing V1 dimension already triggered, now extended to the whole V2 block. `MODEL_VERSION` bumps to `plackett-luce-v2`. Regularization: rather than the invented, unvalidated option of a separate fixed shrinkage strength for the V2 block — `BP §7.1` names general L2/diverse-evidence protection for `θᵀφ`, not a V1-vs-V2 differential, so inventing one would be exactly the kind of ungrounded threshold this codebase avoids — `train_and_evaluate()` now fits every candidate in `REGULARIZATION_GRID = (0.01, 0.03, 0.1, 0.3)` on the same train/held-out split and keeps the one with the lowest held-out NLL, then refits the served weights with that chosen value; below the 5-triad floor (no held-out slice to choose from) it defaults to the grid's smallest entry, same spirit as every other held-out-gated diagnostic here. This mirrors exactly what `fingerprint_v2_eval.py` already validated empirically (0.1 held up at 25 rounds, 0.01 was better at 50) rather than guessing a single number. `recommendations.service.ts` mirrors all of this: `FINGERPRINT_V2_DIMENSIONS` (a new export from `title-fingerprint.type.ts`, alongside the new `FilmFingerprintV2` interface — `v2` is now an optional field on `FilmFingerprintV1`) plus the existing 13 V1 keys become the service's own 28-key `FINGERPRINT_DIMENSIONS`; `fingerprintVector()` gets the identical two-shape read (V1 flat, V2 nested) `training.py` has, so trainer and scorer read the exact same 28 numbers in the exact same order — `UserModelSnapshot.weights` is a plain positional array, not a keyed map, so the two sides silently scoring against different dimension orders would be a real, hard-to-detect bug if they ever drifted.
**Consequences.** A title with V1 only is still a valid recommendation candidate (imputed like any missing dimension, ADR-19) but can never enter training until it gets a `v2` block — a real, documented consequence of this change: the 15 original `FILM*` seed titles, which the enrichment-v2 pass never touched, become permanently untrainable-against unless and until they're re-enriched, not a bug, an honest tradeoff flagged rather than hidden. `loadSnapshot()`'s existing `snapshot.weights.length !== FINGERPRINT_DIMENSIONS.length` guard (unchanged) already refuses to score against a pre-this-change (13-length) snapshot with a `ConflictException`, so no separate migration or backfill was needed for correctness — an old snapshot simply stops being usable and a fresh training run replaces it. This change is scoped to the model-service layer only: no schema migration (fingerprint is already a JSON column; `v2` is additive within it), and no change to `UserModelSnapshot`'s own columns. Two downstream files session C owns broke as a direct, expected consequence of `FINGERPRINT_DIMENSIONS` changing meaning (was "the 13 V1 keys," is now "all 28") — `fingerprint_v2_eval.py`'s own `FEATURE_SETS["v1"]` needs to import the new `FINGERPRINT_V1_DIMENSIONS` name instead, and `train_demo.py`/`personas.demo.json`'s persona `theta` vectors need to grow from 13 to 28 values — both flagged to her directly with the exact fix, neither touched here (her files, her call on how/when to update them; she had already planned to re-measure and regenerate after this landed). Verified: `training.py`/`ranker.py`'s own suite green (53 tests, 8 new: missing-v2-block/missing-one-v2-dimension/reads-nested-v2 on `fingerprint_vector()`, five on the regularization grid — determinism, default-below-floor, and an independent argmin recomputation proving the selection logic itself, not just that it runs); backend suite green (176 unit tests, 6 new covering V2 scoring/imputation/reason-citation; 56 e2e); `tsc`/`eslint`/`ruff` clean.
**Revisit when.** The original 15 seed titles are re-enriched with a `v2` block (removing the "permanently untrainable" caveat above); the People or Cultural-context feature blocks `FINGERPRINT_SCHEMA.md` §3.1 names as still unbuilt get their own extraction pass and need the identical wiring treatment; or a real candidate-generation policy needs `RecommendationReason` to cite a V2 dimension in copy a user actually reads (today's frontend has no translation string for any V2 key — flagged to session B, not built here).

## ADR-71 — Director diversity closes blueprint gap 5's `§9.2` criteria in full

**Context.** ADR-70 unblocked the last of `§9.2`'s three named diversity axes by loading real `credits`/`people` rows; genre (ADR-62) and language (ADR-64) were already wired into `confidenceBand()`/`training.py`, leaving director as the one remaining gap. ## ADR-72 — Licensing agreements deferred to the revenue-model study (partially supersedes ADR-13)

**Context.** DATA_LICENSING.md, PRIVACY.md and the Alpha plan were pulling a commercial TMDB agreement, GroupLens permission, an availability-partner contract and external legal counsel into week one of development, and gating content display on `licenseStatus: 'commercial_allowed'`. The owner decided (2026-09-04) that launch is free with no revenue of any kind, that the revenue model itself is studied only after a real post-launch operating period, and that every licensing/agreement question is an input to that later study, not a pre-launch blocker — confirmed independently against DATA_LICENSING.md's own §0, "Launch-stage policy (owner decision, 2026-09-04)". Requesting a commercial agreement for a product in development with no revenue has no counterparty rationale, and the sources already in use — Wikidata (CC0), Wikipedia (CC BY-SA), TMDB's free non-commercial key, GroupLens's research terms, this codebase's own LLM derivatives, and now IMDb's non-commercial datasets (owner decision, same day, DATA_LICENSING.md §3.2) — already cover a free service in full without a single signed agreement.
**Decision.** (1) No license request, API agreement, permission letter, or counsel engagement is a gate for any phase before the first dollar of revenue. (2) `licenseStatus` values `non_commercial_only` and `unknown`, each with a named source, are displayable throughout the free period; `commercial_allowed` becomes a display condition only once revenue starts. (3) The rights registry (`source_records`) is still populated with source and attribution for every value regardless — cheap now, and it turns a later license change into a data update, not a rebuild. (4) The free period stays genuinely free: no subscription, no ads, no referral commission on "where to watch" links. (5) Every deferred agreement (TMDB commercial, an availability partner, GroupLens permission if an external seed is still wanted, outside counsel, a DPO) opens together at the revenue-model study, priced as a line item there. (6) Legal review before launch is internal, by the team (PRIVACY.md §13), not outside counsel. (7) IMDb's free datasets are required in the free-launch service itself (owner, same day) — the Public Quality source and a title/credit matching aid, official dumps only, attribution rendered, no bulk redistribution; the commercial license (AWS Data Exchange) is priced at the same later study. (8) Unconditional in every phase regardless of revenue: no scraping, no bulk redistribution of any third-party data, no personal data sent to the LLM.
**Rationale.** License terms restrict *use*, not *development stage* — what actually triggers an agreement requirement is the first unit of revenue, not the first line of code. Fingerprints are derived from Wikipedia/Wikidata text, not TMDB, so TMDB's terms' AI/ML clause was never actually implicated. The LLM provider switch (ADR-63) doesn't touch licensing either, since the rights question is about the inputs, not the model. Agreements negotiated later, with real usage numbers in hand, are negotiated better than ones guessed at pre-launch.
**Consequences.** Partially supersedes ADR-13: its "seed the shared latent space before launch only from data licensed for commercial use" clause becomes "an external seed is optional during the free period; the permission question is an input to the revenue study" — MovieLens/Tag Genome are no longer a hard pre-launch block, just not currently planned either. No code changes: `PublicTitle` already needed to show `non_commercial_only` in every environment before revenue exists, which this decision confirms rather than changes. Prepared now to serve that later study cheaply: per-feature usage measurement under the existing `analytics_first_party` consent purpose, and token/cost logging per model call by name (both already-existing mechanisms, not new work). Downstream documents this touches (DATA_LICENSING.md §0/§1/the source matrix/§3.3/§3.5/§6/§7, PRIVACY.md's header/§7/§8/§13, RANKING_ALGORITHM.md §11, `IDENTITY_DECISIONS_2026-09-03.md` B4, the blueprint's gate 4/§11/§17.2/§21.2/App. B, ALPHA_PLAN §0.4/§3/§4/§4b/§5) are each their respective owning session's own edit, not made here — this entry covers only `ARCHITECTURE_DECISIONS.md` and the `IMPLEMENTATION_STATUS.md` status rows it directly names.
**Revisit when.** The first revenue decision of any kind is made, fingerprint inputs move from Wikipedia text to TMDB text, or any currently-used source's terms change.

## ADR-73 — Privacy rights (export, delete, reset) synchronous at Alpha scale; delete is a tombstone, not a hard erase

**Context.** `privacy_requests`/`audit_log` existed since M2 but nothing wrote to either — no export, delete, or reset flow, and `PRIVACY.md` §5/§9/§10 named the design questions unresolved: how a delete survives as a permanent, personal-data-free record (`§9`), how export is served, how a delete is verified and reversible. ALPHA_PLAN phase 2 (items 2.1, 2.3) scoped the work.
**Decision.** New `apps/backend/src/modules/privacy/` module: `POST /privacy/export` re-verifies the password, then returns one portable JSON copy (account, consents, and per profile: title states, triads with replacements, snapshots with weights keyed by feature name, recommendations with outcomes, watch events) — synchronous, not a queued artifact, since Alpha's data volume per user makes that simple and correct rather than needing async job infrastructure this codebase doesn't otherwise have. `POST /privacy/delete` schedules the purge `PRIVACY_DELETE_SAFETY_DAYS` ahead, pauses every profile meanwhile (`profiles.pausedAt`), is cancellable until a periodic in-process sweep executes it, and idempotent. `POST /privacy/reset` deletes one profile's triads/snapshots/recommendations only — account, consents and watch history survive, matching the existing "wipe and start a new profile" UX rather than a full account delete. `GET /privacy/requests` lists a user's own requests. The delete itself is a tombstone, not a hard erase of `privacy_requests`: migration `PrivacyRequestsTombstone` makes `userId` nullable with `ON DELETE SET NULL` and adds `subjectKey` (`sha256(userId)`, indexed) — the row survives the account it named, answerable ("was this account deleted, and when?") from the id alone without keeping the id itself, `PRIVACY.md` §9's "permanent record without personal data" read literally; `profileId` (bare uuid, no FK) records which profile a `reset` applied to. Every privacy route writes an `audit_log` row (success/failure/schedule/cancel) via a new `AuditService.record()` — the first and only writer to that table, accepting an `EntityManager` so the audit row commits in the same transaction as the action it records, never orphaned by a mid-transaction failure. Client IPs are stored as a salted hash (`AUDIT_IP_SALT`), never raw.
**Consequences.** `privacy_requests`/`audit_log` go from schema-only to real writers; `audit_log` still has no reader (no admin board or query surface) — a write-only table until one exists. Deliberately not built here: the four remaining consent purposes' `no_pooled`/`pause_all` enforcement (gap 7, in progress at sessions A/B when this landed) — `pausedAt` is now read by the training trigger and written here on a scheduled delete, but not yet read by recommendation serving itself. `consents.userId` still cascades on delete (`ON DELETE CASCADE`, M2), in tension with the same `§9` promise `privacy_requests` now honors — flagged as a design question (F5 to A), not resolved in this ADR. Verified: 13 new unit tests, 7 new e2e tests over real HTTP (wrong password → 403 audited, export carries every named entity type, reset preserves watch history, delete schedules/pauses/cancels/executes and leaves a tombstone with no `userId` and a `system`-actor audit row, login after execution → 401).
**Revisit when.** `consents` gets the identical tombstone treatment (decided: yes, matching `privacy_requests` exactly — `.claude/SESSIONS.md` request F5; not yet built); an admin board needs to read `audit_log`; or export volume at a later scale needs to move off the synchronous path.

## ADR-74 — Model service over HTTP, and training triggered automatically after the third triad

**Context.** `BP §18.1` requires a new user to reach a first result unaided; ADR-25 decided the HTTP interface between the backend and Python but nothing called it yet — training stayed a manual CLI (`python -m src.training`) through `1a62cb3`.
**Decision.** `services/workers/src/model_service.py`: a FastAPI service wrapping `train_profile()` unchanged — `POST /train` (async, returns a job id), `GET /train/{jobId}`, `GET /train?profileId=`; a single worker thread (trainings run one at a time, not concurrently); an in-memory job ledger (a restart forgets the queue, but the backend re-requests at the next threshold anyway, so nothing is silently lost); at most one pending job per profile (idempotent — a request while one is already queued or running is a no-op, not a duplicate); a request that arrives mid-run queues exactly one more after; a shared bearer token; binds to `127.0.0.1` by default. The backend triggers training from a TypeORM subscriber (`triad-completed.subscriber.ts`) on `triads.status` transitioning to `completed` — not from `TriadsService` directly, so the ranking write path (ADR-32/68) never slows down for it — on the `TRAINING_FIRST_TRIAD_COUNT`th triad (default 3) and every `TRAINING_EVERY_N_TRIADS` after (default 5, both configurable: `App. C` leaves the exact numbers to experiment, not a fixed blueprint value). A paused profile (`pausedAt`) is never trained; a model-service failure never fails the triad ranking it followed. Two owner-facing routes: `POST /profiles/:id/train` (manual) and `GET /profiles/:id/training` (status/latest snapshot). `MODEL_SERVICE_URL` unset disables the trigger entirely and training stays the manual CLI — the state every other e2e spec in this suite already relies on.
**Rationale.** The smallest change that satisfies `§18.1`'s first line without a Redis queue (ADR-10/25: introduced only when `§12.3` signals fire); subscribing at the persistence layer, not the service layer, keeps the ranking path exactly as it was and can never regress it; the two thresholds are configuration because the blueprint deliberately leaves the exact count to experiment (`App. C`), not because either number is load-bearing today.
**Consequences.** `.env.example` gains a `MODEL_SERVICE_*`/`TRAINING_*` block; `Makefile` gains `model-service`; `pyproject.toml`/`poetry.lock` gain `fastapi`, `uvicorn`, `httpx`. No `model_versions` row is written yet (a later phase item). `FastAPI model service` is still 🟡, not ✅: only `/train` and `/health` exist; `/triads/select`, `/score`, `/taste-profile` from ADR-25's original interface remain unbuilt — scoring and selection stay in the backend for now. `New user reaches a first result unaided` moves to 🟡: the backend now trains automatically, but the frontend shows no waiting/progress state for it yet (open, tracked separately on the coordination board).
**Revisit when.** `§12.3` signals fire (heavy concurrent training, long imports) — move to a real queue and a durable job ledger; multiple backend instances are ever deployed — move the ledger out of process memory; or ADR-25's remaining three endpoints (`/triads/select`, `/score`, `/taste-profile`) are built.

## ADR-75 — Third fingerprint block (form families) wired into the trainer and scorer, 28 to 40 dimensions

**Context.** Session C specified and extracted a third fingerprint block (`FINGERPRINT_SCHEMA.md` §3.3, `enrichment.py`'s `generate_fingerprint_v3()`): 12 more namespaced dimensions covering rhythm detail (`rhythm.setupLength`/`turningPointDensity`/`deliberateness`), information handling (`information.expositionDirectness`/`subtext`/`knowledgeComplexity`), style (`style.stylization`/`experimentation`/`scale`), and two tone registers plus narrative scale the first non-synthetic ranker evaluation showed were still missing from V1+V2 (`tone.playfulness`, `tone.sentimentality`, `narrative.scope` — DEMO_DATA_PLAN_2026-09-03.md §7.2's finding, closed here). Extracted and published for all 300 demo titles (the original 15 `FILM*` seed titles remain untouched, same as V2). Owner confirmed directly (asked explicitly, not inferred from the peer relay) before wiring, the same discipline ADR-69's V2 wiring used. C's own real evaluation (`fingerprint_v2_eval.py`, a genuine human-derived ranking, not synthetic) found the block was net-negative at 50 rounds under every regularization candidate (overfit on too little held-out data) but a clear win once re-measured at 75 rounds (71 valid, 14 held out): held-out NLL 0.82 vs 1.076 for V1+V2 alone, Spearman agreement with the judge's own order 0.89 vs 0.84, V1+V2+V3 winning at every candidate in the existing regularization grid, not just the chosen one.
**Decision.** `training.py`'s `FINGERPRINT_DIMENSIONS` becomes `FINGERPRINT_V1_DIMENSIONS + V2_FEATURES + V3_FEATURES` (40 keys total, imported read-only from `enrichment.py` exactly as V2 already was, so the two can never drift apart). `fingerprint_vector()` reads V1 at the top level and both V2's and V3's namespaced `family.feature` keys from their own nested blocks (`fingerprint.v2.features`, `fingerprint.v3.features`) — a namespaced key is routed to V3's block specifically when it is one of V3's own keys (checked against `V3_FEATURES`, not just "contains a dot"), V2's block otherwise, since the two families share at least one namespace name (`tone.*`) without any individual key colliding. `MODEL_VERSION` bumps to `plackett-luce-v3`. Regularization: no new per-block penalty — the existing held-out-chosen `REGULARIZATION_GRID` (unchanged since ADR-69) already won at every candidate for V1+V2+V3 at 75 rounds, exactly the situation an adaptive, held-out-chosen value is for rather than adding an untested, unvalidated per-block hyperparameter (`BP §7.1` names general regularization for this term, not a per-family split) — a real, explicit trade-off flagged to and confirmed by the owner: this single-parameter approach wins from roughly 75 rounds on and loses slightly below it, where a separate per-block penalty (keeping V3 weights near zero until evidence supports them) would cost an extra tuned hyperparameter to buy earlier safety. `recommendations.service.ts` mirrors all of this: `FINGERPRINT_V3_DIMENSIONS` (a new export from `title-fingerprint.type.ts`, alongside the new `FilmFingerprintV3` interface — `v3` is now an optional field on `FilmFingerprintV1`) extends the service's own `FINGERPRINT_DIMENSIONS` to 40 keys; `fingerprintVector()` gets the identical three-shape read (V1 flat, V2 nested, V3 nested with the same family-name-collision-safe routing) `training.py` has.
**Consequences.** A title with V1(+V2) only is still a valid recommendation candidate (imputed like any missing dimension, ADR-19) but cannot enter training until it gets a `v3` block too — the same permanently-untrainable caveat ADR-69 already flagged for the 15 original seed titles, now also true of any title that somehow got V1+V2 but never V3 (none exist today; every title with V2 also has V3 from the same extraction pass). `loadSnapshot()`'s existing `snapshot.weights.length !== FINGERPRINT_DIMENSIONS.length` guard (unchanged) already refuses to score against a pre-this-change (28-length) snapshot with a `ConflictException` — no separate migration or backfill needed. Two files session C owns broke as a direct, expected consequence of `FINGERPRINT_DIMENSIONS` changing meaning again (was "all 28," is now "all 40") — `fingerprint_v2_eval.py`'s own `FEATURE_SETS["v1+v2"]` needs a fixed 28-key tuple instead of reading the now-40-length `FINGERPRINT_DIMENSIONS`, and `train_demo.py`/`personas.demo.json`'s persona `theta` vectors need to grow from 28 to 40 values (or the same `getattr`/zero-pad tolerance train_demo.py already has for 13→28 needs to extend to 40) — both flagged to her directly with the exact failing assertions, neither touched here (her files, her call on how/when to update them). Verified: real, non-synthetic round trip — `python -m src.training` run for real against `movie-postgres`'s highest-triad-count demo profile (71 completed triads, up from 47 at the last verification since more triads had accumulated) reported "chosen regularization=0.03" and a held-out NLL/accuracy matching C's own reported numbers almost exactly (0.8227/85.71% here vs her 0.82/0.86 rounded), and the persisted `user_model_snapshots` row read back directly confirmed 40 weights and `modelVersion: plackett-luce-v3`. `training.py`/`ranker.py`'s own suite green (138 tests in files this ADR owns, 8 new: missing-v3-block/missing-one-v3-dimension/reads-nested-v3-not-v2 on `fingerprint_vector()`, plus a director-diversity-passthrough re-check); backend suite green (262 unit tests, 3 new covering V3 scoring/imputation; 45 in the recommendations spec alone); `tsc`/`eslint`/`ruff` clean.
**Revisit when.** `fingerprint_v2_eval.py`/`train_demo.py` are updated to the new dimension count (flagged to C); the People or Cultural-context feature blocks `FINGERPRINT_SCHEMA.md` §3.1 still names as unbuilt get their own extraction pass; or a real candidate-generation policy needs `RecommendationReason` to cite a V3 dimension in copy a user actually reads (today's frontend has no translation string for any V3 key, same gap ADR-69 already flagged for V2).

## ADR-76 — Activating a `model_versions` row now actually changes what is served (blueprint gap 5/`§18.1` rollback, F10)

**Context.** `AdminModelsService.updateModel()` (session F, `b9bd39b`) already let an admin pin exactly one `model_versions` row `active` — the rollback control `BP §18.1` names — but nothing ever read `active` back: `RecommendationsService.loadSnapshot()` always served each profile's newest `user_model_snapshots` row regardless of `modelVersion`, so activating a version had no observable effect on what a user actually saw. The admin service's own code comment already named this precisely: "Nothing reads `active` yet ... wiring that read is the model-service owner's."
**Decision.** `loadSnapshot()` (the one private method both `findForProfile()` and the library-ranking endpoint already share, so this closes the gap for both surfaces at once) now looks up `model_versions` for the row with `active = true` before falling back to the pre-existing behavior. When one is pinned, it prefers this profile's latest snapshot whose `modelVersion` matches the pinned version exactly; when that profile has no snapshot under the pinned version (never retrained since the pin, or the pin points at a version this profile hasn't reached yet), it falls back to the profile's own latest snapshot regardless of version — the same behavior as when nothing is pinned at all. A pin narrows which snapshot is preferred; it never turns an otherwise-servable profile into an unservable one, and it never reaches across profiles (a rollback is a global policy choice, but which snapshot satisfies it is still resolved per profile, since `user_model_snapshots` has no cross-profile shared row).
**Rationale.** The one-extra-query cost (`model_versions` has at most a handful of rows, queried once per request, not per candidate title) is the smallest change that makes an existing, already-shipped admin control actually do what its own UI and audit log already claim it does — the alternative of leaving it a no-op button would be a real, silent correctness gap in a safety control specifically meant for incident response.
**Consequences.** No schema change (`model_versions.active` has existed since M4; nothing new to migrate). No behavior change at all while `model_versions` has no active row (true of `movie-postgres` today — nothing has ever been registered or activated there), so this ships dormant on the shared dev database until an admin actually exercises it. `IMPLEMENTATION_STATUS.md`'s "Admin board" row moves to reflect the API surface is complete (frontend screens, `§4.2`, remain session B's open item). Verified: 3 new unit tests on `loadSnapshot()`'s new branch (queries the pin, prefers the pinned-version snapshot over a newer unpinned one, falls back correctly when the profile has none under the pin) plus a new e2e file (`model-version-rollback.e2e-spec.ts`) proving the full real-HTTP/real-Postgres round trip: serves the newest snapshot with no pin (unchanged baseline) → activating an older version serves that older snapshot instead (the rollback actually takes effect) → deactivating it reverts to serving the newest again. Backend suite green (274 unit, 100 e2e); `tsc`/`eslint` clean.
**Revisit when.** A candidate-generation or scoring path is added that reads `user_model_snapshots` outside `RecommendationsService.loadSnapshot()` and would need the identical pin-aware selection; or `model_versions` gains a per-profile or per-cohort activation instead of one global pin.

## ADR-79 — Each confidence band carries a held-out accuracy floor (board C8)

**Context.** `confidenceBand()` treated held-out accuracy as a single gate: at or below chance (0.5) → `inconclusive`, otherwise the triad count decided the band. The first non-synthetic ranker (a real human order, DEMO_DATA_PLAN §7.1) therefore showed **strong** on 25 rounds while predicting only **0.67** of held-out pairs — a claim the evidence did not support, and exactly what `BP §9.2`'s "successful prediction of later held-out comparisons" criterion exists to prevent.
**Decision.** Each band gets its own floor, applied as a ceiling on whatever the rest of the method concludes: `strong` needs held-out pairwise accuracy ≥ 0.8, `likely` ≥ 0.7, below that at most `initial`; at or below chance it stays `inconclusive` as before. The floors only ever lower a band, never raise one — a 0.95 accuracy on 5 triads is still `initial`. Unknown accuracy (`null`, below the 5-triad floor, ADR-31) caps nothing, the same no-op every other held-out-gated check already is.
**Rationale.** 0.8/0.7 are not invented: the synthetic personas that pass the demo plan's own acceptance bar sit at 0.75–1.00, and that plan's bar for a recovered persona is ≥ 0.75 — so the floors separate a genuinely predictive model from one merely better than a coin flip, without demoting the personas the pipeline is validated against.
**Consequences.** A profile can now sit at `initial` indefinitely while it keeps answering rounds, which is the honest outcome when the model is not predicting that profile well; the copy already says the evidence is thin at low bands. Still not `§9.3`'s calibrated system — no Brier/ECE (ADR-21). Verified: 5 new/updated unit tests, including the 0.67 case that motivated this.
**Revisit when.** Brier/ECE calibration replaces verbal banding, or measured outcomes show either floor is mis-placed.

## ADR-80 — PRIVACY.md §4's restrictions enforced, and consents become a tombstone

**Context.** Both restrictions in `PRIVACY.md` §4 existed on paper only. `pause_all` had a column (`profiles.pausedAt`, M1) that the training trigger already honoured but nothing else — no route set it, and recommendations kept serving from the model training had stopped updating. `no_pooled` had no implementation at all. Separately, `consents.userId` still cascaded away with the account (M2), losing the record `PRIVACY.md` §9 says must outlive it — the open item ADR-73 flagged as board question F5.
**Decision.** (1) `POST /privacy/pause` and `POST /privacy/resume` set and clear `pausedAt` for the caller's profiles, audited like every other privacy action, no password re-verification (nothing is exposed or destroyed, and both are reversible). Resume deliberately does not lift a pause a *scheduled deletion* imposed — only cancelling that request does, so resuming cannot quietly undo a delete's safety pause. (2) `RecommendationsService.loadSnapshot()` refuses a paused profile with `409 profile_paused`, which covers recommendations and library ranking at once, the same single choke point ADR-76 used. (3) `ConsentsService.pooledEligibleProfileIds()` is the boundary a shared-space retrain must read: it excludes the profiles of users whose `personalization_pooled` row currently reads `granted: false`, and no one else — a user who never answered stays in (the purpose is default-on, PRIVACY.md §3) and a re-grant puts them back. (4) Migration `ConsentsTombstone`: `consents.userId` nullable with `ON DELETE SET NULL`, plus an indexed `subjectKey` (`sha256(userId)`) written on every new row — the identical treatment `privacy_requests` got.
**Consequences.** A purge now leaves the consent record standing with `userId: null`, answerable by `subjectKey` alongside that account's privacy requests; rows created before this migration keep `subjectKey: null` (no backfill, same as the sibling migration — hashing in SQL would pull in `pgcrypto` for a one-off). `no_pooled` is enforced at a boundary nothing calls yet, because the shared latent space is unbuilt (ADR-13, narrowed by ADR-72) — stated plainly rather than claimed as end-to-end enforcement; what it buys is that the retrain, when written, takes its profile set from one tested place instead of re-deriving consent. Verified: 2 new unit tests on the eligibility query, a new e2e proving pause → `409` → resume restores, and the purge e2e extended to assert consents survive with the right `subjectKey`.
**Revisit when.** The shared-space retrain is built and consumes `pooledEligibleProfileIds()`; or `pause_all` needs to stop something beyond training and recommendations.

## ADR-81 — Designed states answer 200 with a discriminator, not 4xx (board B→A, B2)

**Context.** Two of the product's most ordinary states were HTTP errors: `GET …/recommendations` returned `409` before the first model existed, and `GET …/triads/current` returned `400` when the profile had not marked enough films yet. Both are things the screen is designed to show, not failures — but a browser logs every 4xx as a failed request, so the frontend could not keep a clean console or tell a real fault from a normal first run. The work page separately needed a fingerprint summary `GET /titles/:id` never returned (board B2).
**Decision.** Both routes answer **200** with a discriminated union for every designed state. Recommendations: `{ state: 'ready', items }`, `{ state: 'pending', needed }` (rounds still to answer before the first training run; 0 once it is under way), `{ state: 'paused' }` (PRIVACY.md §4, ADR-80), `{ state: 'model_outdated' }` (a snapshot from before a fingerprint-dimension change, ADR-69/75). Current triad: the triad object plus `state: 'ready'`, or `{ state: 'need_more_watched', needed, message }` — the `state` tag rides along on the triad so an existing reader of its fields is unaffected. 4xx keeps its meaning: `401`, and `404` for a profile that is not the caller's. `GET /titles/:id` gains `fingerprintSummary`: the human-reviewed `content_features` rows as `{ key, level: 'low'|'mid'|'high' }`, `null` when none is reviewed — a level, never the raw number, and the public read still never returns `fingerprint` itself (M2).
**Consequences.** A breaking change for the one consumer, which asked for it; `docs/API.md` carries the new shapes. `GET …/library/ranking` deliberately keeps the older `409` contract — it was not part of the request, and `loadSnapshot()` still throws for it, so the two surfaces now differ until someone asks for the third. Levels are thirds of the 0–1 scale; a reviewed row whose `value` is NULL is unknown, not zero, and is skipped. Verified: unit tests for each state and for the summary, and the e2e specs that asserted the old statuses updated to the new ones.
**Revisit when.** The library ranking wants the same treatment, or `/api/v1` (ADR-15) lands and can carry an envelope for all routes at once.

## ADR-82 — A poster on every surface, composed at read time and gated on its licence (board B4/M1)

**Context.** The owner ruled (2026-09-04) that every film carries a poster; the frontend already renders `title.posterUrl`/`title.posterSource` with a hollow slot until one arrives. Session C fetched TMDB's path for 297 of 300 titles through the API (never scraping) and wrote a `source_records` row per image with `licenseStatus: 'non_commercial_only'` and TMDB's required credit. What was missing was the backend half: a column to keep the path in, and the read that turns it into a URL.
**Decision.** `titles.posterPath` (migration `AddTitlePosterPath`) stores TMDB's path (`/abc.jpg`) — the path only, never a composed URL, so the size is chosen per read and a stale full URL can never outlive its permission. `PosterService.forTitles()`/`attach()` compose `https://image.tmdb.org/t/p/w342<path>` and attach `posterSource { name, attribution }` **only** when that title's `posterPath` rights row carries a status this stage may display (`DISPLAYABLE_LICENSE_STATUSES`, DATA_LICENSING.md §0) — the same gate Public Quality already uses, so the free period shows `non_commercial_only` and a revenue stage would not. A title with a path but no displayable row gets explicit `null`s, never an unlicensed image. Applied on every surface that returns a title: `/titles`, `/titles/starter`, `/titles/:id`, the current triad's items, recommendations, library ranking, and the watched/watchlist lists. TMDB's credit line joins `ATTRIBUTION_BY_SOURCE` next to IMDb's and Wikipedia's, so no client hardcodes it.
**Consequences.** `PublicTitle` gains two always-present fields (`null` when withheld), so a client can tell "no poster" from "not allowed to show it" only by their both being null — deliberate: the reason is not the viewer's business, and the hollow slot is identical either way. `titles.posterPath` is NULL on `movie-postgres` until the loader writes it: `seed-demo.lib.ts` maps fixture fields explicitly (`originalLanguage: entry.originalLanguage ?? null`), so it needs one added line for `posterPath` — that file is session C's, flagged to her, not changed here. The read is live and correct meanwhile: every title reports `posterUrl: null`, which is the hollow slot, not a fault. Verified: 4 unit tests on the licence gate itself (composes and credits, withholds an undisplayable status, withholds a missing row, attaches explicit nulls), plus the suites green (302 unit, 101 e2e).
**Revisit when.** Revenue starts and `commercial_allowed` becomes the only displayable status (ADR-72), or a second image source needs a different size or base URL.
**Update (owner decision 2026-09-05, board 13).** The rights-registry gate is removed from the read path: `PosterService` composes the URL and TMDB's credit for every title with a `posterPath`, consulting no `source_records` row — DATA_LICENSING.md §0 already reads a missing or `unknown` row as hygiene debt, not a display block, while the service earns nothing, and the gate as built was stricter than that policy. The registry rows stay, per value, so the display gate returns at the revenue decision as a data change; `DISPLAYABLE_LICENSE_STATUSES` still governs Public Quality values.

## ADR-83 — Adaptive triad selection v1 behind an experiment flag (ALPHA_PLAN 6.2/6.5)

**Context.** Triads were drawn uniformly from the watched-unranked pool (`random-v1`): every round cost the user the same minute and returned whatever information chance supplied. `BP §8.2` scores a triad by information per minute; `§8.3` adds safety constraints; `RANKING_ALGORITHM` §9 names `adaptive-v1` as the target and requires sampling from the top-K so `selectionPropensity` stays a real number. The `experiments`/`experiment_assignments` tables have existed since M4 with nothing reading them.
**Decision.** `ExperimentsService` reads a running `experiments` row, splits by `sha256(experimentId:profileId)` against the arm weights in its `config`, and records the assignment (`orIgnore`, never rewritten — an arm that moved under a profile would make its own history unanalysable). Hashing the pair, not the profile, keeps two experiments from correlating. No experiment row, no usable arms, or a failed write ⇒ control, always. `TriadPolicyService` implements `adaptive-v1`: score = Σ over dimensions of (this profile's per-dimension uncertainty × the spread of that dimension across the three titles) − a repeat penalty for titles from the recent round − a genre-repetition penalty, subject to `§8.3`'s constraint that no two of the three share a director (real `credits` data since ADR-70). Uncertainty is the trainer's Laplace standard errors (ADR-62) when a snapshot has them, else flat — which degrades the term to plain spread rather than pretending to certainty. It scores a bounded sample of candidate triples (not all C(n,3)) and then samples uniformly from the top-K, logging `selectionPropensity = 1/K`; `policyVersion` records `adaptive-v1` against `random-v1`'s control rows.
**Rationale.** Mutual information under a real posterior is what `§8.2` asks for and what the shared latent space will eventually supply; until then, "spread along the axes this profile's own fit is least sure of" is the honest, computable stand-in — it uses uncertainty the trainer already publishes rather than inventing a proxy. The penalties' weights are deliberately blunt starting points to be tuned against `§16` evaluation, and are named as such in the code.
**Consequences.** Nothing changes for anyone until an `experiments` row with id `triad-policy` is created and set `running` — the control path is byte-identical to before, and no such row exists on `movie-postgres` today. On a pool of ~4 eligible titles every candidate falls inside the top-K, so the policy degenerates to uniform: correct (there is nothing to choose between) and asserted in the tests rather than hidden. An undescribed title contributes no information rather than a zero-filled maximum (ADR-19). Verified: 6 unit tests on the policy (including that the repeat penalty measurably bites on a pool large enough to rank, and that zero-filling is not happening) and 6 on the flag layer (determinism, both arms used, independent draws per experiment, control on every failure path); suites green (318 unit, 101 e2e).
**Revisit when.** `§16` evaluation compares the two arms and the weights need tuning; the shared latent space lands and `IG` can target Fisher information for real.

## ADR-84 — The three tracks become real, with a declared exploration share (ALPHA_PLAN 6.3, implements ADR-8)

**Context.** ADR-8 split recommendations into `safe`/`discovery`/`outside_usual` in 2026-09-03, but every row shipped `track: 'safe'` — the frontend's three sections had two that honestly said "not built". `BP §4.4` defines them: safe is the best fit inside the region the model knows, discovery crosses a genre or language on a proven axis, outside_usual is higher-risk exploration against the filter bubble.
**Decision.** The profile's "usual region" is descriptive, computed from the genres and original languages of the titles it has actually watched — it never filters candidates, only decides which track a recommendation is shown under. Over the full ranking (not the top-`limit` slice): a candidate whose every genre is outside that set, or whose original language is, becomes `discovery`; the rest are `safe`. The declared exploration share (default 0.2, ADR-8's "small, declared") takes its slots from the **tail** of the same ranking rather than the head — a track that only ever showed near-misses would prevent no bubble — and each row logs `track: 'outside_usual'` so `§16` can compare the three. The share is `ALPHA_PLAN` 6.5's second flag: it reads the `exploration-share` experiment through the same layer ADR-83 built, falling back to the default for an unknown arm rather than inventing one.
**Consequences.** A profile with no watch history has no region to cross, so everything stays `safe` until it does — honest, rather than labelling arbitrary titles discoveries on day one. Assignment is deterministic in rank order, so `selectionPropensity` stays 1 and the log remains reproducible (ADR-8's own requirement). Ranking the full candidate list before slicing costs one pass over titles already in memory. Verified: 4 new unit tests (safe vs discovery by genre and by language, the share spent on the tail and not the head, nothing called a discovery without history, the experiment arm changing the share); suites green (322 unit, 101 e2e).
**Revisit when.** `§16` measures the three tracks' outcomes and the share or the crossing rule needs tuning; or Watchability data arrives and `outside_usual` should weigh availability before risking a slot.

**Addendum (2026-09-04, A-16, owner decision O-7).** `crosses()` is now a score, not a predicate: one point for a genre set entirely outside the profile's watched genres, one for a language it has never watched (0-2). Only the best available crossing is labelled `discovery`, so a title outside on both axes is never shown beside a one-axis near-miss as though they were the same suggestion.

**A correction to the decision's premise, recorded because it changes what is still open.** O-7 was raised on the reading that the old code required *both* axes and dropped everything short of that, leaving the section empty. It did not: it was already `genreCrosses || languageCrosses`, and the new score has the *identical* emptiness condition — no discovery iff nothing crosses on either axis. So this change improves ordering, not emptiness. The real reason session B saw an empty section is the genre test itself: `genres.every(g => !usual.has(g))` needs **every** genre of a candidate outside the profile's accumulated union, which a wide watch history makes almost unreachable, leaving language as the only live axis. Relaxing that (any genre outside, or a majority) is a separate open decision, not this one.

## ADR-85 — Password reset behind a swappable mailer, with the provider still undecided (ALPHA_PLAN 3.2) — **Resend SDK adapter replaced by the generic SMTP adapter, ADR-95 (2026-09-05)**

**Context.** An account whose password is forgotten had no way back; `ALPHA_PLAN` 3.2 was blocked on §4.2's open owner decision about a mail provider (O-3). That decision gates *sending*, not the flow — so the flow can exist now if the transport is a seam rather than a hardcoded vendor.
**Decision.** `Mailer` is an abstract seam with one implementation today, `LogMailer`, which writes what it would have sent to the server log and sends nothing; `MAIL_TRANSPORT` selects it (default `log`), and an unrecognised value throws at boot rather than silently dropping mail someone is waiting for. `POST /auth/password-reset/request` always answers `202` whether or not the address has an account — answering differently would make the route a membership oracle (`BP §21.3`) — while still doing the real work for a real one, and auditing the ignored case so an operator can see a scan. `POST /auth/password-reset/confirm` spends a single-use, time-limited token (default 30 minutes, `PASSWORD_RESET_TTL_MINUTES`). `password_resets` stores only the SHA-256 of the token, exactly like `refresh_tokens` (ADR-26), so a database read never yields a usable credential; requesting a new link revokes any earlier unused one, so a forwarded older mail stops working. Spending a token **revokes every live refresh token** for that account: a reset is what someone does when they fear the account is not theirs alone, so leaving old sessions alive would defeat it. Both routes sit behind the existing auth throttler.
**Consequences.** The product can recover an account today, with the provider decision (O-3) still genuinely open and now costing one class plus one config value rather than a redesign. Nothing is emailed in any environment yet — the link is readable by whoever runs the server, and by nobody else; that is a development transport, not a shipping one, and `IMPLEMENTATION_STATUS.md` says so. Verified: 5 e2e cases over real HTTP and real Postgres — identical answers for a known and an unknown address, a second request revoking the first link, the full spend (new password works, old fails, pre-reset refresh token dead, token unusable twice), an expired link refused, and a too-short password refused by the same rule sign-up uses.
**Addendum (2026-09-04, A-17, owner decision O-3 = Resend).** `MAIL_TRANSPORT=resend` is the second adapter; `log` stays the default, so local development and the test suite still send nothing. It refuses to boot without `RESEND_API_KEY` and `MAIL_FROM_ADDRESS` — a transport that accepts a reset request, answers the required 202 and silently sends nothing forever is worse than one that will not start. Two behaviours the SDK forced: Resend reports a rejected send in the response's `error` field rather than by throwing, so a caller that only caught exceptions would count every bounce as a delivery — the adapter checks `error` and throws; and nothing but recipient and subject reaches the log, because the body of this particular mail is a working password-reset link. Covered by 11 unit tests against a stub client — no key, no network. Not yet usable in practice: the `kolme.app` domain still needs its SPF/DKIM records in Cloudflare (board C-20), and the owner creates the Resend account and key themselves.
**Revisit when.** The reset mail needs to be more than plain text, or a second kind of mail (recommendation digests, `email_recommendations` in PRIVACY.md §3) makes a template layer worth having.

## ADR-86 — First-party analytics behind the consent that already exists, observability behind unset flags (ALPHA_PLAN 7.5)

**Context.** `ALPHA_PLAN` 7.5 asks for the onboarding funnel, triad timing and click/watch counts, plus OpenTelemetry and Sentry. `BP §13` requires the product analytics to be first-party — a table in this database, not a third-party pixel — and `PRIVACY.md §3` already reserves the purpose `analytics_first_party`, which nothing read.
**Decision.** `analytics_events` holds one row per event: a closed `AnalyticsEventName` union (ten names), a `properties` jsonb that keeps only finite numbers, booleans and tags of at most 32 characters (at most 12 keys), and `profileId` with `ON DELETE SET NULL` — the tombstone shape consents and privacy_requests use (ADR-80), so deleting a profile does not rewrite the funnel counts. `AnalyticsService.record()` writes nothing unless that profile's latest `analytics_first_party` consent is granted and un-revoked; it never throws, because analytics that can fail a rank is worse than no analytics. What the server can measure it measures itself — `triad_answered`'s duration comes from the row's own `shownAt`/`answeredAt`, never from the client, and is **omitted** rather than zeroed when the round was never marked shown (ADR-19). `POST /profiles/:id/analytics/events` accepts only what the server cannot see (which onboarding step, which card opened), always answers `202`, and clamps a client's `occurredAt` to a 7-day backdating window. OpenTelemetry and Sentry start only when `OTEL_EXPORTER_OTLP_ENDPOINT` / `SENTRY_DSN` are set, and their packages were deliberately **not** dependencies while hosting was undecided (ADR-24); ADR-88 settled that and they are installed now (see the addendum below), still loaded by a dynamic import inside the enable branch and a missing package logs what to install instead of failing the boot. `sendDefaultPii: false`.
**Consequences.** The funnel is measurable without a third party, and a user who has not opted in leaves no row — verified over real HTTP: nothing written before the grant, written after it, nothing again after revocation, an unknown event name refused with 400, an object property stripped, and another user's profile silently ignored. The cost is that "how many people finished onboarding" is now "how many *consenting* people finished onboarding", which is the honest number and must be read as such. Tracing stays unmeasured until someone installs the two SDKs and points them somewhere.
**Addendum (2026-09-04, A-15).** The SDKs are installed: `@sentry/node`, `@opentelemetry/sdk-node`, `@opentelemetry/auto-instrumentations-node`, `@opentelemetry/exporter-trace-otlp-http`. Still nothing runs unless `SENTRY_DSN` / `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and the import stays inside the enable branch — a tracing SDK that patches `http`, `pg` and `dns` should not be loaded into a process told not to trace. Two things the real SDKs made necessary: `instrumentation-fs` is turned off, because a span per file read drowns the request traces this exists to show; and `Sentry.init()` **does not throw on a DSN it cannot parse** — it prints `Invalid Sentry Dsn`, builds a client anyway, and silently sends nothing, so the return value is taken from `getClient()?.getDsn()` rather than from init returning. Reporting "enabled" while nothing would ever be sent is precisely the failure a monitoring setup must not have. Verified by booting the backend against a stub OTLP collector on 4318: two real span batches (37 KB) arrived from `/api/health` traffic; with the variables unset the boot log mentions neither SDK.
**Revisit when.** Sampling at 100% costs too much (`OTEL_TRACES_SAMPLE_RATE` is already the knob), or logs and metrics are wanted alongside traces (this exports traces only), a new event is genuinely needed (extend the union — deliberately not a free-form name), or `§16` wants an aggregate the row shape cannot answer.

## ADR-87 — The training trigger fires after the commit, not inside it (fixes ADR-25's trigger)

**Context.** `TriadCompletedSubscriber` (ADR-25) noticed a triad turning `completed` in `afterUpdate` and scheduled `TrainingService.onTriadCompleted()` with `setImmediate`, on the stated assumption that the next tick came after the writing transaction returned. It does not: `afterUpdate` fires *inside* that transaction, and the count `onTriadCompleted` issues runs on a different pooled connection that cannot see the uncommitted row. The count therefore came back one short — the third round counted as the second, `shouldTrainAt` said no, and **no training was ever triggered automatically**. It passed for months only because the tmpfs test container committed faster than the next tick arrived; moving the test database to a disk-backed server (board C-17) lost that race every time and exposed it. Diagnosed by instrumenting the subscriber: three completed rounds, counts of 1, 1, 2.
**Decision.** `afterUpdate` only *notes* the profile id, in a map keyed by `event.queryRunner` so concurrent requests cannot flush each other's rounds; `afterTransactionCommit` reads the note and fires the trigger, after the row is visible to every connection. `afterTransactionRollback` drops the note, so a round that never happened is never trained on. The trigger stays detached from the request — the response still does not wait on the model service, and a failure is still logged, never thrown.
**Consequences.** Automatic training now actually happens, on a real database, at the round the threshold names. The e2e that was meant to prove this passed on a timing accident before, so it proved nothing; it now passes on the slow database it had never passed on, three runs in a row, and nine unit tests pin the shape (nothing before commit, once per profile per transaction, per-runner isolation, rollback forgotten, no double-fire). Worth reading twice: a green test on a fast fixture can be green for the wrong reason.
**Revisit when.** The trigger needs to survive a process restart between commit and call — that needs an outbox row, not a subscriber.

## ADR-89 — Rate limit keyed by user identity, by address only when anonymous (ALPHA_PLAN 7.6, board A-10)

Recorded after the fact (`42830a3`; flagged as undocumented by AUDIT_2026-09-05 §4).

**Context.** The app-wide `ThrottlerModule` limit (`THROTTLE_LIMIT`/`THROTTLE_TTL_MS`, 60 per minute by default) was keyed per IP: a household, campus or carrier NAT shared one bucket between unrelated users, while one account rotating addresses got a fresh bucket each time.
**Decision.** `IdentityThrottlerGuard`, the global `APP_GUARD`, keys the bucket on the JWT `sub` when the request carries a valid access token and on the client address otherwise, namespaced (`user:`/`ip:`) so the two can never collide. It verifies the token's signature itself rather than reading `req.user`: a global guard runs before the route's `JwtAuthGuard`, and an unverified `sub` could be re-rolled on every request and never counted. The per-route auth throttles (login, register, password reset — ADR-26) are unchanged.
**Consequences.** A rejected or expired token falls back to the address bucket, so no caller escapes a limit by sending a token the app rejects anyway. One extra signature verification per authenticated request. `src/perf/load-test.ts` drives the real journey and counts 429s apart from 5xx (150 users × 30 triads, 0 failures, `42830a3`).
**Revisit when.** Limits need to differ by plan or by route family, or the throttler moves to a shared store (Redis) for multi-instance deploys.

## ADR-90 — The catalog ships with the schema: `npm run release` = migrations + seed + everything derived from it (owner rule 2026-09-05)

**Context.** `kolme.app` went live on 2026-09-04 with an empty `titles` table: the deploy ran migrations only, `seed:demo` was a dev tool that also creates the `@demo.local` personas, and the backend image shipped `dist` without the fixture. Every user saw "no results" on the discover screen. Owner's rule: the seed and all it produces are part of the deployment, never a separate manual step.
**Decision.** The Railway migrate service and the compose `migrate` profile run `npm run release` = `node dist/migrate.js`, one process (`migrate:prod`, the name the live service already calls, is the same entry): pending migrations, then `seed-demo --catalog-only` (titles + `content_features` provenance, upsert by `internalId`; no persona accounts — their password is public in the repo), then the `load-catalog-rights` and `load-imdb-ratings --fetch` passes, in-process. The runtime image carries `catalog.demo.json`/`personas.demo.json` beside `dist/scripts`. Every step is idempotent, so the service runs on every push (Railway auto-deploy).
**Consequences.** The committed fixture is the catalog's source of truth in every environment: a title edited only in a production row is overwritten by the next release (corrections go through the fixture; provenance corrections through supersede rows, BP §11.3). A release depends on `datasets.imdbws.com` being reachable and fails loudly otherwise, rather than shipping a catalog without Public Quality. Found live: the Railway services have **no** config-as-code path set (Railway deprecated it, sunset 2026-12-01), so the start command lives in the service's Deploy settings and `railway.migrate.json` is the reference copy, not what runs — which is why the release hangs off the entry point that command already names rather than a new script the dashboard would have to learn.
**Addendum (2026-09-05, same day).** Railway's pre-deploy command exists, so the release moved onto `backend` itself: `npm run release --workspace=@movie/backend` runs in the new image before each deployment and a failure stops the deploy — which also closes the push-time race between two parallel deploys. The separate migrate service (`pure-cooperation`) was deleted from Railway the same day, on the owner's order, and `railway.migrate.json` is gone; the compose `migrate` profile stays for self-hosting. Found live: `backend` is built by Railpack from the workspace, not by the Dockerfile, so the fixture is read from `src/scripts/fixtures` there (the Dockerfile copy serves the compose path).
**Revisit when.** The catalog gets an editor in production, or the fixture outgrows the image.

## ADR-91 — Constraint names follow one convention, derived by a naming strategy (AUDIT_2026-09-05 follow-up)

**Context.** Every migration since M1 named its foreign keys `FK_<table>_<column>` by hand, while TypeORM's default derives a hash from table and columns. The entities therefore expected different names from the ones the database carries, and `schema:log` proposed dropping and recreating 35 foreign keys on every run -- noise that hid the two real drifts beside it (`outcomes.occurredAt`'s default, the `recommendations` index shape). Seven constraints from `InitialSchema` still carried hashes that no longer even matched TypeORM's own derivation, because M1 renamed `user_title_state` to `user_title_states`.
**Decision.** `ConventionNamingStrategy` (`config/naming-strategy.ts`) makes `FK_<table>_<column>` the derived name on every DataSource built from `getConnectionOptions()`; unique constraints, indexes and primary keys keep TypeORM's defaults, and the hand-named ones are declared explicitly on their entities. Migration `RenameLegacyConstraintsToConvention` renames the seven legacy constraints (catalog-only, reversible). The check is `npm run typeorm -- schema:log` against a migrated database: it must print no statements, and a future `migration:generate` produces convention names without anyone typing `foreignKeyConstraintName`.
**Consequences.** Entities are again a truthful description of the schema, so drift is visible the moment it appears. Renaming constraints changes nothing about behaviour or data; a rollback restores the hashes.
**Revisit when.** A second schema or database engine needs different naming, or TypeORM's schema comparison starts modelling index sort direction (the `recommendations` index's `DESC` lives in the migration only).

## ADR-92 — Below the 5-triad floor, the strongest regularization serves (owner decision H5, 2026-09-05)

**Context.** `training.py` picks the L2 strength per run from `REGULARIZATION_GRID` by held-out NLL (RANKING_ALGORITHM §2/§6), but below the 5-triad floor there is no held-out slice, and the fallback was the grid's *weakest* entry. A profile with 1-4 triads fitting a 40-dimensional weight vector is the most underdetermined case in the pipeline, and it was getting the loosest shrinkage of any regime -- served unconditionally, since the serving fit runs regardless (AUDIT_2026-09-05 H5). The two pairwise-accuracy numbers were already made comparable for exactly this near-zero-weight regime (ADR-84 addendum, M2).
**Decision.** Below the floor the fallback is `REGULARIZATION_GRID[-1]`, the strongest value; at or above it the grid search is unchanged. "No information to select a regularization" argues for more caution, not less.
**Consequences.** Early models shrink harder toward zero: relative order still drives recommendations, the confidence band was already capped at `initial` there, and a held-out slice takes over from the fifth triad on. No schema or API change; `chosen_regularization` is persisted as before.
**Revisit when.** `§16` measures early-round recommendation quality, or the grid itself is retuned (a wider grid could make "strongest" too strong for 4 triads).

## ADR-95 — Mail leaves through a generic SMTP adapter, not a vendor SDK (owner review of external dependencies, 2026-09-05) — **partially superseded by ADR-97 (2026-09-05): the Resend transport is back, over HTTPS**

**Context.** ADR-85's second transport was `ResendMailer` over the Resend SDK: one npm package and one adapter written to one vendor's response shape, for the single mail this product sends (the password-reset link). The owner's review asked which external dependencies an internal, easily verified piece could replace. A self-hosted mail server is not that piece — deliverability, IP reputation and SPF/DKIM/DMARC upkeep are a full-time burden for one mail — but the *SDK* is: every provider, Resend included, accepts the same SMTP session.
**Decision.** `MAIL_TRANSPORT=smtp` with `SmtpMailer` over nodemailer (zero dependencies, bundled types). `SMTP_HOST` and `MAIL_FROM_ADDRESS` are required at boot, `SMTP_USER`/`SMTP_PASSWORD` come together or not at all, `SMTP_PORT` defaults to 587; 465 selects implicit TLS, and whenever credentials are configured nodemailer is told `requireTLS`, so a server that will not STARTTLS gets no password. A send whose recipient the server rejected (nodemailer resolves, with the address under `rejected`) throws, as the Resend adapter did for its `error` field, and no log line ever carries a credential or the body. The `resend` package and transport name are gone; `MAIL_TRANSPORT=resend` fails at boot with a message that names `smtp`. O-3 stands: Resend is reached as `smtp.resend.com:465`, user `resend`, password = its API key.
**Consequences.** One dependency fewer, and the provider is a variables change with no code path per vendor; the prod compose gains `SMTP_*` and an `smtp_password` secret. 21 unit tests against a stub transport — no server, no network. Still nothing is emailed in any environment (`log` everywhere) until the owner sets the variables and board C-20's DNS records exist.
**Revisit when.** A second kind of mail makes templates or a provider's tracking/webhook features worth an SDK again, or the sending volume needs a queue (`BP §12.3`).

## ADR-97 — Mail: delivery rented behind an owned seam, a Postgres outbox, no `log` in production (owner decision 2026-09-05; partially supersedes ADR-95)

**Context.** ADR-95 dropped the Resend adapter for a generic SMTP one while the Railway backend was set to `resend`, so the next deploy refused to boot (~06:30, hotfix `f9eedd4`). The owner then ruled on mail as a category: no self-run mail server (IP reputation, bounces, SPF/DKIM/DMARC are a full-time burden for one message), no SMTP from Railway (outbound SMTP is Pro-only; Free/Hobby must use an HTTPS API), and everything else owned — templates, tokens, retries, status — behind the `Mailer` seam, so the provider is one adapter and one variable.
**Decision.** Three transports: `resend` as one HTTPS POST with an `Idempotency-Key` (no SDK), `smtp` for the VPS path, `log` for development only — refused when `NODE_ENV=production`. Every message is a `mail_outbox` row first (ADR-91 names, cascades with the account): `enqueue()` attempts at once, a failure is retried by a sweep (`MAIL_OUTBOX_SWEEP_INTERVAL_MS`, default 30 s) with backoff 30 s → 32 min over 8 attempts and never past the message's `expiresAt` (a reset link's TTL); the body rests only sealed (AES-256-GCM under an HKDF subkey of `JWT_SECRET`) and is wiped when the row leaves `pending`, so ADR-85's "a database read never yields a credential" still holds; delivered and dead rows purge after 7 days; `GET /admin/mail-outbox` shows status without address or body. Password reset audits `ok` / `scheduled` / `failed` and revokes the token only when the row is dead or could not be written.
**Consequences.** No provider SDK; a provider blip costs a delay, not a lost reset; an operator sees every message's state. New boot rule in production: `MAIL_TRANSPORT` must be `resend` or `smtp` with its variables — the kind of change the incident rule says is announced on the board before the push. Verified on stubs: 33 mailer, 9 outbox and 5 cipher unit tests; password-reset unit and e2e suites; migration applied to dev and test databases.
**Revisit when.** A second mail kind wants templates, a second replica needs a row claim (`SKIP LOCKED`), or a provider's webhooks or tracking are worth an SDK.

## ADR-99 — A completed *set* of three is never re-asked as new evidence (remediation brief P0-04, revises ADR-34)

**Context.** The live round of 2026-09-05 got round 2's exact three films back in round 4, ranked identically, and it counted as a fresh piece of evidence toward the training threshold. ADR-34's one-triad lookback (excluding only the immediately-previous triad's titles) fixed a worse bug -- a title could enter at most one triad ever -- but with a small watched pool it lets an older set reappear with no signal that it is a repeat, inflating both `completedTriads` and the trainer's evidence count. `BP §8.1` still names re-testing a past comparison ("verification/refutation in an independent context") as one of six legitimate triad functions, so the fix is to label the repeat, not forbid it.
**Decision.** `triads` gains `setHash` (md5 of the three title ids sorted and joined, identical for every display permutation; `modules/triads/triad-set.ts`, backfilled by `AddTriadSetHashAndPurpose`), `purpose` (`'learn' | 'verify'`) and `countsTowardActivation`. `getCurrent()` draws a `learn` set from the watched pool minus the previous triad's titles (ADR-34's exclusion, unchanged) that is not one of the profile's already-completed sets; only when every set that pool can make is already completed does it draw one anyway, labelled `verify`, `countsTowardActivation: false` -- still from that same fatigue-excluded pool, so a verify round is never the triad that was *just* completed. `replace()` applies the same rule when it swaps an item. `TrainingService.countCompleted` and the trainer's `TRAINABLE_TRIAD_PREDICATE` both filter on `learn`/`countsTowardActivation`, so a verify round advances neither the automatic-training threshold nor the model fit. The adaptive policy (`TriadPolicyService`) takes the same completed-set exclusion and never proposes a verify round itself, falling back to the random policy (now `random-v2`) when its own pool is exhausted.
**Consequences.** A profile with a small watched pool sees more `verify` rounds sooner -- expected, not a regression: it is exactly the signal that the catalog needs more titles the user has watched. `training.e2e-spec.ts` and `full-journey.e2e-spec.ts` moved from 6 to 9 watched titles: with exactly 6, round 3 deterministically lands on round 1's set (the two halves of 6 alternate), which is now correctly `verify` and no longer trips the third-round trigger by itself. `triad-rank.e2e-spec.ts`'s repeat test is unaffected -- it only asserted the *titles* repeat, which they still do.
**Revisit when.** A `bridge`/`boundary`/`explore` purpose is added (`BP §8.1`) and needs its own activation rule, or `countsTowardActivation` needs to vary independently of `purpose`.

## ADR-100 — A durable `training_jobs` queue owns retries, backoff and readiness (remediation brief P0-02)

**Context.** The model service's own job ledger (ADR-25, `JobStore` in `services/workers/src/model_service.py`) is explicitly in-memory: its own docstring names "a restart forgets queued jobs" as a deliberate Alpha limit. `TrainingService` called it directly on every status poll and every dispatch, so a redeploy of that one Python process silently lost whatever it was tracking, with nothing durable noticing. The brief's live round also found no operational answer to "can training plausibly succeed right now" beyond reading logs, and no admin surface for a failing job beyond the per-profile status route.
**Decision.** `training_jobs` (Postgres, `TrainingJobsService`) mirrors the mail outbox's proven shape (ADR-97) instead of inventing a second retry mechanism: `enqueue()` writes a row and dispatches to the model service at once (a partial unique index on `profileId` where status is `queued`/`running` is the idempotency guarantee), a periodic sweep polls every `running` row and dispatches every due `queued` one, and a transient failure (`errorKind: 'error'`, including the model service having forgotten the job entirely) schedules a backoff retry up to `MAX_ATTEMPTS`; a deterministic one (`errorKind: 'invalid'` -- nothing trainable yet) fails permanently on the first attempt, since retrying changes nothing until the data does. `TrainingService` no longer calls the model service directly for job lifecycle at all -- `status()`/`summarize()` read the durable row, so a model-service blip costs the next sweep tick, never the request in front of a user (`state: 'unknown'` is consequently unreachable now). Every stored error is sanitized (connection strings, bearer tokens, filesystem paths stripped, truncated to 500 chars) before it can reach the frontend or the admin board. `GET /admin/training-jobs` exposes counts and recent rows (pseudonymous profile ids only, same shape as `GET /admin/mail-outbox`); `GET /admin/readiness` answers the brief's literal question -- database reachable, catalog size against `CATALOG_MIN_TITLES` (200, the Phase 0 floor), fingerprint coverage against a 50% floor, and a live model-service `/health` ping -- for the admin board, never the hot path.
**Consequences.** "The last successful model stays served when a new training run fails" needed no new code: `user_model_snapshots` is already append-only and `RecommendationsService` already serves the latest one, so a failed job simply writes nothing. `training.e2e-spec.ts`/`full-journey.e2e-spec.ts`'s dispatched-but-not-yet-computed state is now `running` (this class's own tracking state), not the model service's own `queued` sub-state -- proxying the latter would collide with this table's *own* "queued and due for a dispatch retry" meaning, redispatching a job the model service was already quietly working on. `AdminModule` now imports `TrainingModule` for `TrainingJobsService`/`ModelServiceClient`. Verified: 25 new unit tests (`TrainingJobsService`, `sanitizeError`, `AdminModelsService.readiness`/`trainingJobsSummary`), `training.service.spec.ts` rewritten against `TrainingJobsService` instead of live model-service mocks, full e2e suite green.
**Revisit when.** A second replica needs `SELECT ... FOR UPDATE SKIP LOCKED` on the sweep (today: `numReplicas: 1`, same assumption the mail outbox makes), or the model service gains a push/webhook so polling can go.

## ADR-101 — IMDb's dataset dump is out of the critical release path (P0-4, revises ADR-90)

**Context.** `npm run release` (ADR-90) runs `refreshImdbRatings({ fetch: true })` on every deploy, and `fetchDump()` wrote the download straight into the path future runs read from: a network drop mid-download truncated that file in place, destroying the last good ratings rather than merely failing to refresh them, and either way `refreshImdbRatings` threw, which `migrate.ts` let fail the whole release -- a schema migration and the catalog reseed blocked by `datasets.imdbws.com` being unreachable. Railway's filesystem is also ephemeral outside a mounted volume, so a fresh container has no previous dump to fall back to at all.
**Decision.** `fetchDumpAtomic()` downloads to `<target>.part`, runs `validateDump()` against it (gzip integrity, the expected `tconst/averageRating/numVotes` header, a byte-size and row-count floor sized for the real ~7 MB/1.5 M-row dump), and only then `renameSync`s it onto `target` -- atomic on the same filesystem, so a reader never sees a half-written file. A failed download or a dump that fails validation deletes the `.part` file and keeps whatever is already at `target`, returning `stale: true` (reported via `captureException`) instead of throwing; it rethrows only when there is no previous file at all. `migrate.ts` additionally wraps the whole IMDb step in a try/catch that logs and alerts but never fails the release -- migrations and the catalog seed are the critical path, IMDb ratings are not. A separate, non-corruption coverage check (matched/wanted ratio below 40% on a structurally valid dump) alerts without blocking, catching a format change IMDb makes without discarding good data over it.
**Consequences.** A release now completes even when IMDb's endpoint is down or serves garbage; ratings are simply stale (or absent, on a truly fresh volume) until the next successful pass -- the periodic in-app refresh (`public-quality-refresh.service.ts`, `IMDB_REFRESH_INTERVAL_HOURS`) or the next deploy. `LoadImdbRatingsSummary.stale` surfaces this in logs and to Sentry; nothing in the read path (`PublicQualityService`) changes. Verified: 11 unit tests on `validateDump`/`fetchDumpAtomic` against a stubbed `fetch` (truncated gzip, wrong header, undersized file, network throw, HTTP error, no-previous-file rethrow); existing `load-imdb-ratings.e2e-spec.ts` unaffected (its functions were not touched).
**Revisit when.** A persistent volume is mounted for `IMDB_DATASETS_DIR` in production (then "no previous file" stops being the common case on a fresh deploy), or a second dataset source needs the same atomic-download treatment.

## ADR-102 — Automated encrypted backups to R2, off the app's own credentials, with a scheduled restore drill (P0-5)

**Context.** `docker/backup-postgres.sh`/`restore-postgres.sh` (AUDIT_2026-09-05 H8/H9) both run through `docker compose exec`, which has no equivalent on Railway -- there is no host to exec into, and a `pg_dump` there would have to run as a Railway Cron job talking to Postgres over the network. Backups also had nowhere off-box to go: the only precedent (ADR-98) treated "a verified backup+restore drill" as a prerequisite the owner ran by hand before a risky change, not a standing schedule, and nothing existing separated backup storage from the credentials that could also delete it -- a compromised `DATABASE_URL`-holding process had no barrier between it and the backups meant to recover from it. O-8 provisioned a Cloudflare R2 bucket (`kolme-backups`, EU, private) and a scoped API token (Object Read & Write, that bucket only) for exactly this.
**Decision.** Two new scripts, plumbing-only (no Nest module, no new backend dependency): `backup-postgres-to-r2.sh` runs `pg_dump --format=custom` against `DATABASE_URL`, verifies the archive with `pg_restore --list` before doing anything else with it (same non-destructive check as H8's fix), encrypts it (`openssl enc -aes-256-cbc -pbkdf2`, key from `BACKUP_ENCRYPTION_KEY`, passed via `-pass env:` so it never appears in `ps`), writes a sha256 checksum alongside it, and uploads both to `s3://$R2_BUCKET/postgres/` over R2's S3-compatible API (`aws s3 cp --endpoint-url`). `restore-drill-from-r2.sh` downloads the newest (or a named) object, verifies its checksum and decrypts it, and restores it into `RESTORE_DRILL_DB` -- a disposable sibling database on the same server it drops and recreates every run (guarded against a handful of real database names by name) -- then queries it to prove the data is not just present in the archive's table of contents but actually restorable and queryable, and drops the drill database again. `docker/backup.Dockerfile` (`postgres:18-alpine` + `openssl`, `aws-cli`, `bash`; the client must be >= the server, and Railway's production Postgres is 18.6 -- see the correction in ADR-98) is what a Railway Cron service runs each script from (`docker/railway.backup.json`, reference-only like `apps/backend/railway.json` -- Railway Cron services are created by hand in the dashboard). Retention lives in the bucket itself, not in a script that has to remember to run it: `docker/r2-lifecycle-policy.json` + a one-time `configure-r2-retention.sh` (run once, by hand, with the real credentials, never by a Cron job) expires objects under `postgres/` after 30 days via R2's own S3 lifecycle API. "Alert on absence" is Railway's own Cron run-history and failure notifications (a dashboard setting, no code) rather than a third process holding the same write-capable R2 credential just to poll for freshness -- the app that serves traffic never needs object-storage write access at all, and the six variables named on the board (`R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET`/`R2_S3_ENDPOINT`/`BACKUP_ENCRYPTION_KEY`) stay the only ones this touches, all Shared Variables in Railway, none in this repository or in the backend's own runtime.
**Consequences.** A backup a compromised backend or database credential cannot reach or delete; a restore path proven weekly, not assumed; retention that survives even if the Cron job that would have applied it stops running. Verified locally against `moviedb_test` end to end -- dump, `pg_restore --list`, AES round-trip, decrypt, restore into a disposable database, `information_schema.tables` count, drop -- everything except the two `aws s3` calls themselves, which need the real R2 credentials only Railway holds; the first live run is the owner's or the coordinator's to trigger once the two Cron services exist.
**Revisit when.** A second database needs the same treatment, a `BP §12.3` trigger makes a managed Postgres with native PITR worth its cost, or Railway's Cron notifications prove insufficient and a dedicated freshness check becomes worth a third credential surface.

## ADR-103 — Four readiness capabilities, not one "trained or not" flag (remediation brief §5.1)

**Context.** `GET .../recommendations` and `GET .../training` each answered their own narrow question (can I show suggestions; is a job running), and nothing answered the brief's actual complaint: a user who ranked ten rounds saw one undifferentiated "still learning" with no way to tell whether the ranking of their *own* watched titles was ready, whether a taste profile existed, whether new-title suggestions specifically lacked candidates rather than a model, or whether availability data even exists. The brief's own capability table names four distinct questions with different data requirements -- a bare ordinal ranking needs no fingerprints at all, a semantic profile needs them or a documented fallback, a recommendation needs both a model *and* a non-empty candidate pool, and watchability needs a data source this product does not have yet (AVL-01).
**Decision.** `GET /profiles/:profileId/readiness` (`ProfileReadinessController`/`ProfileReadinessService`, `apps/backend/src/modules/recommendations/`) returns `{ ordinalModel, semanticProfile, recommendation, availability }`, each a `{ status, reason, action, publishedAt, modelVersion }` -- `status` one of `not_ready | eligible | queued | processing | ready | failed | stale` (the brief's own state machine), `reason`/`action` stable codes matching this API's existing structured-reason convention (`need_more_triads` and friends), never prose. It is composed, not computed twice: two small additions to `RecommendationsService` (`snapshotState()`, the same ready/pending/paused/model_outdated discriminator `findForProfile()` already computes internally, and `candidatePoolSize()`, the same candidate filter as a `COUNT` instead of the full scored pipeline) plus the existing `TrainingService.status()` are the only inputs; no new column, no new trainer output. `recommendation` mirrors `ordinalModel` exactly whenever the model itself is not ready (nothing to recommend from), and only diverges when the model is ready but the candidate pool is empty (`insufficient_eligible_candidates`) -- the two distinct reasons a user could see no suggestions the brief specifically asked to be told apart. `availability` is always `not_ready`/`no_availability_data_source` today, honestly, rather than fabricating a value AVL-01 has no source for yet; the shape is ready for when one lands.
**Consequences.** `semanticProfile` is, today, the *same* `CapabilityReadiness` value as `ordinalModel` -- one Plackett-Luce fit produces both a ranking and the weight vector this codebase calls the taste profile, and nothing currently reports per-triad fingerprint coverage as its own signal. Giving them genuinely independent values would need the trainer itself to report that coverage, which is real future work, not something this contract can honestly claim without it (the exact anti-pattern §11 of the brief forbids: treating a missing distinction as a zero). **Consumed since 2026-09-05** by `ReadinessPanel` in `ProfileScreen`'s model section (movie-p1): the four capabilities with a status, the reason, and what is required of the user, each rendered from client-side copy keyed by the stable codes -- an unrecognised code renders as nothing rather than leaking `insufficient_triads` onto the screen. The panel sits beside the existing model block rather than replacing it. On the home screen, `RecommendationsScreen` now derives its pending situation from `recommendation` first and from the training state only for what readiness cannot express (a job that succeeded without publishing versus a service that could not be reached — both arrive as `model_service_error`); a failed readiness read falls back to the old inference rather than losing an explanation. That is what put `insufficient_eligible_candidates` on screen: a ready model with an empty pool used to render as an empty list. 9 new unit tests for the service's state mapping (every branch: disabled, paused, idle above/below threshold, queued, running, both failure kinds, stale, ready-with-and-without candidates), 4 for the two `RecommendationsService` additions.
**Revisit when.** The trainer reports fingerprint coverage per fit (then `semanticProfile` earns its own, lower status when coverage is thin but the ordinal ranking is otherwise fine) or a real availability data source exists (AVL-01) -- and whenever a screen is redesigned to read this contract instead of `getTrainingStatus`/`getRecommendations` directly.

## ADR-104 — The watched date is a plain string the client supplies, never a timestamp the server guesses (remediation brief P1-03/DATE-01)

**Context.** The live round of 2026-09-05 found two related bugs in `user_title_states.watchedAt` (a `timestamp`): a title marked watched showed the previous day, and editing a diary note alone silently moved the displayed date. Both traced to the same design: `watchedAt` stored the server's UTC "now" (wrong for anyone east of UTC acting just after their own local midnight -- Riyadh is the primary market, UTC+3), and the frontend's diary always resent a value reconstructed via `new Date(`${date}T12:00:00`).toISOString()` regardless of whether the date field was touched, so a notes-only save could still shift the stored instant depending on the *viewer's own* browser timezone at save time.
**Decision.** `user_title_states` gains `watchedOn`: plain `'YYYY-MM-DD'` text, deliberately never a native `date`/`timestamp` column -- the bug was exactly a timestamp/timezone being interpreted differently by different code, and a bare string sidesteps the entire class by construction. The backend only ever stores what it is given, verbatim (`UpdateTitleStateDto.watchedOn`, `@Matches(/^\d{4}-\d{2}-\d{2}$/)`); it never derives a day from its own clock. Every frontend call that marks a title watched *now* (`ListScreen`, `RecommendationsScreen`, `DiscoverScreen`, `WorkScreen`) sends `lib/format.ts`'s new `todayLocal()` -- the device's own wall-clock day, computed from `Date`'s local getters, never `toISOString()`. The diary sends its date input's value unchanged; PATCH semantics extend to it (omitting `watchedOn` leaves an already-set day alone, exactly like `notes`), which is what stops a notes-only save from moving the date. Display goes through a new `formatWatchedOn()`, pinned to `timeZone: 'UTC'` when rendering the bare string -- the day a fact happened does not change with who is later looking at it, unlike `formatDate` (kept, unchanged, for real instants: consent timestamps, document revision dates). `watchedAt` stays, demoted to legacy bookkeeping only; nothing reads it for display any more. Migration backfills `watchedOn` from `watchedAt`'s UTC date for existing rows -- an acknowledged approximation, since a user's actual local day cannot be recovered from a bare UTC timestamp after the fact.
**Consequences.** `WatchEventsService.create()`'s own call into the same PATCH path derives `watchedOn` from its own `watchedAt` input's UTC date (the closest thing to a chosen day that path has; the frontend does not call it today). `docs/REMEDIATION_MAP_2026-09-05.md`'s queue item 4 (DATE-01) closes. Not done here: `seed-demo.ts`'s persona fixtures still only set the legacy `watchedAt` (out of this session's registered files; their library screens show no date until backfilled or re-seeded).
**Revisit when.** A profile-level IANA timezone is added (`BP` leaves this open) and "today" should be computed from it server-side too, for a client that cannot be trusted to report its own clock correctly (a very old cached PWA build, a manipulated clock).

## ADR-105 — The move to EU-West is a backup-restore cutover, not a database edit (owner decision O-11, 2026-09-05)

**Context.** The four Railway services were provisioned in **US East (Virginia)**, while QUICKSTART §8.2, ADR-88 and the privacy notice all told users the data lives in the EU. Twelve real users and a 300-title catalog is the smallest this data will ever be, so the honest fix is to move rather than to rewrite the promise (owner decision O-11, option (b), 2026-09-05 08:05).
**Decision.** The move reuses the P0-5 path already proven in production rather than any new mechanism: the daily encrypted `pg_dump` in R2 is the transport, and `docker/restore-into-target-from-r2.sh` — the drill script aimed at a real, empty target instead of a disposable sibling — is the restore. It writes only to `TARGET_DATABASE_URL`, refuses a target that already has tables (`ALLOW_NONEMPTY_TARGET` to override), never drops anything, and prints row counts to compare against the source before the switch. `SKIP_EXTENSIONS=vector` leaves the unused `vector` extension (ADR-2/ADR-57) out of the restore when the target's image does not ship it, by filtering the archive's table of contents — the dump itself is never edited. Order: fresh backup → new **PG 18** Postgres in EU-West with its own Volume → restore → compare counts → announced downtime window → `DATABASE_URL` switched on `backend` and `model-service` → the other services and both Cron services moved → docs and the privacy notice corrected. The old database is **kept for a week** after verification and deleted only by the owner.
**Consequences.** The cutover is a short announced outage, not a live replication; anything written during the window is lost, so the window is taken when the app is idle and the final backup is the one restored. Verified end to end before any production step: an encrypted dump of the PG 15 dev database restored into a throwaway PG 18 server (33 tables, 300 titles, 12 users, 33 migration rows), and the non-empty guard refused the second run. The version gap between dev/CI (PG 15, ADR-98) and production (PG 18.6) is unchanged by this and stays a separate decision.
**Executed (2026-09-05).** New `Postgres-eu` (Railway `postgres-ssl:18` template, EU West/Amsterdam, own Volume); the 05:37 UTC backup restored into it (33 tables, 384 titles); `DATABASE_URL` switched on `backend` and `model-service` at 05:48 UTC (`/api/health` 200 throughout, `catalog.titles` 384); the remaining services and both Cron services moved to EU West by 07:10 UTC with one ~25s gap while the backend's Volume moved. Times are UTC (the cutover was run and first reported in GMT+3). No write was blocked during the switch, so the eleven minutes between the restored snapshot and the switch is the window in which a write could have landed in the old database only -- checked against it before it is deleted. The old database stays a week and is the owner's to delete.
**Revisit when.** Railway offers a Middle East region (latency, not residency, would be the driver), or the data grows past what a dump-and-restore window can carry.

## ADR-106 — Catalogue search folds both sides and reads alternate titles from `localized_titles` (remediation brief P1-01/SEARCH-01)

**Context.** The brief's evidence was «Anora» returning nothing where «أنورا» returned one row. The map could not reproduce it from the code (`ILIKE` is case-insensitive), which is the real finding: there was no fixed set of queries with known answers, so nobody could say what search did. Three gaps were real: Latin diacritics were matched byte for byte («Amelie» missed «Amélie»), the Arabic fold stripped tashkeel and tatweel from the *query* only, so a title stored as «الرِّسالة» or «الــبلبل» was unreachable, and `localized_titles` — the table SCHEMA.md §2.2 created for alternate titles, and ADR-2 named as the search target — was never read.
**Decision.** One predicate, all four sources: `titleEn`/`titleAr` by `ILIKE`; `titleAr` folded on both sides, now with `translate(col, ARABIC_STRIP, '')` removing tashkeel, shadda, the dagger alef and tatweel from the column exactly as `foldArabic()` removes them from the query; `unaccent(titleEn)` for the Latin half; and an `EXISTS` over `localized_titles` with the same folding, so one query reaches the original-language title, an official title in another market, and a transliteration. `EXISTS`, not a join: a film with ten alternates is still one result. The `unaccent` migration is deliberately non-fatal and `TitlesService` probes `pg_extension` once — a deployment whose role cannot install a contrib extension boots and searches accent-sensitively rather than failing (boot contract, incident `f23ec48`).
**Consequences.** `test/titles-search-golden.e2e-spec.ts` is the golden set the brief asked for: 53 pinned cases over real HTTP and real Postgres — the other language, the wrong hamza, the missing accent, the wrong case, a fragment, and the name a film is known by elsewhere. It found the two folding bugs above, which no unit test could (the fold lives in SQL). Nothing populates `localized_titles` yet: the search path and its contract are proven by the test, and the ingestion of alternate titles belongs to the catalogue pipeline (SEARCH-01 follow-up), not here. No index is used for the folded or unaccented comparisons; at 384 titles this is a sequential scan by design, and the GIN FTS index the table already carries is the escape hatch when the catalogue is large enough to need it.
**Revisit when.** The catalogue passes roughly ten thousand titles (then the folded expressions need their own immutable-wrapper indexes, or the FTS index takes over), or alternate-title ingestion lands and ranking between a primary and an alternate match starts to matter.

## ADR-108 — The onboarding round tells the truth about what it is worth (P0-8)

**Context.** Three claims on the ranking path were not true. `GET .../triads/current` answered `needed: 1` whenever resting the previous round's titles left fewer than three, whatever the profile actually had — a hard-coded number presented as a count. That same rule turned a profile with exactly three watched films into a permanent wall: its only set was always "just used", so it was told to mark another film for ever. And `RankScreen` kept its own tally — every completed row, `verify` repeats included, plus an optimistic +1 on save — so the live round of 2026-09-05 read "ten completed rounds" to a profile the backend counted as having one piece of evidence (ADR-99 already excluded repeats from activation; only the screen still added them up).
**Decision.** `needed` is the real remainder, `3 - watched`, and is returned only for the one state that blocks a round: fewer than three watched films. Fatigue becomes a preference, not a ban — the previous round's titles are rested when the profile has other films and drawn from when it does not, in which case the round is labelled `verify` and counts toward nothing, exactly as ADR-99 defines. The server reports `learningRounds` and `verificationRounds` apart, on `GET .../training` and inside `GET .../readiness`, and every threshold (`nextTrainingAt`, activation) reads the learning count alone; `completedTriads` stays as an alias of `learningRounds` so existing readers do not break. `GET .../readiness` also carries `rounds` — the two counts, `firstTrainingAt`, `nextTrainingAt`, the `triadEligible` `watchedTitles` the rounds are drawn from, and `suggestedWatchedTitles: 9`. `RankScreen` keeps no tally of its own and reads that block.
**Rationale.** Three watched films make exactly *one* distinct triad; nine make eighty-four. The number is a property of C(n,3), not a tuning knob, which is why nine is a constant in the readiness contract and not configuration. "Three is enough to start" stays the promise on the blocked screen — the ask for seven to nine is progressive, two films at a time, and only after ranking has begun.
**Consequences.** A repeat round is now visible as a repeat ("and six repeat rounds, which count for nothing: the same films again") rather than inflating a counter. A three-film profile keeps ranking instead of hitting a wall, and is told what would make the next round new. ADR-34's H1 case ("mark another film", never "mark three") is superseded: it described a state that no longer exists.
**Revisit when.** A purpose beyond `learn`/`verify` (bridge, boundary, explore — ADR-99's own revisit trigger) needs a third count, or the trainer starts weighting a verify round's agreement with the model as evidence of its own.

## ADR-109 — The training queue leases its rows and reconciles the profiles it lost (P0-9)

**Context.** ADR-100 made the queue durable but not self-healing. Three holes were left. A row could stay `running` for ever: `poll()` returned immediately when `modelServiceJobId` was null (the state a crash between dispatch and the recorded id leaves), and a model service that answered "running" for ever was believed for ever. Nothing prevented double execution across processes: the only guard was an in-process `sweeping` flag, so a second replica -- or the Railway Cron the queue is heading for -- would dispatch the same `queued` row and fit the same profile twice. And a profile whose enqueue was lost (the model service unreachable when the round was ranked, or training switched on afterwards) waited for its next completed round to land exactly on a threshold, which for a profile that stopped ranking because nothing appeared never comes.
**Decision.** Claiming a row is a lease, taken with one statement -- `UPDATE training_jobs SET status='running', attempts=attempts+1, startedAt=now WHERE id=? AND status='queued'` -- and only the worker whose update affected a row dispatches it. The lease expires after ten minutes: a row still `running` past it goes back to the queue through the ordinary backoff, so it either succeeds later or fails visibly after `MAX_ATTEMPTS`. A reconciler runs each sweep and enqueues profiles that qualify, have no job row at all and have no snapshot, excluding paused ones; a profile that has a `failed` row is left alone, because a failure is the operator's to see rather than something to loop on. Every catch in the sweep now reports through `captureException` and no longer takes the tick down with it. No transactional outbox: the enqueue and the ranking write are not the same transaction, and the reconciler is the cheaper answer to the same gap.
**Rationale.** All three are the same fix -- state that only one actor may own, for a bounded time, with a way back. The lease needs no new column: `status` is the lock and `startedAt` its stamp, so this ships without a migration (boot contract, incident `f23ec48`).
**Consequences.** `startedAt` now means "when the current attempt was claimed", not "when the row was first tried" (`createdAt` is that). `runDue()` reports a fourth number, `reconciled`. The reconciler's predicate is SQL over three tables, so it is proven in `test/training.e2e-spec.ts` against real Postgres, not against the in-memory fake.
**Revisit when.** A second replica sweeps concurrently often enough that `SELECT ... FOR UPDATE SKIP LOCKED` beats one conditional update per row, or the model service starts pushing job completions instead of being polled.

## ADR-110 — A recommendation is a row the client can name, and being shown is its own event (P0-10)

**Context.** The feedback loop existed on paper and was unreachable in practice. `POST /recommendations/:id/outcome` (ADR-67) has taken `clicked`/`saved`/`dismissed_not_relevant` since 2026-09-03, but the API never told the client which row a card was, so no screen could ever call it; the recommendations screen's "watched" wrote a bare state PATCH, so `WatchEventsService` -- the one place that closes BP §4.5's loop -- was never reached from the product at all; and there was no control for "this suggestion missed", which is the only signal a silence cannot supply. Meanwhile every request stamped every row `shownAt`, including the rows behind a collapsed track and including ProfileScreen's one-item request, made purely to read a confidence band off an item it then threw away.
**Decision.** Each item carries its `recommendationId`. Creating the row and being seen are separate events: rows are written with `shownAt: null`, and `POST /profiles/:id/recommendations/impressions` stamps the ids the client actually rendered (first write wins). The screen reports `clicked` on open, `saved` on add-to-list, and `dismissed_not_relevant` from a new "not a good suggestion" control on the work card; a watch goes through `POST .../watch-events` -- which marks the title watched *and* writes the `watched` outcome -- and names the recommendation it followed, instead of the server guessing the most recent one for that title. `ranked_later` needs no client: `TriadsService.recordRankedOutcomes()` already writes it. Readiness carries the model's own `confidenceBand`, so no screen requests a recommendation to read one.
**Rationale.** Every event in the loop now names the recommendation it belongs to, which is what makes a later comparison meaningful when a title is recommended more than once. And an impression that is asserted rather than observed is not a measurement: the split costs one small request and makes "shown" mean shown.
**Consequences.** `dismissed_not_relevant` is about the suggestion, never the film: the card is hidden and no title state changes (BP §2.4 #2). A dropped impression or outcome call is a lost measurement, never a lost action -- all of them are fire-and-forget except the dismissal, whose effect the reader sees. The watch path now honours the client's local day (`watchedOn`), which the state PATCH already did and the watch-event route did not.
**Revisit when.** Impressions need to distinguish "in the viewport" from "rendered" (an IntersectionObserver, and a stronger claim than this one), or an off-platform click (`opened_provider`) becomes reachable once availability has a data source (AVL-01).

## ADR-107 — A post-deploy canary walks the whole journey, and its rows are marked so nothing else counts them (P0-6)

**Context.** Every outage of 2026-09-05 passed `/api/health`: a model service that was never deployed (the loop ended at "still learning your taste" for ever), a boot that refused a renamed env var, a catalog that never loaded, an empty starter list. A process check answers "is it up"; nothing answered "can a person who signs in now reach a recommendation".
**Decision.** `npm run canary` (`apps/backend/src/scripts/canary.ts`) signs in as a fixed account -- registering it on first use, once, because registration is bucketed at five a minute per address -- and walks the real journey over the public API against `API_BASE_URL`: sign in → profile and consents → mark the starter films watched → rank rounds until the activation threshold (ADR-99) → poll `GET /profiles/:id/readiness` (ADR-103) with exponential backoff under the throttler → require `recommendation.status = ready` and a non-empty `/recommendations` → delete the profile it created, keeping the account. It runs as its own Railway Cron service every six hours, never as a pre-deploy gate. `--accounts N` walks N numbered accounts (`canary@kolme.app`, `canary+2@…`) in sequence; twenty of them is the readiness evidence, in place of a separate Alpha environment. Any failed journey exits non-zero (Cron failure notification) and reports through `captureException` with the step that broke. `users.isCanary`, stamped at registration from the address, keeps those rows out of the pooled retrain (`ConsentsService.pooledEligibleProfileIds`) and out of first-party analytics.
**Rationale.** The canary must be indistinguishable from a user to prove anything, which is exactly why it must be distinguishable to everything that aggregates users. The flag is set once at the door rather than re-derived from the address at each reader. The account survives each run because registration is bucketed at five a minute per address; the profile is what carries the rows, and every one of them cascades from it.
**Consequences.** One additive, defaulted migration (`isCanary`), so an older image still boots against a migrated database. `CANARY_PASSWORD` and `API_BASE_URL` are read by the script alone -- no boot contract change, and an unset one is a warning and a clean exit, never a page (the Cron service may exist before the owner sets it). A 401 that a registration answers with 409 is reported as "the account exists and `CANARY_PASSWORD` is not its password", which is the one thing the API cannot say from outside. A twenty-account run takes roughly `20 × (journey + 15s login spacing)`; the login bucket is per address, not per identity, which is what paces it.
**Revisit when.** The canary needs to assert *which* titles come back rather than that any do (that needs a fixed catalog it owns), or a staging environment exists and the journey should run there before production.

## ADR-111 — The screen shows the working logic instead of explaining it (UX-A mobile audit, 2026-09-05)

**Context.** The mobile audit at `cd31d86` (`docs/UX_AUDIT_MOBILE_2026-09-05.md`) measured a home screen of 13 cards, 6065px and 741 words with 56px posters and "unknown" stated 26 times; a triad screen whose save button sits at 1125px in an 812px viewport; a 113px two-row header duplicating the theme toggle; English Wikipedia paragraphs leading Arabic cards; and a 3714px profile page. The product's logic (rank three → learn traits → suggest in three lanes) was told in paragraphs and never shown.

**Decision.** One visual grammar across all screens: (1) poster first, ≥96px wide, and the poster opens the work page; (2) the four values (Q16) render as one "value strip" — fit bar + word in the accent, confidence as the bar's dashing/opacity, quality a muted number with its source, availability a platform chip or a hollow chip; unknown is a hollow mark, never repeated text; (3) the three lanes are horizontal shelves in their role colours (`--role-safe/discovery/outside`) under a "your taste so far" strip that states confidence once; (4) the triad, its numerals and its save button fit one viewport; (5) a single-row 56px header (menu · Kolme · search) with theme and language inside the menu (Q20); (6) the work page opens on a 16:9 backdrop (Q21) with the English synopsis collapsed; (7) the profile is a hub of four cards with sub-pages; (8) onboarding step 3 is replaced by a tappable poster grid. The brand is **Kolme** alone (O-13أ) with a three-card mark. Internal terms (`plackett-luce`, "صفحة العمل", "بصمة", "في هذا المسار") never reach the screen.

**Rationale.** Each item removes a place where the user had to read to understand what the shape could have shown. The tokens, type, radii and the two themes (Q1–Q15) are unchanged; this ADR spends them differently.

**Consequences.** UX-B implements screen by screen in the order in the audit §4, with before/after captures at 375px in both themes and no API contract change. Approved mockups: Claude Design canvas «نماذج Kolme للجوال»; source under `docs/design/mobile-2026-09-05/`.

**Amendment (owner, 2026-09-05, after comparing three palettes on the canvas).** The accent moves from the 3 September teal to a deep indigo: dark `--bg #06070f` · `--surface #10132a` · `--well #171b38` · `--line #232853` · `--muted #9aa0c8` · `--text #eef0ff` · `--accent #8b7cff` · `--accent-ink #12093d` · roles safe `#5fd0e6` / discovery `#e07cc8` / outside `#f0a050`; light `--bg #f4f4fa` · `--surface #ffffff` · `--well #e9e9f5` · `--line #d4d5e8` · `--muted #5e6285` · `--text #171a33` · `--accent #5b4bd6` · `--accent-ink #ffffff` · roles `#1e7fa0` / `#b0338f` / `#b85a10`. ## ADR-112 — Light and dark are sibling themes, not competing directions (owner correction, 2026-09-05)

**Context.** ADR-111 shipped one indigo family in both modes, while the owner's later, explicit reference makes «طاولة المونتاج» — white, blue and limited lime — the light identity; the current light tokens therefore describe implementation state, not acceptance. The visual split is an owner choice within the shared triad interaction (`BP §4.3`), separate value meanings (`BP §2.4 #7`) and bilingual surface (`BP §5.1`).

**Decision.** Preserve the existing near-black/deep-indigo dark mode. Replace only light with the selected GPT reference after the exact image is archived locally and semantic colours pass contrast review. Blue owns light-mode action/brand; lime is a bounded highlight whose role must be frozen before code. `system / light / dark` selection does not change.

## ADR-114 — People state intent; the system owns derived work (owner decision, 2026-09-06)

**Context.** Training already triggers after committed ranking thresholds and retries durably, yet Profile/Recommendations still asked a person to “train/update my model”; readiness even told them to fix schema, service and empty-catalogue states.
**Decision.** BP §2.4 #13 and §4.6 govern every interaction: ask only for a fact, choice, consent or authority the system cannot know. Persistence derived from that act, training, recomputation, synchronization, polling and technical retry are automatic. Consent, pause/resume, deletion and other destructive authority remain explicit.
**Contract.** `CapabilityReadiness.action` is limited to `mark_watched_titles`, `rank_more_triads`, `resume_processing`, or `null`. Eligible, failed, stale, catalogue-coverage and model-service states are `null`; a CTA may exist only when it executes the named user decision.
**Implementation.** Readiness and recommendation reads idempotently repair an eligible-but-idle or schema-stale model; Profile, Recommendations and Library poll derived state silently. Normal model controls are removed. `POST /profiles/:id/train` remains compatibility/operator recovery only and must not be surfaced by first-party UI.
**Failure boundary.** A manual retry remains acceptable only after an attempted read/write of the person’s chosen action, with draft preservation and idempotency; it is never required to advance derived work.
**Supersedes.** ADR-96’s manual training CTA and ADR-103’s `request_training`/`retry` actions; refines ADR-100/109/113 without weakening their visibility, retry, accessibility or privacy guarantees.

## ADR-115 — Permanent experience tracks evolve through controlled candidates (owner decision, expanded 2026-09-06)

- **Context and current state.** ADR-113 saved `cinema / premiere / montage`, but the implemented `Baseline v1` still shares typography, the Kolme mark, icon artwork, numeral treatment, motion grammar and composition; its material differences are mainly palette, radii and depth. It is an owner-approved visual baseline, pre-measurement, not an evidence-proven winner and not yet the required three complete experience identities.
- **Axis boundary (owner correction, 2026-09-06).** This ADR governs the **appearance** axis only: `cinema / premiere / montage`. Its goal is materially different page distribution, composition and form for each appearance. The “different visual atmosphere with the same user experience” goal belongs to the separate **theme** axis, `system / light / dark`, in ADR-112. Appearance tracks may share facts, tasks, permissions, state and business logic, but they must not collapse into one page layout with three palettes.
- **Permanent model and loop.** The appearances are permanent user-selected tracks, never temporary test arms, merger candidates or losers to remove. A saved choice follows its evolving track rather than freezing a release. Each track owns an independently versioned baseline and one active scoped candidate: adoption folds the result into the next baseline, rejection removes only that candidate, and the candidate slot—not the successful result or permanent track—is then replaced by a new idea starting from the latest baseline. `system / light / dark` remains an independent colour preference and may never overwrite an explicit saved track.
- **Protected directions.** `cinema` is immersive, image-led, atmospheric and deliberately low-density; `premiere` is curated, editorial, ceremonial and balanced between image and explanation; `montage` is fast, modular, constructive, information-dense and direct-action oriented. These promises are stable; their exact implementations remain evolvable candidates.
- **Required expression.** A mature baseline for every track must differ materially and coherently from the other two—not merely by recolouring—in composition, hierarchy, density, action placement, disclosure, palette, shape, depth, typography, in-product Kolme logo/lockup, icon language, numeric presentation, visual effects, motion grammar and the situations in which those devices are used. The differences accumulate through bounded candidates on the same shared journeys.
- **Typography and numbers.** Each track requires a distinct approved, licensed, self-hosted Arabic/Latin-capable type family or pairing, with its own display/UI hierarchy, weights, rhythm and numeric face; this supersedes IDENTITY Q9's one-family rule between appearance tracks while retaining ADR-94 and Q10–12's legibility and Latin-tabular-digit safeguards. Numeric presentation must also differ in prominence, scale, placement, enclosure, visualisation and disclosure—subordinate cinematic captions, aligned editorial facts, or prominent montage counters—while the source value, locale, unit, precision and rounding remain truthful and unchanged.
- **Brand and icons.** Each track requires a materially distinct in-product Kolme mark/lockup/art direction and icon family, not one asset merely recoloured: cinema may be open/luminous and contextual, premiere composed/title-card-like and precisely enclosed, montage flat/modular/film-strip-like and bolder. This refines IDENTITY Q22/Q24 between appearance tracks: the `Kolme` name and triad promise remain recognisable; a neutral legal/PWA master icon may remain shared; official third-party marks are never restyled; directional behaviour and action outcomes remain fixed. Every action retains its localised accessible name on the control, while decorative/redundant icons and graphic-only logo marks remain hidden from assistive technology.
- **Composition, effects and motion.** One route/component/state/data tree may expose track-specific composition, tokens and assets without becoming three products. Cinema uses measured fades, focus, continuity and shallow depth for scene entry and progressive reveal; premiere uses restrained fades, lifts and wipes for sequence, focus and confirmation; montage uses quick snaps, short slides and cuts for reorder, filtering, paging and immediate feedback. Difference must include trigger, purpose, choreography, easing and duration—not decorative timing alone—and motion may never delay input or carry essential meaning.
- **Shared truth and accessibility.** All tracks preserve the same tasks, content, permissions, API contracts, saved state, navigation destinations and fit/quality/availability/confidence meanings. Colour, type, mark, icon, number, layout or motion never changes a fact or acts as the sole carrier of meaning. Arabic/English legibility, RTL/LTR, zoom, contrast, focus, keyboard operation, 44px targets, performance and an equivalent static `prefers-reduced-motion` path are rejection guardrails, not tradeable success metrics.
- **Candidate discipline and evidence.** The existing task or PR names the track/surface and baseline, protected traits, one coherent hypothesis and bounded delta, what stays fixed, success signal, accessibility/performance guardrails, decision owner and rollback; baseline-restoring fixes are not candidates, and no second candidate opens in that track until the first closes. A bundled identity candidate supports only a bundle-level conclusion. Before sufficient eligible traffic, decisions use owner acceptance, task usability and formative research without causal or population-wide winner claims.
- **Rationale and learning outcomes.** Persistent diversity lets the product learn which ideas work, where and why without converging into three skins. Track-selection share describes self-selected preference—not superiority—because the default and populations differ; reasons require direct, voluntary research. An adopted learning may remain track-specific, be adapted differently to another personality, become shared behaviour when identity-neutral, or inform default policy; it is never copied literally across all tracks merely because one track is used more.
- **Consequences, privacy and revisit.** The first candidates must establish real structural differences on a shared core journey, then cumulatively complete every required identity dimension above; palette-only work qualifies only for a colour/contrast/accessibility hypothesis. `appearance_exposed / selected / changed` remain definition-only until actual rendering plus matching versioned disclosure, consent and enforcement are guaranteed; activation must distinguish `selectionOrigin: default | explicit | restored`, locale, colour preference, resolved mode and rendered baseline/candidate. Reports cover consenting users only, never upload pre-consent history, never record accessibility/assistive-technology settings, and attribute a motion effect only when rendered or else evaluate its static fallback as part of the bundle. Allocation, power/sample rules, surveys, dashboards and a registry remain deferred until a frozen candidate and eligible traffic support a useful predeclared plan. Removing or merging a permanent track requires a new explicit owner decision that supersedes this ADR, never a low usage count.

## ADR-116 — Cumulative catalog identity; no automatic rebind (CAT-1, 2026-09-06)

**Context.** At `378c152`, ordinal source IDs and an internalId-only upsert could attach new works to existing user history (`BP §13.1`).
**Decision.** `catalog.demo.identity.json` permanently reserves explicit internalIds and known Wikidata/IMDb/TMDB bindings, including excluded rows. Reordering the TSV is harmless; changing its reserved work is rejected. New reservations are additive and reviewed against the previous fixture.
**Rationale.** Provider identity, not translated title spelling or release year alone, distinguishes works. A remake requires distinct provider IDs; a cut, dub or subtitle variant belongs to `title_editions` under the same work.
**Enforcement.** Build/import reject collisions across all four identifiers; import checks the whole titles table under a write-conflicting transaction lock before any side effect. Database expression indexes reject provider collisions; a trigger forbids changes to existing UUID/internalId/provider bindings. Missing IDs may be added, never removed or replaced.
**Curation.** New Arabic overrides require a cited title and matching IMDb/Wikidata identity. A missing Arabic title remains excluded and fails the completeness gate; verified additions accumulate while builder metadata and evidence refresh from source. Only existing `fingerprint`, `posterPath`, `cultural` and downstream `evidence.plotSummaryAr`/`plotSourceAr` are retained; `titleArSource` and other builder evidence refresh. Partial probes never rewrite the fixture.
**Consequences.** `1788490000000-CatalogIdentityGuards` fails on legacy collisions or invalid identifiers without repairing data. Apply through the normal migration path only after reviewing legacy data; this task tests locally and does not deploy. Reservations are retained even for excluded works.
**Revisit when.** A provider merge/correction or true work-identity correction is verified: use a separate reviewed migration, never an automatic rebind, dedup deletion or replacement title.

## ADR-117 — Independent light admin shell, read-only monitoring and server-enforced capabilities (ADMIN-W0, 2026-09-06)

**Context.** At `dee0cd371eb6be73eabba0f3f3e4728d3291e4cd`, AdminScreen mixes four sections and one visible write under a single admin role. The owner's [control-center constraints](ADMIN_CONTROL_CENTER_2026-09-06.md) §2 require preservation, a fixed light admin theme and separate monitoring/administration; this is an engineering choice serving `BP §5.1`, `§21.3`.
**Decision — theme.** AdminShell uses locally scoped admin tokens, a local light marker and `color-scheme: light`, independent of consumer theme and appearance. It never rewrites root theme attributes or saved consumer preferences; returning to the consumer restores the same chosen experience. This is an admin-only exception to ADR-112/113/115, not a fourth consumer appearance.
**Decision — separation.** Monitoring performs reads, analysis and navigation only, with no mutation imports or indirect mutation calls. It may show `sampled` status and link to administration with the same record and filters; the existing sample action executes only in administration. The compatibility wrapper must preserve access to all four old sections without embedding mutation-capable legacy UI in monitoring.
**Decision — capabilities.** The target vocabulary is `admin.monitor`, `audit.read`, `catalog.manage`, `fingerprints.review`, `models.manage`, `users.manage`, `jobs.manage`, `settings.manage`. Roles compose explicit capabilities; authentication plus the server's per-operation capability and resource checks are the security boundary. Admin context controls UI availability only; cached roles, hidden controls and client checks never authorize a request. Unknown or absent grants deny access.
**Compatibility.** Refine ADR-26 through a server-owned, explicit temporary mapping of legacy `admin` to owner capabilities, preserving existing access without granting normal users administrative rights. Bootstrap the first owner outside the board; prevent disabling or removing the last owner's critical capability. New high-impact operations require reason, confirmation, atomic audit and readback, including failed/rejected-attempt handling as specified in the staged plan.
**Rationale.** Operators need stable, accessible information density and a trustworthy distinction between observation and change; least privilege must remain effective for direct API callers.
**Consequences.** This ADR records the target, not implemented capabilities. [W0 preservation and gates](ADMIN_W0_PRESERVATION_CONTRACT_2026-09-06.md) bind W0 → W1 → W2; old AdminScreen cannot be removed before its complete preservation matrix passes and its compatibility wrapper is delivered. W2 adds no new backend mutations or migrations; jobs, settings and experiment controls retain their later gates, with W5 before W6.
**Revisit when.** Owner constraints change, legacy-role migration can safely end, or a new operation needs a reviewed capability, owning API/schema contract and preservation evidence.

## ADR-118 — Publication is a policy-gated pointer to a reviewed revision, not a title flag (PUB-W0, 2026-09-06)

**Context.** The owner's 2026-09-06 catalog-scale decision lets CAT-1B/CAT-2 accumulate up to 1000 internally reserved identities (`IDENTITY_VERIFIED_PENDING_PUBLICATION`, `INCOMPLETE`) while the public release fixture stays at 389 (`BP §11`, `§6`); nothing in `titles` today tells "the identity exists" apart from "this exact content passed a publishability check and may be shown", and `posterPath`/`genres`/`description` are mutated in place with no history to review or roll back.
**Decision.** `title_revisions` holds one immutable content snapshot per accepted change (`titleEn`/`titleAr`/`description`/`posterPath`/`genres`/`releaseYear` plus the `source_records` ids it was built from); `titles."publishedRevisionId"` (nullable, `ON DELETE SET NULL`) is the only pointer every public read path may follow. Readiness is never a column the writer sets — a versioned policy evaluator computes it from a snapshot's own fields and its cited `source_records.licenseStatus`, the same append-only, never-overwritten-in-place discipline `source_records` already uses for per-field rights, scoped here to whole-snapshot publish gating instead.
**Policy `public-v1`.** A snapshot is ready only with a non-empty `titleEn`/`titleAr`/`description`/`posterPath`/`genres`, a resolved catalog identity (not `INCOMPLETE`/`UNRESOLVED`, `ADR-116`), and no cited `source_records` row whose rights have expired (`retentionUntil` in the past); `licenseStatus` alone never blocks during the free launch (`ADR-72`, `DATA_LICENSING.md` §0). Failure returns explicit `blockerCodes` (`POSTER_MISSING`, `DESCRIPTION_MISSING`, `GENRES_MISSING`, `IDENTITY_UNRESOLVED`, `LICENSE_BLOCKED`), never a silent default.
**Enforcement.** `publishedRevisionId IS NULL` must hide the title from every public surface — search, starter/detail, recommendations, counts, triads, direct UUID access, state and watch-events (owner rule 2026-09-06: no `UNKNOWN` standing in for missing content) — but the guard that does this (`publication-guard.ts`'s `wherePublished`/`PUBLISHED_TITLE_WHERE`) is built and unit-tested, **not wired into any consumer** (owner decision 2026-09-06, PUB-G1 scope review): connecting it while every title is still unpublished would empty the catalog everywhere at once, so wiring stays an explicit, separate follow-up.
**Publishing (board 1D-9).** `PublishTitleService.publish(titleId, expectedRevision, actor)` is the only writer of the pointer, and does all of it in one transaction: a `pessimistic_write` row lock on the title; `expectedRevision` must still equal the current pointer (`null` = "never published") or the call is refused `409 revision_mismatch`, so a decision made on a stale read can never land; the `public-v1` policy is re-run **inside** that transaction against the row's current state, never a cached preview, refusing `409 not_ready` with its `blockerCodes`; then a new immutable `title_revisions` snapshot, a conditional pointer switch (`affected !== 1` also fails closed), an `audit_log` row through the same manager, and a readback that must see the new pointer before the caller is told it succeeded. Manual only — one explicit admin call per title (`POST /admin/publication/titles/:id/publish`), no scheduler and no batch endpoint. A refused republish never unpublishes what is already live.
**Consequences.** Migration `1788496000000-AddTitleRevisions` (PUB-S1) created `title_revisions` and `titles.publishedRevisionId`; every title, including the 380 the shadow report already finds ready, keeps `publishedRevisionId = NULL` until 1D-9 runs. `PUB-B1`'s backfill closed the data gaps (`docs`/scripts under `pub-b1-*`) but set no pointer. No CAT-1B/CAT-2 record may bypass this by construction.
**Revisit when.** A licensed availability partner, human review step, or a second differentiated catalog needs its own policy version alongside `public-v1`.

## ADR-119 — Ranking a triad confirms its titles watched, via `watch_events`, not a parallel table (TRIAD-WATCH, 2026-09-06)

**Context.** `watched` (`user_title_states`) and `ranking` (`triads`) are already distinct facts — no code turns exposure into a preference (`BP §2.4` principle #2, `API.md`'s "does not imply liking"). But `TriadsService.rank()` never wrote `user_title_states` at all, so a triad could complete without its own three titles ever being recorded watched, and nothing distinguished a self-reported watch from one only known because it was ranked.
**Decision.** `rank()` upserts all three titles to `state: 'watched'` inside the same row-locked transaction as the completion, and records why via `watch_events.source = 'triad_ranked'` — a new value on the existing exposure-provenance log (`BP §6.2/§13.1`), not a second table answering the same question. A ranking wins even over an explicit `not_watched` set moments earlier through another tab: comparing three films is stronger evidence than the exposure list. `watchedOn`/`notes`/`importedRating` are never touched, and the new `watch_events` row's own `watchedAt` stays NULL — a ranking supplies no day (`DATE-01`).
**Enforcement.** `watch_events.triadId` (nullable, `ON DELETE SET NULL`) plus a partial unique index on `(triadId, titleId)` back the "at most three, once" contract; `CreateWatchEventDto`'s `@IsIn` never lists `triad_ranked`, so no client can claim it directly. `SET NULL` rather than cascade/restrict: `PrivacyService.reset()` deletes the triad row itself while this exposure history is explicitly kept (`PRIVACY.md` watch-history row) — verified live in `privacy.e2e-spec.ts`.
**Consequences.** Migration `1788492000000-AddTriadRankedWatchEvents`. `export.builder.ts` needed no change — `watchEvents` was already a plain `manager.find`, so the new source and column surface in exports automatically. Training's predicate (`status='completed' AND ranking IS NOT NULL AND NOT holdout AND purpose='learn'`) is untouched: `watched` still never enters the fit.
**Revisit when.** A second derivation path for `watched` needs its own source value, or `watch_events` needs a correction flow beyond today's append-only rows.

## ADR-120 — Additional posters are rows in `title_posters`, not a second column on `titles` (POSTERS-MULTI P1, 2026-09-06)

**Context.** `titles.posterPath` holds exactly one TMDB path per film (ADR-82). P0 measured `GET /movie/{id}/images` across the catalog at `d135564`: 378 of 389 titles (97.2%) have two or more posters, so the images the owner wants to show exist and only the place to keep them is missing.
**Decision.** A new `title_posters` table, one row per image: `titleId` (`ON DELETE CASCADE`), `posterPath`, `sortOrder`, a nullable `sourceRecordId`, `createdAt`, unique on `("titleId", "posterPath")`. Not an array column and not a `posterPath2`: each image carries its own rights row and its own order, which a column of paths cannot express, and the rights registry already works this way for every other per-field claim (`BP §11.3`).
**`titles.posterPath` is untouched.** It stays the single poster `PosterService` and every current caller reads, and the same path is also the `sortOrder = 0` row here — so this migration cannot break a consumer, and the poster a user has seen until now stays first when the carousel appears.
**Enforcement.** `CHK_title_posters_path` (`~ '^/[A-Za-z0-9_-]+[.][A-Za-z0-9]+$'`) turns ADR-82's "the path only, never a composed URL" from a comment into a constraint: a full URL cannot be stored and so cannot outlive the permission it was fetched under. `CHK_title_posters_sortOrder` keeps the order non-negative; the unique constraint makes P2's backfill idempotent and leads with `titleId`, so P3's batched read needs no second index. `FK_title_posters_sourceRecordId` is `ON DELETE NO ACTION`, like `localized_titles`: a registry row is superseded by a new row, never deleted, so a displayed image can never silently lose its provenance.
**Consequences.** Migration `1788494000000-AddTitlePosters`, schema only — nothing writes to the table until P2 backfills it, nothing reads it until P3, and no API or client shape changes in this step. TMDB's per-image metadata (language, size, votes) is deliberately not stored: `sortOrder` carries the decided order, and P2 owns how it is derived. The two check constraints appear in `schema:log` as proposed drops, the same pre-existing noise the four checks on `titles`/`profiles` already produce, because this repository declares checks in migrations rather than on entities; `synchronize` is off in every environment.
**Revisit when.** A second image kind (backdrop, still) or an image source other than TMDB is wanted — either needs its own column or table, not an overloaded `posterPath`.

## ADR-121 — Catalog intake: candidates live outside `titles`, jobs pull and verify, people reserve and admit (CAT-J1, 2026-09-06)

**Context.** The owner wants films pulled into the catalog periodically from more than one source, complete and without duplicates. Today a row in `titles` means "identity exists" (ADR-118), identity reservation is a reviewed Git step (ADR-116), ADMIN-W5 shipped the durable `admin_jobs` queue (ADR-117), and PUB-G1's guard was wired in `0585dca` but admission has not been authorised.
**Decision.** A new `catalog_intake` table holds every discovered candidate by its provider ids alone (partial unique indexes on Wikidata/IMDb/TMDB, format checks, no `internalId`), with per-field provenance, the `intake-v1` evaluation (`evaluatorVersion`, `blockerCodes`, `evaluatedAt`) and a status (`discovered | verified | blocked | duplicate | admitted`). Work runs as allowlisted `admin_jobs` types registered from `CatalogIntakeModule` via `registerType`: `catalog_verify` and `catalog_reconcile` are read-only reports over what is admitted; `catalog_pull` writes `catalog_intake` only; `catalog_admit` exists by name and refuses every call (`DEPENDENCY_DISABLED`, non-retryable) until the coordinator authorises admission in a reviewed commit. Sources implement `CatalogSourceAdapter` (official APIs and dumps only, each fact with its rights); Wikidata plus Wikipedia leads is the first. A timer on the `PublicQualityRefreshService` pattern (`CATALOG_PULL_INTERVAL_HOURS`, `CATALOG_PULL_CRITERIA`; off unless both are set) enqueues one `catalog_pull` row per period under an idempotency key — it never runs work inline and never publishes (ADR-118: manual publish only).
**Rules.** Never invent: an Arabic title comes from a Wikidata label, an arwiki page or a cited override, or the candidate stays `TITLE_AR_MISSING`. `DUPLICATE_OF_TITLE` and `POSSIBLE_DUPLICATE` are human-review flags — no automatic merge, deletion or rebind (ADR-116). `intake-v1` answers admissibility only; `public-v1` still decides publication after admission. This module reads `titles`/`source_records` and never writes them, and touches nothing under `publication/`.
**Consequences.** Migration `1788502000000-AddCatalogIntake`, additive. `GET /admin/catalog-intake` (+`/stats`, `/:id`) is the read-only queue the control center renders. The genre map and film classes mirror `fetch-catalog.ts`; `wikidata.lib.spec.ts` reads that file as text and fails on drift until an approved extraction lets both import one module. Enrichment is not a job type: the Python worker has no HTTP surface and W5 forbids shells, so intake only records `FINGERPRINT_MISSING`.
**Revisit when.** Admission is authorised (then `catalog_admit` gains the row-locked INSERT into `titles` + `source_records` + audit + readback under the seed's own preflight), a second adapter (TMDB) needs a per-field source policy, or W6 typed settings replace the two environment variables.
